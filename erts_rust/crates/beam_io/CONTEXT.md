# `beam_io` — Poller/Reactor, Ports, Port-Task Scheduling, Drivers, io-device Requests, Signals, CPU time, ddll

## Intent
Owns the **I/O subsystem** of the Rust ERTS rewrite (Stage 5, Part II §H) and the **OS/driver seam** — a clean rewrite seam (Part II §A) reproduced with the *frozen* driver C ABI (workspace `../CONTEXT.md` §1 **A.4**): a driver `.so` compiled against the unmodified `erl_driver.h` links and behaves identically.
Hosts the `mio`-backed **poller/reactor**, the **`Port`** (a process-like I/O endpoint over a `Box<dyn Driver>` + two byte queues), **port-task scheduling** (`erts_port_task_execute`), the **io-device request layer**, the **`Driver` trait + built-in drivers** (`fd`, `efile`, OS-child `spawn`, `tcp_inet`, `udp_inet`, `ram_file_drv`, `{line,N}` buffering, the text⇄binary phase change), the **driver C-ABI host layer** (`src/abi/`), and the safe raw-OS floors `beam_rt` (`#![deny(unsafe_code)]`) cannot issue itself: OS signals, CPU time, `ddll`, `fs_access`, `close_fd`.
A close is **asynchronous**: a port whose output queue is not empty when it is closed parks in `PortState::Closing` and the port layer finishes the teardown on the rounds that follow (`Port::close` → `PortRegistry::finish_closing_ports`).
Per-driver, `inet`, `abi` and io-device detail lives in the child nodes named by the Routing Table.

Four driver→owner side channels sit beside the port's own `{Port,{data,…}}` notification: the `{line,N}` frames (`LineNotification`), the completions (`PortCompletion`), the `{active,…}` deliveries (`ActiveInput`) and the failure latch (`PortFailure`); the grants an `{active,…}` delivery *spends* come off a drain beside them (`ActiveSpend`), and a driver's current `{active, Mode}` is read through `PortRegistry::active_mode`.
`beam_rt` is the only consumer: it owns the poll loop, the port run queues and the scheduler thread, drives one long-lived `Poller` + `PortRegistry`, renders those drains plus the once-only `take_exit_status`/`take_eof` as the owner's messages, and wakes a blocked receiver through `beam_process`.
`DynLib` is the one facility here with no consumer outside this crate (*Handoffs*).

## API Surface (FROZEN — dependents route here)
Re-exported at the crate root and via `beam_io::prelude::*`; only **frozen contracts and non-obvious behaviour** are listed, rustdoc carries the mechanical signatures.
Mechanism, per-suite and oracle detail for the port-level channels lives in `src/CONTEXT.md`; the driver, `abi` and io-device halves in their child nodes (Routing Table).

### `poller.rs`
- `Token(usize)` — opaque handle; **token `0` is the waker's**, user tokens start at `1` · `Interest` (`READABLE`/`WRITABLE`/`BOTH`/`ERROR`, **no empty mask**) · `Ready` — observed readiness, **no public constructor** · `Event` (`token`/`key`/`ready`).
- **`Interest::ERROR` is a caller-intent bit, not an OS request**: no backend takes an error request (`erl_poll.c`'s `ev2pollev` maps only `IN`/`OUT`), while `epoll`/`kqueue` — and the `poll(2)` fallback's `POLLERR`/`POLLNVAL` — report error readiness unconditionally, so the delivery half is `Ready::is_error()` and the registration mask never suppresses it.
- `Poller` owns `mio::Poll` **and the single `mio::Waker`**; `poll(timeout)` returns an **owned `Vec<Event>`** (`None` blocks) and is **`EINTR`-tolerant** — an `Interrupted` wait is retried and the retry **preserves the deadline**.
- Regular files are refused by epoll (`EPERM`), so `register` keeps a `libc::poll(2)`-backed fallback set merged into `poll`'s answer, capped (`FALLBACK_POLL_CAP`, 1 ms) so a non-empty set never blocks indefinitely.

### `timer.rs` / `queue.rs`
- `Timeout` (`Copy`) — one deadline · `Timer` — deadlines keyed by `u64`, self-contained (nothing in-crate consumes it): `schedule` replaces **any** deadline for a key, `pop_expired` returns due keys in **schedule** order · `ByteQueue` — a byte buffer whose `front()` is always contiguous.

### `port_task.rs` (port-task scheduling — `erts_port_task_execute`)
- Reduction constants: `CONTEXT_REDS` is `beam_common::CONTEXT_REDS` (4000), re-exported (no local copy); `PORT_REDS_{INPUT,OUTPUT,TIMEOUT} = 40`, `PORT_REDS_EXECUTE = 1000`; `PortTaskOutcome::reds_used` models the per-kind cost only.
- `PortTaskKind { Input, Output, Timeout }` (`priority()`: Input < Output < Timeout) · `PortTask` (`Copy + Eq`) · `PortTaskQueue` — one pending task per kind, ordered by kind **priority only**; a not-yet-due `TIMEOUT` stays queued (divergence: the C dequeues it, charges 0 reds and drops it); `arm_timeout` re-points/replaces a pending `TIMEOUT`. `Readiness`'s `read_ready()`/`write_ready()` both fold a poll **error** in (a poll error re-triggers **every** armed direction, the C's `ERTS_POLL_EV_ERR`).
- `ReadMessage { header, body: Option<Vec<u8>> }` — one completed read with the C `driver_output2` header/body split preserved: one `ReadMessage` is one **`driver_output*` call**, never one byte chunk; `body: None` is the C's `buf == NULL` and `Some(vec![])` a present empty body.
- `PortNotification::Data { port, read } | Closed { port }` — **exactly two variants** (exhaustively matchable by `beam_rt`: two arms, no wildcard); a round reports **one `Data` per `driver_output*` call**, in arrival order, and an explicit empty read is a real `{Port,{data,[]}}`.
- `LineNotification { port, header, bytes, eol }` — the **separate** channel a `{line, N}` port reports through, a struct rather than a third `PortNotification` variant so that enum stays exhaustive; `header` is the producing read's `ReadMessage::header`, prepended as cons cells to **every** frame that call completes.
- `ActiveInput { port, event }` / `ActiveInputEvent { Data(ReadMessage), Passive, Error(InetReason) }` — the **separate `{active, …}` input channel**, built like `LineNotification` so `PortNotification` keeps two variants and `CompletionEvent` gains none; `Data` keeps the header/body split, `Passive` is a spent `{active,N}` counter, `Error` a read failure, none carrying an atom (the runtime picks the message from the driving port's driver name).
- `ActiveMode { False, True, Once, Multi { remaining: i16 } }` + `ActiveSpend { Once, Multi }` — the **state seam** of the same `{active,…}` machine: `ActiveMode::from_parts(active: i32, active_count: i16)` is the **single** place the C's `INET_PASSIVE`/`INET_ACTIVE`/`INET_ONCE`/`INET_MULTI` = `0/1/2/3` encoding lives, `is_active()` is the C's `active > 0` test on the **mode** field, `remaining()` is the **running** `active_count` (`Some` only for `Multi`). `ActiveSpend` is a grant a delivery spent to exhaustion: `Once` flips the mode **silently** (the C sends no passive message) and `Multi` reports a counter that reached zero; `True`/`False` are never spent. Published through `Driver::active_mode`/`Driver::take_active_spends`, never by writing a mode into this layer.
- `PortTaskOutcome { ran, reds_used, notifications }` — `notifications` carries `PortNotification`s only; every other channel has its own drain.

### `port.rs`
- `PortState { Opening, Open, Closing, Closed }` · `DEFAULT_READINESS_RED_BUDGET = PORT_REDS_EXECUTE` · `PortControl::CLOSE == "close"` — the one **reserved** control-op name (any other name is a driver verb) · `PortCommandOptions { nosuspend, force }` — the `erlang:port_command/3` flag set, a `Copy` value the runtime validates once and carries through every retry of a suspended command.
- **`PortState::Closing` is a real, observable state**: `Port::is_closing()`, `Port::is_closed()`, `Port::output_len()`, `CLOSING_DRAIN_STALL_LIMIT` (16). `Port::close` is two halves — **begin** (`driver_flush()`, then a synchronous `drain_output_during_close()` under one `DEFAULT_READINESS_RED_BUDGET` through the ordinary output-task path, a pending `INPUT`/`TIMEOUT` task dropped first because a closing port has no owner left) and, only when the queue emptied, `pub(crate) fn finish_close` (driver `stop`, then `Closed`; a `stop` failure still leaves the port `Closed`, so it can never look open again).
- A queue that is **not** empty **parks** the port in `Closing` with an `OUTPUT` task pending and its poller registrations armed; `stop` has not run and the port stays in the registry. `note_closing_drain()` measures each round against the port's own `closing_watermark` and answers "give up" after `CLOSING_DRAIN_STALL_LIMIT` consecutive no-progress rounds (a **refused write during the drain counts as no progress**, a merely slow drain is never cut off). A second `close` on a `Closing`/`Closed` port is an idempotent `Ok(())`: no second `flush`/`stop`/`Closed` report.
- `PortCommandOutcome { Done, Busy }` + `Port::command(&mut self, data, options)` — the C's `erts_port_output` busy arm and **the one place the decision table lives** (rustdoc has the table): a non-`Open` port (a parked `Closing` one included) ⇒ `BadArg`; `[force]` **without** `DriverFlags::SOFT_BUSY` ⇒ the typed `notsup` raise, decided from the driver's **flag word** and **before** any output (`erl_bif_port.c:168-235`); `[force]` **with** it ⇒ `Done`, busy bypassed (`io.c:1731`); idle ⇒ `Done`, bytes queued plus one `OUTPUT` task (`io.c:1763`); busy with a plain or `[nosuspend]` command ⇒ `Busy`, nothing queued and no task (`io.c:1763-1769`).
- The driver-state accessors a runtime reads are plain forwards: `is_busy()` → `Driver::is_busy` · `port_closed()` → `Driver::port_closed` (a **latched, sticky** peer/OS close, so a drain made a round late still sees it) · `active_mode()` (with the **running** counter) · `awaits_callers_async_op()` · `take_active_spends()` (**oldest first**, consumed on take and **unstamped** — the registry's form is stamped).
- `Port::driver_as::<T>()`/`driver()` are the read-only views (the downcast is the accepted-socket adoption's route to a listener's driver); `PortControlReply { bytes, shape }` is the whole `erlang:port_control/3` reply, its rustdoc mapping `(shape, bytes, PORT_CONTROL_FLAG_BINARY)` onto the oracle's rendering (`Null` ⇒ `[]` for **every** flag word; `Buffer` + empty + flag ⇒ `<<>>`; `Buffer` + empty, no flag ⇒ `[]`; non-empty ⇒ a list, or a binary under the flag).
- **Every driver interaction — `start`/`output`/`ready_input`/`ready_output`/`control`/`timeout`/`drive_async`/`port_exit`/`flush`/`stop`, ten of them — installs all four sinks** (`DriverContext::with_reads`/`with_completions`/`with_active`/`with_failure`), the timeout and flush paths included because both discard the driver's `Result<()>` and a `flush` may hand a final completion up; the seven interactions that can plan I/O refresh the port timer from `Driver::next_timeout`. A write (`output`/`ready_output`) is **verified**: the queue must shrink by exactly the count the driver reported (else the typed `error::unsupported(...)`), and a non-empty queue left behind schedules an `OUTPUT` task.
- Line framing: `set_line_mode(Option<usize>)`/`line_mode()` (`Some(0)` = no limit) and `flush_linebuf()` (the C `flush_linebuf_messages`, run from the `take_eof`=`driver_eof` point; a `close` never flushes). A round harvests raw-mode input as ≤1 `PortNotification::Data` and in line mode stages `LineNotification` frames instead — detail `src/CONTEXT.md`.

### `registry.rs`
- `PortRegistry` — id allocation (inner `beam_process::PortTable`) + `HashMap<u64, Port>` by port number; `port_table`/`port_table_mut` expose that **same** id table.
- `close` runs `Port::close` and removes the port from the live map **only when it really finished** (`Port::is_closed()`), harvesting what its teardown staged; a **parked** port stays live with its number, descriptors and poller registrations. A port's **number** is retired only when its `Closed` notification is reported, so a deferred `Closed` can never name a reused id.
- `is_closing(id)` — whether `close` parked the port (still live: `contains` is true). `awaits_callers_async_op()` — whether **any** live port owes a parked caller an answer; keys are snapshotted first, so it is safe while iterating and it never touches a driver context.
- A private `finish_closing_ports` runs from **both** round drivers (`execute_port_tasks`, `handle_events`) **after** `reap_failures` and **before** the closed drain, so a port whose queue empties this round is reported `Closed` in that same round: it re-drains each live closing port under one `DEFAULT_READINESS_RED_BUDGET` through the same `drain_output_during_close`, then either finishes it (`stop`, removal, queued `Closed`) or leaves it parked. `reap_failures` uses the private forced `close_now` instead — a failed driver's queue is **dropped**, not drained (the C's `prt->ioq.size = 0` before `erts_deliver_port_exit`, `io.c:7220`).
- Frozen seams (all `BadArg` for an unknown id): `handle_events` (**schedules *and* runs** one round) and `execute_port_tasks` (port-number order under a reduction budget; async completions are driven *before* input is harvested) — or `schedule_events`/`schedule_readiness` to enqueue only, gated by `PortArms`; `port_command_with` (the registry surface of `Port::command`; the write itself belongs to the scheduled `OUTPUT` task) and its legacy `port_command`, which keeps its `Result<()>` signature; the accessors `is_busy`/`port_closed`/`active_mode`/`is_closing`/`awaits_callers_async_op`; `port_control` (reserved `"close"`; **any other `op`** goes verbatim to `control(op, arg)`); `take_exit_status`/`take_eof`; the timer seams; `notify_port_exit` (`Driver::port_exit` **at most once**, port left live); `drive_async`; `set_line_mode`/`flush_linebuf`; `take_failures` (the ports a driver closed from inside a callback, in reap order).
- The four owner drains share one rule — drain after **every** round, after **every** explicit driver interaction and after **every** `close`, because draining is what removes the entries: `take_line_notifications` (in **port-number order**), `take_completions`, `take_active_inputs` and `take_active_spends`, each followed by its `closed_*` queue that the removal fills — the spend queue **after** the driver's `stop`. A completion, delivery or spend staged before or at a `close` is reported **exactly once**.
- `port_control_reply(..)` is `port_control`'s reply **with** its `ControlReplyShape` (the reserved `"close"` arm answering an empty `Buffer`, since no driver ran and no reply pointer existed), while `control_reply_shape(id)` reports the shape of the port's **last** reply on its own; `port_control` keeps its unchanged `Result<Vec<u8>>` shape.

### `port_failure.rs` — the driver-failure channel (the C's `driver_failure*`/`driver_exit`)
A driver *closing its own port* is neither a return value nor a message, so it gets its own channel; `PortNotification` keeps two variants and `PortCompletion` stays an owner message.
- `FailureReason { Eof, Normal, Atom(String), Posix(i32), Code(i32) }` — the C's whole family, with `atom_name()`, `code()` and `is_eof()` (the flag that makes a `{line,N}` port flush its partial line first) · `DriverFailure { reason, signals_owner }`: `signals_owner` is `false` only for `driver_exit`, which unlinks the owner **before** closing, so rendering an `'EXIT'` would invent a message the oracle never sends.
- Flow: a driver latches one through `DriverContext::signal_failure` (**exactly one**; the three `deliver_*` seams refuse afterwards, the C's `-1`), `Port::take_failure` collects it, and the private `PortRegistry::reap_failures` tears the port down through the forced `close_now` after the callback returned — `stop` runs, the port leaves the live map, already-staged input is reported ahead of the close, and the number is retired only by the deferred `Closed` report. Both round drivers reap at the end of their round, and `output`/`port_control`/`drive_async`/`notify_port_exit` right after the single callback they made (a callback's own error is still the one reported).

### `driver.rs`
- `DriverFlags(u32)` (`SOFT_BUSY`) · `PortExitReason { Closed, OwnerExited, Normal }`. `SOFT_BUSY` **membership**: `tcp_inet` advertises it (`inet_drv.c:1374`), `udp_inet` (`:1432`) and `ram_file_drv` (`ram_file_drv.c:126`) do not — so `erlang:port_command/3` with `[force]` is the oracle's `notsup` on those two and `true` on `tcp_inet`.
- `ControlReplyShape { Null, Buffer }` — the second fact a `control` reply carries, which the bytes alone cannot: `Null` is the C's `*rbuf == NULL` (`*rbufp` tested **first**, `io.c:4134`), answered as the empty **list** for **every** flag word; `Buffer` is a real reply buffer, so zero bytes under `PORT_CONTROL_FLAG_BINARY` is `<<>>` and zero bytes without it is `[]`. Reported by the **defaulted** `Driver::control_reply_shape()` (`Buffer`, the honest answer for every built-in driver).
- `DriverContext<'a>` — the driver's view of its port and **the only way it touches the poller or the queues** (`register`/`reregister`/`deregister`/`input`/`output`; registration keys are the port number). Four delivery seams, each the typed `unsupported` without its sink (never flattened, never dropped) and each refusing once a failure latched in the same callback: `deliver_read(header, body: Option<&[u8]>)` (the `driver_output2`/`output_binary`/`outputv` seam; bytes banked on `input()` close into their own body-only read **first**) · `deliver_completion` · `deliver_active_input` (stamped with this context's own port, queued in call order) · `signal_failure` (a request and never a teardown).
- `pub trait Driver: core::any::Any` — **frozen**, with the one downcast path `impl dyn Driver { pub fn downcast_ref<T: Driver + 'static>(&self) }` (trait upcasting to `&dyn Any`, so no `unsafe` and no `as_any` boilerplate; every driver is therefore `'static`). Required: `name()` (+ `flags()`), `start`, `output`, `ready_input`, `stop`.
- Defaulted members that carry a contract (rustdoc has the rest): `has_control()` (**`false` iff the driver's C counterpart has `control == NULL`**, e.g. `ram_file_drv` — then `port_control/3` answers the oracle's `badarg`) · `is_busy()` (the `set_busy_port` **state**, `false` for every built-in, overridden by `abi::DriverPort`) · `port_closed()` (a **latched, sticky** peer/OS close for the runtime to render as `{tcp_closed, Port}`; overridden by `TcpInetDriver`) · `active_mode()` (`ActiveMode::False`) · `take_active_spends()` (default an **empty, allocation-free** `Vec`) · `has_pending_async()` (the **drive** gate) · `take_exit_status()`/`take_eof()` (only `SpawnDriver`). Further capabilities must be additive with defaults that keep the built-ins compiling.
- `flush(&mut self, ctx: &mut DriverContext<'_>) -> Result<()>` — additive **defaulted** (a no-op), the C's `drv->flush` (`io.c:3659` `flush_port`: the `!= NULL` slot test at `:3664`, the call at `:3687`). Called **once** from `Port::close`, after the port entered `Closing` and **before** the output drain, so what it leaves in `ctx.output()` is what the drain writes; a discarding flush takes the bytes off the queue itself and no count is verified (the C's `flush` is `void`).
- `flush`'s overriders: **`TcpInetDriver`** — the only discarding driver: `discard_output = !(token.is_some() && interest.is_writable()) || options.linger_zero`, then `ctx.output().clear()` (the C's `tcp_inet_flush`, `inet_drv.c:12708-12731`) · **`SpawnDriver`** — latches `terminating` only, the C's `fd_flush` · **`abi::DriverPort`** — forwards the loaded entry's slot, an absent one swallowed. `FdDriver`, `RamFileDriver` and `UdpInetDriver` inherit the no-op deliberately (`udp_inet`'s entry has a NULL flush slot, `inet_drv.c:1406-1443`; `ram_file_drv.c:120`).
- `awaits_callers_async_op(&self) -> bool` — additive **defaulted**, the wait predicate split from the drive predicate: default `self.has_pending_async()`. `TcpInetDriver`/`UdpInetDriver` answer their queued-op probe (**accept-inclusive** — a queued `accept` carries a real caller's `{inet_async,…}`); `abi::DriverPort` answers `false` (a `driver_async` job completes in the driver's own `ready_async`). The drive gate in `execute_port_tasks` stays `has_pending_async()`.
- `DriverFactory = fn() -> Result<Box<dyn Driver>>` · `DriverRegistry` — name→factory (the `driver_tab.c` seam); `with_builtins()` registers `"fd"`, `"efile"`, `"tcp_inet"`, `"udp_inet"`, `"ram_file_drv"`.
- **The statically-linked (emulator `driver_tab`) set is a separate, narrower contract** — `STATIC_SPAWN_DRIVERS: [&str; 3] = ["ram_file_drv", "tcp_inet", "udp_inet"]` + `is_static_spawn_driver`, `with_static_spawn_drivers()` and `create_static_spawn(name)`, which refuses a name outside the set with `BeamError::BadArg` (the oracle's `badarg` for `open_port({spawn_driver,"fd"},[])`) **even on a `with_builtins()` registry that registers them** — exactly the oracle's `erl_ddll:loaded_drivers/0` answer.

### `completion.rs` — the driver→owner completion side channel
A side channel beside `PortNotification` (two variants) and the `{line,N}` frames: a driver reports an asynchronous outcome here and the runtime turns it into the oracle's message.
- `PortCompletion { port, event }` — the port id stamped by `DriverContext::deliver_completion`, never by the driver · `CompletionEvent { InetReply { caller_ref, reply }, InetAsync { id: u16, result } }` — the `{inet_reply, Port, Reply[, Tag]}` and `{inet_async, Port, Id, Result}` shapes.
- `InetReply { Ok, Error(InetReason) }` · `InetReason { Closed, Timeout, Errno(i32) }` (`atom_name` = the lowercase POSIX name, with the C's `errno_<N>` fallback) · `InetAsyncResult { Ok, Data(ReadMessage), Accepted { fd }, Port(PortId), Error(InetReason) }`: `Data` keeps the header/body split and `Accepted` hands the descriptor over **owned**, so no teardown path can close it. `caller_ref` is the `prim_inet` caller tag carried **verbatim** (a 131-led `term_to_binary(Mref,[local])` image), never decoded here.

### `drivers/` — the built-in drivers (per-driver roles, verb tables, constants and suites: `src/drivers/CONTEXT.md`)
- `fd.rs` — `FdDriver`, the built-in `"fd"` byte-stream driver (owns its fds; line/phase modes, `Some(0)` = no line limit; the `line`/`noline`/`binary`/`text`/`getopts` verbs, unknown ⇒ `BadArg`; EOF de-registration with the fd still attached); `line_buffer.rs` + `binary_io.rs` are the two input-framing facilities. `efile.rs` — `EfileDriver`, byte movement delegated to a composed `FdDriver`, `make_efile()` its `DriverFactory`; a failed syscall ⇒ the raw `BeamError::Io` errno, an unopened port / unparsable argument ⇒ `BadArg`.
- `spawn.rs` — `SpawnDriver` (`name() == "spawn"`), the **only** module here that may spawn OS children; **constructed** (`with_stream_options`) and **really spawning** in the constructor, reaping eagerly (`take_exit_status()`/`take_eof()` once only); `SpawnSpec`/`SpawnOptions`/`StreamOptions`/`SpawnStream`/`build_command` are the term-free `open_port/2` shape (empty command/path or argv ⇒ `BadArg`). `stop`'s order: `deregister` both fds → `close_stdin_for_eof()` → a **bounded** `reap_after_stdin_eof` (`CHILD_EXIT_WAIT_MS` 250 ms, probing every `CHILD_EXIT_POLL_MS` 5 ms, draining the child's stdout meanwhile) when `flush` latched `terminating`, else the abrupt `reap_child()` → `close_fds()`.
- `ram_file.rs` — the built-in **`ram_file_drv`** (`RamFileDriver`/`make_ram_file`): a command-driven port (an opcode byte on the output queue → a reply on the input queue) over a `Vec<u8>`, the C's 13 opcodes and its `OK`/`NUMBER`/`DATA`/`ERROR` reply encodings.
- `inet/` — the built-in **`tcp_inet`** (stream) and **`udp_inet`** (datagram) drivers, one socket behind one port, reached via `open_port({spawn_driver, tcp_inet | udp_inet}, …)`; shared `wire.rs`/`opt.rs`/`sys.rs`/`stat.rs`, `{packet, 1|2|4}` framing on the read path and on **both** `tcp_inet` write routes (named `send` and `erlang:port_command/2`), `opcode.rs` decoding the decimal `erlang:port_control/3` numberspace onto the same named-verb bodies, and **no** write-side framing on `udp_inet`. A write header is prepended **once per command**, announcing the **payload** length after the `prim_inet` caller-tag strip and **after** the connection guard, with `stat.send_oct` counting header + payload.
- **The read path's ordering rule: a complete buffered unit wins over a pending peer close** (the C's `tcp_recv`, `inet_drv.c:13130`, delivering at `:13216-13217`/`:13229-13230` and reaching the `n == 0` → `tcp_recv_closed` arm at `:13206-13208` only on a later call). `read_bytes` **records** the close in `TcpInetDriver::pending_close` and never latches; whether it is then applied is the caller's `ReadReport` — a **selected** read (a queued `TCP_REQ_RECV`, the `recv` verb, an `{active,…}` delivery) applies it, only the reactor's eager passive read (`ReadReport::Unselected`, the passive `{Port,{data,…}}` delivery shortcut) does not, so `{Port,{data,…}}` still precedes `{tcp_closed,…}`; `read_available` latches before queueing the bytes it just read, `try_complete_recv` leaves the observation in `pending_close` and applies it through `latch_pending` only when no complete unit is left, and `latch_peer_close` is the **single** latch site. Why the split: the C selects a socket's read side only for a granted `{active,…}` or a waiting `TCP_REQ_RECV`, so a peer close an eager passive read stumbles on has **not** been discovered in the C's terms and must not end the connection (the invariant in full: *The read-selection invariant*, below).
- `SocketOptions::linger_zero` — the C's `TCP_ADDF_LINGER_ZERO` (`inet_drv.c:864`), latched in `opt_sys.rs` **before** the `setsockopt` so a failing syscall still records it, inherited by `inherited_from`, never reported to `getopts`; one of the two conditions `TcpInetDriver::flush` discards queued output on. `TcpInetDriver::stop` calls `release_socket(ctx)` and **never touches the ioq** (the C's `tcp_inet_stop`, `:11895-11924`); `desc_close`'s unconditional `tcp_clear_output` belongs **only** to the close verb (`:11932-11939`).
- `TcpInetDriver::from_accepted(fd, listener)` — the C's `tcp_inet_copy` (`inet_drv.c:11795`) as an additive inherent constructor: adopts `fd` **owned** exactly as `from_socket` does, then applies the listener's inherited option set plus its cached `stype`/`family`; it is the **only** copy path (`INET_REQ_FDOPEN`'s `adopt_prebound` copies nothing, as the C's `inet_ctl_fdopen` does). `peer_closed()` is the driver's latched peer-close observation, mirrored by `Driver::port_closed`.
- **The async-op queue** (the C's `desc->async`): one receive slot (`INET_MAX_ASYNC = 1` ⇒ a second concurrent receive answers `[0]"ealready"`; an id is consumed even by a refused enqueue) + a multi-op accept list; `deadline_for` merges into `Driver::next_timeout`; `drain_closed` answers `{error, closed}` **exactly once** per pending op. Served: `TCP_REQ_RECV`(42), `ACCEPT`(26) (its `Accepted { fd }` handed off **owned**) and `udp_inet`'s `PACKET_REQ_RECV`(60); `INET_REQ_CONNECT`(3) is a bounded synchronous wait consuming no async id (a documented divergence).
- Per-driver detail — the `init_caller` rows, the `{active,…}` matrix, the inheritance field list, the opcode/verb table and the type ⇄ recv/send/accept matrix — is `src/drivers/CONTEXT.md` and `src/drivers/inet/CONTEXT.md`. **A.4 residuals** (never a wrong result): the improper `[hdr|<<body>>]` DATA reply renders through `ReadMessage`; `INET_REQ_FDOPEN`'s prebound descriptor is never closed (borrowed, port-lifetime); `ignorefd`/`tcp_sendfile` reproduce their refusals only.

### Write shutdown — the answer matrix (oracle-measured, OTP 29.1.1)
### The read-selection invariant (why an eager read past a half-close is not the C's)
The C selects a socket's read side in exactly two states — a granted `{active, …}`
(`sock_select(desc,(FD_READ|FD_CLOSE),(desc->active>0))`, `inet_drv.c:7966`) and a waiting
`TCP_REQ_RECV` (`:12317`) — so every read it makes is one somebody answers (the active owner, or the
queued receive via `async_error_am_all(am_closed)`, `:12829`). This floor's poller is edge-triggered
and keeps `READABLE` registered for the socket's whole life, so the reactor also reads a **passive**
socket with no receive queued: that read is a *delivery* shortcut for the passive
`{Port, {data, …}}` channel, not a discovery. It is reported as `ReadReport::Unselected`: the bytes
are delivered, and a close it finds is recorded in `TcpInetDriver::pending_close` and applies
**nothing** — no `delayed_close_recv`/`delayed_close_send`, no teardown. The first read the C *would*
have made (a queued `TCP_REQ_RECV`, the `recv` verb, or an `{active, …}` delivery) applies it —
`ReadReport::Answered` on the `read_available` path, `latch_pending`/`latch_peer_close` on the two
that read through `read_bytes` themselves — which is why `tcp_recv_closed`/`tcp_recv_error`'s reply
ladder is unchanged in the selected case. `pending_close` is sticky (a reset is reported by `read(2)` once) and
is cleared only by the latch.

Consequence, measured against OTP 29.1.1 / erts-17.1: after `gen_tcp:shutdown(S, write)` a
zero-length `gen_tcp:send` answers `ok` **for ever** (nine calls spaced ~40 ms: `{ok,ok,[ok×8]}`),
because the C never observes the peer's end-of-file in that state; the first non-empty send answers
`{error,closed}` and every later send `{error,enotconn}`. A read discovery also arms **no**
`TCP_ADDF_DELAYED_CLOSE_RECV` (C-exact: `tcp_recv_closed` arms only the send one-shot, `:12816`), so
after a queued receive was answered `closed` the next receive is the torn-down `enotconn`.


`gen_tcp:shutdown(S, write)` (the `TCP_REQ_SHUTDOWN` control verb) only records the intent: the socket
is *not* closed and its state stays `{ok,[connected,open]}` (`GETFD` still answers the descriptor). What
the next operations answer is `PeerClose`'s two one-shot ladders (`drivers/inet/mod.rs`), armed by the
**first failing write**, never by the shutdown itself:

| step | answer |
|---|---|
| `shutdown(S, write)` | `ok` — and again `ok` while no write has failed yet (idempotent) |
| any number of **zero-length** `send` (`<<>>`, `[]`, `[<<>>,[]]`) | `ok` for ever (the write-shutdown arm of `TcpInetDriver::write_command` in `async.rs` answers them without writing) |
| the **first non-empty** `send` | `{error, closed}` (`TCP_ADDF_DELAYED_CLOSE_SEND`, `inet_drv.c:12681`-`:12692`) |
| **every later** `send` (non-empty *or* zero-length) | `{error, enotconn}` (the one-shot spent) |
| `shutdown(S, write)` **after** a failed write | `{error, enotconn}` |
| `shutdown(S, read)` after the write latch | `{error, enotconn}` |
| `recv` after a **write**-latched close | the first answers `{error, closed}`, later ones `{error, enotconn}` — a write discovery arms the receive one-shot too (`tcp_send_or_shutdown_error`, `:13660`-`:13685`), so the read path needs nothing extra |
| the peer | receives every pre-shutdown byte, then `{tcp_closed, S}` |

`shutdown(S, read_write)` is **racy on the oracle** and is deliberately not pinned.

Pinned by `drivers/inet/write_shutdown_matrix_tests.rs` (the answer matrix over a `Rig`) and, end to end,
by the differential corpus's `inet_write` group — `shutdown_write_then_send_closes_the_writer`,
`repeated_write_shutdown_keeps_the_writer_closed`,
`empty_payload_after_write_shutdown_is_a_noop_success`, `send_counters_advance_with_the_writes`,
`both_directions_of_the_stream_write`, `write_answer_matrix`, `empty_payload_is_a_successful_noop`.

### The command accounting invariant (zero-length commands included)

`InetStat::output(len)` counts a **command**, not a write: every command that reaches
`TcpInetDriver::write_command` advances `send_cnt` by one and adds `payload + h_len` to `send_oct` — so a
**zero-length** command advances `send_cnt` and adds nothing, `inet_drv.c:11560`-`:11582`
(`inet_output_count`) running *before* `tcp_sendv`'s `(h_len == 0 && len == 0)` shortcut (`:13736`). The
write-shutdown arm therefore calls `self.stat.output(0)` before it returns. `send_pend` is **not** the
driver's: it is the port's own output-queue depth, rendered from `ctx.output().len()` at `inet:getstat/1`
time, and the `usize` a command returns is what `Port` charges against that queue
(`check_write_accounting`, `port.rs`) — a zero-length command consumes only its stripped caller tag, so
the arm returns the same figure the normal path's net shrinkage would. Oracle-measured figures (the
zero-length rows included) live in `drivers/inet/stat_send_tests.rs`'s `RAW_ROWS`.

## Constraints
- Errors: **`beam_common::{Result, BeamError}` only**; I/O/syscall failures⇒`BeamError::Io`, argument faults⇒`BeamError::BadArg`, id/registration exhaustion⇒`BeamError::SystemLimit`. Never panic on runtime data, never `unwrap()`, never `todo!`/`unreachable!` in shipped code.
- **Safe Rust by default.** `unsafe` only in the raw syscall wrappers (`read`/`write`/`pipe`/`fcntl`/`open`/`dup`/`fstat`/`lseek`/`fsync`/`ftruncate`/`close`, the spawn driver's `fork`/`execve`/`waitpid`/`dup2`, `inet`'s `setsockopt`/`getsockopt`, `cpu_time`'s `getrusage`/`clock_gettime`, `signal`'s `pipe2`/`sigaction`, `ddll`'s `dlopen`/`dlsym`/`dlclose`, `fs_access`'s `access`/`geteuid`/`getegid`), `mio::unix::SourceFd` construction, and the `abi` host's raw `ErlDrv*` handling; every block carries a preceding `// SAFETY:` rationale and `unsafe_op_in_unsafe_fn` stays clean.
- **Port ids come from `beam_process::PortTable`** — no second number allocator; a failed `start` runs the driver's teardown (deregistering any fd) and releases the number — no id-space/poller leak.
- **Single-thread invariant (enforced).** `Port`/`PortRegistry` are **not** thread-safe and this crate has no locking: create and drive them from **one OS thread**. `PortRegistry` carries a `PhantomData<core::cell::Cell<()>>` marker so it is neither `Send` nor `Sync`; `DynLib` is likewise not `Send`/`Sync` (`Poller`/`Waker` are exempt — the waker must cross threads; `SignalFacility` is process-global).
- **Only `drivers/spawn.rs` may spawn OS children**; the `signal`/`cpu_time`/`ddll`/`inet`/`file` modules never fork/`Command::spawn`.
- **A `Closing` port must always be able to finish.** Whatever a drain does — a short write, a refused write, a driver that never consumes — the close completes: the park is bounded by `CLOSING_DRAIN_STALL_LIMIT`, and the teardown (`flush` → drain → `stop` → `Closed` → number retirement) runs exactly once per port.
- **The `Driver` trait, `DriverContext`'s public methods and the `Port`/`PortRegistry` signatures are the frozen driver seam**, extended only by **additive, defaulted** members that leave every existing implementor and call site behaving as before (`flush`/`awaits_callers_async_op` defaulting as above, `is_busy`/`port_closed` to `false`, `active_mode`/`take_active_spends` to passive/no spends, `is_closing`/`output_len`, `port_command_with`) — never by changing an existing signature. Files target ~1000 lines. Deps: `beam_common`, `beam_term`, `beam_process`, `beam_abi`, `beam_alloc`, `libc`, `mio` only (see *Design Decisions* for the `beam_io → beam_abi`/`beam_alloc` edge).

## Design Decisions
- **`mio` backend.** A portable, safe `Poll`/`Registry`/`Waker` behind a **mio-independent** API (`RawFd` + `Interest`/`Token`/`Ready`), so another backend could be added later (io_uring/`/dev/poll` is **not implemented today**). The epoll backend is **edge-triggered** (`EPOLLET`), so a driver must drain a readable descriptor to `EAGAIN`; fd registration is Unix-only, so Windows/iocp is out of scope (as in `beam_abi`).
- **The `Port` owns both `ByteQueue`s, not the driver** (the C `ioq`): `Port::output` appends then calls `Driver::output`, which **pulls** from `ctx.output()` — no double buffering.
- **The parked close is the C's Limbo state, with a valve of our own.** A close with a non-empty queue goes through `flush_port` → `ERTS_PORT_SFLG_CLOSING` and finishes at the driver-callback epilogue (`io.c:3946-3971`, `erl_port.h:798-812`), which is why `PortState::Closing` exists: the bytes are the caller's and must still be written. The C has **no bound** there, but this port layer must always be able to complete a close, so `CLOSING_DRAIN_STALL_LIMIT` (16 consecutive no-progress rounds, any shrinkage resetting the count) is a **documented divergence**: without it a driver that cannot write a byte would hold the port number, its descriptors and its poller registrations indefinitely and the owner would never be told. A slow drain is never cut off.
- **Task execution here, the scheduler thread above.** The poll loop, port run queues and scheduler-charged reductions are `beam_process`/`beam_rt`; only `execute_port_tasks` yields `Data`/`Closed`.
- **Readiness ⇒ task, gated by `PortArms`**: a full close (`EPOLLHUP` ⇒ `read_closed` **and** `write_closed`) schedules no bogus OUTPUT task on a read-only driver. A poll **error** reaches both armed directions (C parity). **Divergence:** the C keeps three FIFO queues with no cross-kind priority; here one queue is kind-priority-ordered (INPUT → OUTPUT → TIMEOUT) — observable only in the order two *different* kinds run in a round.
- **The spawn driver is constructed, not registered, and reaps eagerly:** a `DriverFactory` cannot carry command/argv/options, so it is built from a `SpawnSpec`; the child starts in the **constructor** (a failed spawn registers nothing and `os_pid()` is readable before `PortRegistry::open`); `{fd, N}` adopts a descriptor as a **duplex** stream and never closes it.
- **The TCP/UDP drivers are a floor, not a full `inet`** — the served verbs, the framing types and the `{active,…}` matrix are oracle-cross-checked (see `src/drivers/inet/CONTEXT.md`).

## Known Issues
- **`FdDriver` is deliberately minimal** (byte-stream only; no output line framing, no packet framing) and **`SpawnDriver` is the OS-child floor**, not the whole `spawn` driver — synthesizing `{Port,{data,…}}`/`{Port,{exit_status,…}}`/`{Port,eof}` from its bytes, latched EOF and once-only exit status is the runtime's job. Per-driver limits: `src/drivers/CONTEXT.md`.
- **A control verb's *operand* is decoded by the caller, but its *opcode* is not.** `port_control(op, &[u8])` takes a `&str` op + raw bytes: packing `erlang:port_control/3`'s `Data` term into the C's request payload is the runtime's job, while an integer `Op` is forwarded as its **decimal string** and decoded onto the named verbs by `src/drivers/inet/opcode.rs`. The `INET_REQ_*` surface, its guard order and its refusal-only arms are `src/drivers/inet/CONTEXT.md`'s.
- **The inet drivers' `port_command/2` path adopts the failure seam; the `init_caller` rule is size-only** — the tag's bytes are **never inspected**, so a *plain* payload reads as a huge length and is the C's `FALSE`. The four oracle-measured rows (malformed, socket-less/unconnected, empty queue, empty/non-ETF tag) are `src/drivers/CONTEXT.md`.
- **A completion is addressed to the port's owner, not to the C's `driver_caller`.** `InetReply`/`InetAsync` are staged with `deliver_completion` and drained by `take_completions`; the C sends to `desc->caller`. Rendering and delivering is the runtime's (*Handoffs*).
- **The busy-port decision table is the whole of the flow control this crate owns.** `Port::command` owns it and answers a `PortCommandOutcome` (or the typed `notsup`), and `PortRegistry::port_command_with`/`is_busy` expose it; the **caller-blocking** half of a plain command on a busy port (suspend the caller, re-issue once the driver clears the state, answer `true`) is a scheduler operation needing a process this crate has none of, so it lives in `beam_rt` (`crates/beam_rt/src/port/busy_wait.rs::issue`, see *Handoffs*).
- **The loaded-driver write path has no byte-count/remainder by design — the C's `output`/`outputv`/`ready_output` callbacks are `void`.** Counting the whole drained buffer as written is exactly the C (`prt->bytes_out += size`); do not "fix" it into a remainder.
- **The output queue is one byte stream with no per-command boundary.** The `{packet,1|2|4}` header and the `send_oct` charge are decided **once per command**, at the point the command is queued and after the connection guard, so a **second** command queued behind a still-stalled partial write is not framed or counted independently: its bytes land behind the first command's remainder, where the framing and accounting latches are still set. The `prim_inet` caller-tag strip shares that property, exactly as the C's single `ioq` plus its one `tcp_sendv` call per `port_command` do (`src/drivers/CONTEXT.md`).
- **Driver-readiness residuals.** `DriverState::fd_armed` hands `ready_input`/`ready_output` the first `BTreeMap`-ordered fd matching the direction, so a multi-fd port would starve the others (harmless for every current driver — one fd each). A `{fd,N}` spawn port keeps an `Interest::BOTH` registration for its life, so a spurious `OUTPUT` task is scheduled on every write-readiness event.

## Handoffs (beam_rt — out of this node)
**Adopted upstream:** `{line,N}` framing (`set_line_mode` + `take_line_notifications`), the completion channel (`take_completions` → `crates/beam_rt/src/port/completion.rs`), the driver-failure channel (`take_failures` → `crates/beam_rt/src/port/failure.rs`), the `{active,…}` input channel (`take_active_inputs`/`take_active_spends`/`active_mode` → `crates/beam_rt/src/port/active_input.rs`), the peer-close latch (`port_closed` → `crates/beam_rt/src/port/peer_closed.rs`), the control-reply **shape** (`port_control_reply`'s `ControlReplyShape`, rendered by `crates/beam_rt/src/native/port.rs::port_control`), the `#file_info{}` `access`/`uid`/`gid` path, the signal and CPU-time facilities, `create_static_spawn`, the once-only `take_eof`, the port-monitor id table, the `{get_until,…}` io request, `ram_file_drv`'s port path, the busy-port caller-blocking wait (`crates/beam_rt/src/port/busy_wait.rs`), `erlang:port_control/3` and a refused command's `badarg`.
**A closed port is not gone at `close`'s return.** A parked close leaves the port live — `contains`, `is_closing` and its poller registrations all still hold — and `erlang:port_command` on it is the C's `badarg` (`io.c:3877-3880`). The `Closed` notification arrives from a **later** round and the number retires with that report, so `beam_rt` must not drop its port-table entry at `close`'s return and must keep driving rounds (or read `is_closing`) until the `Closed` it drains names the port.
**The two async predicates: `has_pending_async` drives, `awaits_callers_async_op` waits.** `has_pending_async` answers "work a round must drive" and `awaits_callers_async_op` answers "an answer is still owed to a waiting process"; `beam_rt`'s caller-blocking port wait reads the **drive** predicate instead (`crates/beam_rt/src/context/pump.rs::wait_for_port_event` → `Runtime::ports_awaiting_async` → `beam_rt`'s own `PortRegistry::awaits_async_completion`, which folds `beam_io`'s `Driver::has_pending_async` over the live ports) and counts delivered port events per round to detect progress, because a listener's standing accept interest must keep that wait alive — the answer being gone is caught by the delivery count, not by the wait-side predicate.
**The busy-port flow control is complete on the `port_command` route.** `beam_rt`'s `erlang:port_command/2,3` reaches this crate's decision through `PortRegistry::port_command_with` (`crates/beam_rt/src/port.rs::RuntimePorts::command_with_data`, its `decide_before_data` gate and then `PortRegistry::command`), and the caller-blocking half is `crates/beam_rt/src/port/busy_wait.rs::issue`: a caller that owns the scheduler pass pumps bounded rounds until `PortRegistry::is_busy` clears and then re-issues the command, while a caller inside a slice parks (`PortWrite::Parked` → `BifOutcome::Suspend`, the instruction re-run on resume) — the C's `erts_suspend` + `ERTS_BIF_YIELD3` re-run.
**Residual of the busy-port flow control:** the wait is bounded by a 5 s deadline where the C is unbounded (`BUSY_PORT_DEADLINE`), and the `send`-to-port route (`erlang:send/2,3` and the inline `Instr::Send`) cannot consume a suspend latch, so a plain command on a busy port there — like `RuntimePorts::write_command`, which holds no `Runtime` to pump with — stays the typed `NO_PUMP_REASON` gap.
**The control-reply shape is the fact the bytes cannot carry, and this crate reports it.** `PortControlReply { bytes, shape }` (`PortRegistry::port_control_reply`) is the whole `erlang:port_control/3` reply: `ControlReplyShape::Null` is a driver that answered `*rbuf == NULL`, which the oracle renders as the empty **list** `[]` for **every** flag word (`io.c:4134` tests the pointer first), while `Buffer` + zero bytes + `PORT_CONTROL_FLAG_BINARY` is `<<>>` (`io.c:4136-4162`). The flag word is not part of this seam's reply (`PortControlReply` carries bytes + shape only) and the rendering is `beam_rt`'s (`crates/beam_rt/src/native/port.rs::port_control`); `PortRegistry::control_reply_shape` reports the last reply alone and is `BadArg` for a port a driver reaped from inside its own `control` callback, so a caller that must not lose the shape takes the combined call.
**The driver-failure channel: this crate latches and tears down, the runtime renders.** A driver that closes its own port latches exactly one `FailureReason` (`DriverContext::signal_failure`); `reap_failures` runs the forced teardown after the callback returns and `PortRegistry::take_failures` hands the term-free `PortFailure { reason, signals_owner }` up in reap order, the driver's `stop` already run and the `Closed` report already minted, with the bytes that callback delivered ahead of it (`take_reaped_notifications` re-prepends them). Rendering the owner's `{'EXIT',Port,Reason}` / every monitor's `{'DOWN',…}` from it, gated on `signals_owner`, is `beam_rt`'s (`crates/beam_rt/src/port/failure.rs`).
**The `{active,…}` channel: this crate produces the delivery, the runtime renders the message.** `take_active_inputs` (drained after **every** round and after **every** `close`) answers one `ActiveInputEvent` per driver delivery with the read's `header`/`body` split intact, `take_active_spends` reports the grants a delivery spent (`Once`/`Multi`), and `active_mode(port)` answers the driver's live mode with its running counter; the messages themselves — `{udp, S, IP, Port, Data}` (the 7 packed header bytes split into `{IP, Port}`), `{tcp, S, Data}` under the port's `[list]`/`[binary]` shape, `{tcp_passive,S}`/`{udp_passive,S}` and `{tcp_error,S,Reason}`/`{udp_error,S,Reason}` with the atom chosen from the driving port's driver name — are `beam_rt`'s (`crates/beam_rt/src/port/active_input.rs`), as is the `{mode, list|binary}` decision (`{mode,…}` never reaches this crate). A datagram header is one `INET_AF_INET` packed record, the only family the inet drivers here serve. **Do not add a variant to `PortNotification`** (two arms, no wildcard) and do not route these through `CompletionEvent`.
**The completion channel: this crate stages, the runtime addresses and renders.** `take_completions` (drained after **every** round and after **every** `close`) answers one `PortCompletion` per event, port stamped by `DriverContext::deliver_completion`; `beam_rt` (`crates/beam_rt/src/port/completion.rs`) renders `{inet_reply, Port, Reply[, DecodedTag]}` (decoding the 131-led `caller_ref` with `beam_codec`) and `{inet_async, Port, Id, Result}`, and adopts an `InetAsyncResult::Accepted { fd }` into a **second** port (`TcpInetDriver::from_accepted(fd, listener)` or the served `INET_REQ_FDOPEN`) **or** closes it — `beam_io` never closes it. A **built-in** driver port has no term path of its own (`PortMeta::driver_terms` is `None` for `PortName::SpawnDriverBuiltin`); `PortEvent::Term` exists only for `dlopen`ed driver ports.
**`driver_caller`.** The C sends `{inet_reply,…}` to the command's `desc->caller`; this floor stages it for the port's **owner**, so addressing the reply to the caller needs a caller notion the frozen seam lacks.
**The delivered-data term shape (`mode` list vs binary) and the `LineNotification` header stamp are the runtime's.** `PortNotification::Data` carries bytes while the C's `tcp_reply_data` builds the term from `desc->mode`; `beam_rt` matches `{ port, read }`, renders the oracle's improper-list shape and stamps a `LineNotification`'s `header` as the same cons prefix on `{eol|noeol, Data}`.
**`tcp_inet` peer close → `{tcp_closed, Port}`: this crate observes, the runtime reports.** `TcpInetDriver` latches the observation (`peer_closed()`, mirrored by `Driver::port_closed`, sticky; `recv`/`send` answer `[0]closed`/`[0]enotconn`), and the latch is read once per port-task round beside the other driver→owner channels; `beam_rt` (`crates/beam_rt/src/port/peer_closed.rs`) gates the message on the driver's **live** `{active,…}` mode and then retires the port through the `driver_exit` route, so an `{active,once}`/`{active,N}` grant a delivery spent is silent and the report is at most one per descriptor.
**Two owner-facing messages are still missing — the real refusal-list gap:** a `send_timeout` expiry's `{inet_reply, Port, {error,timeout}}` (the option is stored, never armed) and `SUBSCRIBE`(24)'s later `{empty_out_q, Port}`; both are *missing messages* rather than wrong values, so a caller waiting on either hangs, and neither has a channel of its own today. The options (`{deliver, port|term}`, `send_timeout`, `send_timeout_close`, codes 25/30/35) are stored and reported byte-exactly, and `Getservby*`/`SUBSCRIBE`'s reply are **served**.
**`DynLib` has no consumer outside this crate.** `beam_rt`'s `erl_ddll` floor is built on `beam_abi::driver::loader`, so the safe `dlopen`/`dlsym`/`dlclose` wrapper stays an unadopted seam; a consolidation would move it **down** into `beam_abi` (its own loaders cannot call this module).
**The `erl_ddll` error taxonomy is duplicated OUTSIDE this crate (report — not fixable here).** A full atom+code+message copy lives in `crates/beam_bifs/src/runtime/ddll.rs` and a partial one in `crates/beam_abi/src/driver/loader.rs`; the recommended single owner is `beam_abi`, but `beam_bifs` does not depend on it, so that adds a DAG edge whose zero-new-edge alternative is the LCA `beam_common` — an **owner decision + a `CHANGE.md` entry**, not this node's.
**The `file:*` API belongs to `beam_rt`'s `prim_file` floor, and no `beam_io` code is on that path.** The `efile` driver offers the driver-level verb set only; `file:*`/`prim_file` is a Rust-`std::fs` floor in `beam_rt/src/native/prim.rs`, so routing `file:open/2`+`read/2`+`write/2` onto it would still owe the `{error,atom}` and `FileDataMode` renderings. Consequence worth knowing before profiling anything named `file_io`: the workload's whole-file (`file:write_file/2`+`file:read_file/1`) and **raw-handle** (`file:open(_,[raw])`+`read`/`write`/`close`) shapes touch **no port, no driver and no poller round** — they are a direct `prim_file` BIF call per operation, so a per-operation cost there is never this crate's. The one `file_io` case that *is* a port is `file:open(Name,[ram,…])`: `ram_file.erl` opens it as `open_port({spawn,"ram_file_drv"},Opts)`, i.e. the `{spawn,Cmd}` name form, whose first-token driver lookup belongs to `beam_rt`'s `open_port` classification (`{spawn_driver,Name}` reaches `create_static_spawn` here; `{spawn,Cmd}` does not). `HANDOFF_FILE_IO_PERF.md` in this node carries the measured attribution and the exact `beam_rt` patch for both.
**Every other handoff is a child node's:** the driver/async-op/accept-family seams (incl. the datagram `{header,N}` impossibility and `INET_REQ_FDOPEN`'s documented non-mirror) are `src/drivers/inet/CONTEXT.md` › *Handoffs*; the io-device request's `{stop,…}` boxing and `Leftover` are `src/io_device/CONTEXT.md` › *Deviations from the oracle*, beside its `reply_get_chars`/`reply_put_chars` residual in *Handoff to `beam_rt`*.

## TCP accept state machine
The state machine is the child node's: the **sticky** multi-accept `INET_F_MULTI_CLIENT` bit behind `GETSTATUS`, the per-port sorted accept-timer list (the C's `desc->mtd`), the `[0]einval` ladder for every non-listening state and the arm/re-arm/disarm readiness cycle live in `src/drivers/inet/CONTEXT.md`, pinned by `src/drivers/inet/accept_tests.rs` (19) + `tests/inet_accept.rs` (7).
The accepted descriptor is handed over **owned** (`InetAsyncResult::Accepted { fd }`), and the listener's option set comes across through `TcpInetDriver::from_accepted(fd, listener)` — this crate's implementation of the C's `tcp_inet_copy` (`erts/emulator/drivers/common/inet_drv.c:11795`); its field-by-field inheritance list is the child node's.
The seam exists: `PortRegistry::driver_as::<TcpInetDriver>(listener)` reaches the listener's concrete driver, and the accepted driver is then opened as a second port — proven end to end through the registry by `src/drivers/inet/inherit_tests.rs`'s registry-route rows. The runtime must open that second port with **that** constructor rather than `from_socket`, and `InetAsyncResult::Accepted { fd }` is either adopted that way **or** closed by the runtime.
