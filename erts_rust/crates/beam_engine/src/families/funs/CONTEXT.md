# `beam_engine::families::funs` — fun / closure instruction family

## Intent
Owns the closure and fun-application opcodes of the typed-IR engine:
`Instr::MakeFun3`, `CallFun`, `CallFun2`, `Apply`, `ApplyLast` (ownership table:
`../mod.rs:146-150`).
Builds local closures and dispatches fun/`M:F` application; `call_fun`/`call_fun2` are the
**closure-apply** seam (`ExecutionContext::resolve_local_fun`) and `apply`/`apply_last` are the
**dynamic-entry** point of the cross-module-call seam.
Ground truth (read-only, never modify): `emu/instrs.tab` (`i_make_fun3` :545,
`i_call_fun`/`i_call_fun_last` :363/:371, `apply`/`apply_last` :298/:306) and
`beam_common.c` (`call_fun` :1604, `fixed_apply` :1528, `apply` :1433, `expand_error_value` :754).

## API Surface (`mod.rs`)
- `pub(crate) fn exec(machine, module, labels, instr, func, pc, ctx) -> Result<Option<Step>>` — `mod.rs:123`; the per-family seam contract (`Ok(Some)` executed / `Ok(None)` not my variant / `Err` raised).
- `mod.rs:275` `register_args` — collect `x(0)..x(arity-1)`.
- `mod.rs:413` `apply_target` — the `fixed_apply` shape (`module=x(arity)`, `function=x(arity+1)`); its host `call_bif` `Err` is routed through `Machine::raise_bif_error` (`mod.rs:464-467`) and returned as `ApplyTarget::Raised`, never a raw error.
- `mod.rs:369` `enum ApplyTarget { Called(Eterm), Enter{context,func,pc}, Raised(Step) }` — `Raised` covers both a non-atom-target `badarg` and a host BIF error from the applied target.
- `mod.rs:488` `raise_badarg` — catchable `badarg` raise for a non-atom `apply` target.
- `mod.rs:528` `atom_name` — resolves a runtime atom **value** through `ExecutionContext::atom_name` (the live-namespace seam, defaulting to the running module's own table); typed `BadArg` for a non-atom or an id the host cannot name.
- `MakeFun3` (`:137`) builds via `terms::make_fun_rooted`; header arity = `descriptor.arity - num_free`.
- `CallFun`/`CallFun2` (`:178`/`:190`) hand a re-readable `FunSource` (`:304`) to the shared `call_fun` (`:480`), which classifies the target's shape and **then** routes through the in-machine closure-apply seam `ExecutionContext::resolve_local_fun` (see below); `ExecutionContext::apply_fun` is the value-returning fallback when the host declines.
- `mod.rs:350` `reason_atom` / `:360` `raise_reason` / `:375` `raise_badfun` / `:407` `raise_badarity` — the structured target-shape reasons (see below).

## The structured target-shape reasons (`{badfun,Fun}` / `{badarity,{Fun,Args}}`)
- `call_fun` classifies the call target **before** the seam, exactly as C's `call_fun` (`beam_common.c:1604-1622`) does, so the oracle's structured `error` reasons are reproduced instead of the bare `badarg`/`badarity` a host seam can only report:
  - the target is not a fun ⇒ `{badfun, Fun}` (`EXC_BADFUN` + `expand_error_value`'s `TUPLE2(am_badfun, fvalue)`, `beam_common.c:754-768`), built by `raise_badfun` (`:375`);
  - the target IS a fun but its **header arity** (`terms::fun_arity` — C's `fun_arity(funp)`, the right field for *both* a `make_fun3` closure and an external `fun M:F/A`) differs from the call's arity ⇒ `{badarity, {Fun, Args}}` (`EXC_BADARITY`), `Args` being the **actual** argument list `x(0..arity)`, built by `raise_badarity` (`:407`).
- **The classification is gated on the running module naming the reason tag** (`call_fun`, `mod.rs:514-524`): `raise_badfun` only when `module.atom_table.lookup("badfun").is_some()`, and `raise_badarity` only when `badarity` is nameable. C's **global** `error_atom` table always names both, so C always raises the structured reason; this engine's atoms are module-local, so a module that cannot name the tag **declines the classification and falls through to the closure-apply seam below** (`register_args` → `resolve_local_fun` → the `apply_fun` fallback, which owns a live namespace), yielding the typed `unsupported_opcode: apply_fun` rather than a substituted atom. Every `beam_rt` process names both (`beam_rt::boot::CORE_ATOMS` seeds `badfun`/`badarity`), so the real runtime always takes the structured-reason path.
- Both reasons ride the machine's structured-reason path (`machine.throw_error`) with class `error` (`raise_reason`, `:360`), so a live `try`/`catch` observes `{error,…}` and an uncaught raise carries the reason term in the raise's live-reason slot.
- Both are ONE rooted reservation: `{badfun,Fun}` = a 2-tuple plus the target's operand slack; `{badarity,{Fun,Args}}` = a 2-tuple + the inner `{Fun,Args}` 2-tuple + `2·arity` list cells + the slack, carved via `Slack::tuple`/`Slack::list` (`raise_badarity`, `:407-431`). The target is re-read from the machine's post-collection state through `FunSource::read_slack` — never held in a Rust local across the reservation.
- The tag atoms (`badfun`/`badarity`) are resolved from the running module's own atom table; ERTS resolves them from its **global** `error_atom` table (neither name is interned by a module's own source — verified with `beam_lib:chunks(F,[atoms])`), and `beam_rt::boot::CORE_ATOMS` seeds both. A module that **does** name the tag raises the structured reason; a module that cannot name it declines the classification and reaches the closure-apply seam (see above) — never a substituted atom.
- Oracle-verified (OTP 29.1.1 / erts-17.1): `f(F) -> F(1).` with `f(5)` ⇒ `{error,{badfun,5}}`, `f(notafun)` ⇒ `{error,{badfun,notafun}}`; `am1(F,A) -> F(A).` with `am1(fun(X,Y) -> X end, one)` ⇒ `{error,{badarity,{#Fun<…>,[one]}}}`; the external `fun lists:reverse/2` called with one argument ⇒ `{error,{badarity,{fun lists:reverse/2,[one]}}}`, while a matching-arity external fun call is *dispatched* (⇒ `function_clause`) — i.e. the header-arity check is exactly what gates it.

## The in-machine closure-apply seam (`CallFun`/`CallFun2` → `resolve_local_fun`)
- `CallFun`/`CallFun2` dispatch through the shared `call_fun` (`mod.rs:480`), which consults `ExecutionContext::resolve_local_fun` **FIRST** (`mod.rs:497`) — after the shape check above, so only a well-formed, matching-arity target reaches the host. On `Ok(Some((callee, label)))` the engine enters the lambda body **in this machine**, exactly as C's `call_fun` dispatches to the fun body's code in the same process:
  - it copies the closure's free variables into `x(arity..arity + num_free)` (C's `reg[i + arity] = funp->env[i]` order — arguments first, captures after) (`mod.rs:503-507`);
  - it registers `callee` as a module context and resolves `label` against that module's **own** label map, so an unknown label is `error::unknown_label`, never a jump into the wrong module (`mod.rs:508-512`);
  - it stores the caller's next instruction `Continuation::Address { func, pc: pc + 1, context: current_context() }` in the live frame and reports `Step::Enter` (`mod.rs:516-525`).
  A `receive` inside the closure then suspends **this** process (an ordinary `RunOutcome::Wait`), and a raise inside it lands in the caller's live `try`/`catch`.
- `Ok(None)` (the seam's default — a host without the seam) keeps the value-returning `ExecutionContext::apply_fun` fallback byte-identical (`mod.rs:529-537`); the fun kinds with no local label (an external `fun M:F/A` and the `-eval` evaluator's closure) take that fallback.
- Every error — the seam's own (`mod.rs:538`) and the fallback's (`mod.rs:536`) — is routed through the catch-aware funnel `Machine::raise_bif_error`, so a routable raise lands in a live `try`/`catch`; a genuine capability gap (`error::unsupported`) stays the uncatchable typed error. The shape check above only replaces the *bare* `badarg`/`badarity` the seam used to produce.
- The seam's `Step::Enter` is folded by the module-context-aware driver exactly like the cross-module-call seam below (switch context + re-bind the literal area); a `Step::Wait` from inside the closure leaves its module context for `resume_outcome`.

## The cross-module call seam (load-bearing — verify here, do not trust summaries)
- `apply`/`apply_last` resolve their target through `ExecutionContext::resolve_external_call` **FIRST** (`mod.rs:441`), which answers with the callee's **shared `Arc<Module>`** + its export entry `Label`. `apply_target` registers that module as a context and returns `ApplyTarget::Enter{context,func,pc}` (`mod.rs:442-447`). Only the seam's `Ok(None)` default falls back to the synchronous `ctx.call_bif` (`mod.rs:464-466`) → `ApplyTarget::Called`; a **host BIF error** there is routed through `Machine::raise_bif_error` and returned as `ApplyTarget::Raised` (`mod.rs:466`).
- `Instr::Apply`'s `Enter` arm stores the **caller's** return address `(func, pc+1, current_context)` in the live frame, then returns `Step::Enter` (`mod.rs:209-224`) — the same discipline as a local `Instr::Call`, so a `receive` inside the callee suspends **this** process and its `return` unwinds into the caller's frame.
- `Instr::ApplyLast`'s `Enter` arm returns `Step::Enter` after the frame is already popped (`mod.rs:243`, `:262-264`), so the callee runs on the caller's frame.
- The seam's `Step::Enter` is folded by the module-context-aware driver (`../../../src/machine/drive.rs:140-158`: switch context + re-bind the literal area); the callee's `Step::Wait` becomes `RunOutcome::Wait` (`drive.rs:159-161`), leaving the suspended frame's module context for `resume_outcome`.
- A `raise` from a cross-module callee lands in the **caller's** catch frame: the landing is reported as `Step::Enter` into the handler's context (see `../exceptions/tests/cross_module.rs:578`, whose `guarded_caller` builds the `proc_lib:init_p_do_apply/3` `try apply/3 catch ... end` shape).
- The `Instr::CallExt*` core arms (NOT this family) use the same seam: each calls `resolve_call_ext_apply` (the `erlang:apply/3` special case, `dispatch.rs:689`) and then `resolve_external_entry` → `resolve_external_call` (`dispatch.rs:361-379` for `CallExt`, `:400-408` for `CallExtOnly`, `:455-464` for `CallExtLast`; `resolve_external_entry` at `dispatch.rs:624-645`); `apply_import_target` (`dispatch.rs:778`) applies the arm's own `ImportFrame` discipline to the resolved target.

## Constraints
- `#![deny(unsafe_code)]` crate-wide; this node has no `unsafe`.
- Errors are `beam_common::{Result, BeamError}` only — never a panic, never a wrong result; a non-atom target is the C's catchable `badarg` raise (`raise_badarg`), or the typed `BeamError::BadArg` when no catch frame / the `badarg` atom is absent.
- A **host BIF error** from an applied target (`apply_target`'s `call_bif` `Err`) is likewise the C's **catchable** raise: it is routed through `Machine::raise_bif_error` into the caller's live `try`/`catch` (`ApplyTarget::Raised`), matching C's `$HANDLE_APPLY_ERROR` → `handle_error` → `next_catch`. Only engine-diagnostic `Err`s from *outside* the host BIF call (a bad register, the resolver / label resolution) keep their `?` and escape as the typed error.
- Term construction/inspection only via `crate::terms` / `beam_term`.

## Known Issues / Notes for Agents
- **No TODO/FIXME/limitation marker in this node** — the cross-module seam is implemented on both the `Apply`/`ApplyLast` path here and the `CallExt*` path (`interpreter/dispatch.rs`), and adopted by the `beam_rt` host (`RuntimeContext::resolve_external_call`).
- The target-shape classification is **engine-side and kind-agnostic**: it uses the header arity field (`terms::fun_arity`), which `beam_term::fun::write_fun_external` populates as `arity & FUN_MAX_FIELD` (`beam_term/src/fun.rs:422`) for an external `fun M:F/A` just as `write_fun_local` does for a `make_fun3` closure, so no per-kind branch is needed. The engine has **no safe external-fun builder** (`crate::terms` builds only `FunKind::Local`), so the external-fun arity shape is pinned by the C source (`fun_arity(funp)`, `beam_common.c:1604-1622`), the header-encoding invariants in `beam_term/src/fun.rs` and an oracle probe rather than by an in-node unit test.
- **A raise/receive from a cross-module callee IS propagated, not folded into `blocked()`.** Each `Instr::CallExt*` arm resolves the seam before the synchronous `call_bif` (`interpreter/dispatch.rs:361-379` for `CallExt`), so a callee suspend or raise reaches the driver. `blocked()` is only the **non-blocking** entries' report for a `receive` with no message (`crate::error::blocked`); a host that pumps (beam_rt) or a caller driving `resume_outcome` gets `RunOutcome::Wait`.
- Non-zero `wait_timeout` has **no host timer** — it suspends like `wait` and resumes only on a message (`../receive.rs:147-163`, `../CONTEXT.md` Known Issues). Not cross-module-specific.
