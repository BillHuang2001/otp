# `beam_bifs::ets` — the `ets:*` BIF bridge (`src/ets.rs` + `src/ets/`)

## Intent
The `ets:*` BIF surface of `beam_bifs`: the `TableRegistry` (handle → live `beam_ets::Table`, name → handle, direction-tagged continuation handles, compiled-spec handles, creation-time `TableProfile`s) plus every registered `ets:*` BIF, built on `beam_ets`'s table semantics.
The crate's `TableRegistry` is the M1 "runtime side" of ETS — the table state itself, the access matrix and the match-spec engine stay in `../beam_ets` (read-only).
Ground truth (read-only): `../../../erts/emulator/beam/erl_db_*.c`, `erl_db_util.c`, `../../../erts/emulator/beam/erl_db_hash.c` and the compiled `ets.erl` wrappers.
`bif.tab` declares 59 `ets:*` keys: **58 are served here**, **1** C-interior one (`internal_request_all/0`) stays a seam-backed typed `unsupported_bif` gap registered in `../runtime/other.rs`.
`fun2ms/1`/`repair_continuation/2` are **not** in `bif.tab` (pure `ets.erl` functions) and stay unregistered.

### The `TableRegistry` public surface
`insert`/`get`/`get_mut`/`contains`/`remove`/`take`/`forget_profile`/`len`/`is_empty`/`insert_name`/`lookup_name`/`remove_name`/`insert_continuation`/`take_continuation`/`continuation`/`continuation_table`/`insert_spec`/`spec_raw`/`contains_spec`, plus the two **runtime-adoption** entry points (see the adoption-contract section): `handles_owned_by(OwnerId) -> Vec<u64>` and the associated `owner_of(ProcessId) -> OwnerId`.

### Resolution, ownership and access gating
- **`resolve_handle` (`src/ets/resolve.rs`) is THE single table-argument resolver**, shared by every table-taking BIF: a handle ref thing, or — for a table created with the `named_table` option — its **name atom**; anything else is `badarg` (the `{Name,Node}` distributed form is **not** a table argument in OTP 29). `ets:new/2` returns the **name atom** for a `named_table` and the handle ref otherwise.
- **The owner is recorded and every table-taking BIF is access-gated.** `ets:new/2` records `ctx.self_pid()` as the owner (`resolve::caller_owner` → `beam_ets::OwnerId`, the pid immediate bridged losslessly), and each BIF evaluates the **calling** process through the same bridge: owner ⇒ read+write; a non-owner ⇒ `public` both, `protected` read only, `private` neither. Every denial is `badarg` and leaves the table in the registry. `ets:info/1,2` is **not** gated.
- **`ets:info/1,2` on an unknown or deleted table returns the bare atom `undefined`** (the oracle's `ets_info_1`); the resolution happens before the `Item` is looked at, so `ets:info(bogus, 42)` is `undefined` while `ets:info(T, 42)` on a live `T` is `badarg`. M1 deviation: the oracle distinguishes a tid from an ordinary `make_ref()` (the former `undefined`, the latter `badarg`), but the M1 handle is an ordinary ref thing, so a bare ref is `undefined` here too.
- **`ets:info/1,2` emits the oracle's full 15-field order** (`id, decentralized_counters, read_concurrency, write_concurrency, compressed, memory, owner, heir, name, size, node, named_table, type, keypos, protection`; `owner` renders the recorded pid term — the atom `undefined` when unset — and `heir` the installed pid, or `none`). `ets:info(T, id)` returns the **tid reference** (`make_ref_thing(heap, info.id.raw())`; `is_reference/1` true, `Info =:= T`), not a bare integer. `TableInfo::entries` is reproduced by hand (it takes `&mut AtomTable` while `BifContext` borrows the atom table immutably).

### The `ets:new/2` option parser and the two fields the model cannot express
- **`parse_options` reproduces the C `ets_new_2` accept/reject matrix** (`erl_db.c`): kinds `set`/`ordered_set`/`bag`/`duplicate_bag`, accesses `public`/`protected`/`private`, `named_table`, `compressed`, and the tuples `{keypos, N>0}`, `{read_concurrency, Bool}`, `{write_concurrency, Bool|auto|{debug_hash_fixed_number_of_locks, N}}` (`N` in `1..=32768`), `{heir, none|Pid}`, `{heir, Pid, Data}`, `{decentralized_counters, Bool}`. Repeated options follow last-wins **except** the bare `set`/`protected` atoms, which are NO-OPS (`erl_db.c:2710`); an `ordered_set` carrying the explicit lock count is `badarg` after the loop.
- **The concurrency options are handed to the model**: `parser → options.set_write_concurrency_mode(WriteConcurrency::{Off,On,Auto,FixedLocks(u32)})` and `options.set_decentralized_counters(Option<bool>)`, so `TableInfo::write_concurrency`/`TableInfo::decentralized_counters` are authoritative — `ets:info/2` reads `TableInfo::decentralized_counters` directly and `TableInfo`'s boolean for the plain `false`/`true` `write_concurrency` forms.
- **`TableProfile`** is the shrunken sidecar for the only two `write_concurrency` renderings the model's boolean cannot express: `Auto` (the atom `auto`) and `FixedLocks(u64)` (the hidden `{debug_hash_fixed_number_of_locks, N}` tuple, `N` **normalized** by `db_hash_create`'s rule — round the request down to a power of two, then clamp up to `NLOCKS_WITH_ITEM_COUNTERS = 64`). It SURVIVES a take/restore round trip (`TableRegistry::take` keeps it); only a permanent removal drops it (`TableRegistry::remove`, or the explicit `TableRegistry::forget_profile` `ets:delete/1` calls).
- **The creation-time heir is set on the OPTIONS.** `parse_options` records `{heir, …}` through `options.set_heir(Some(Heir { owner, data }))` / `set_heir(None)`, so `Table::new` deep-copies it into table-owned storage at build time — there is **no** post-build `set_heir`. `Heir::data` is `None` for the arity-2 `{heir, Pid}` (the C's `THE_NON_VALUE`, inheriting in silence) and `Some(term)` for the arity-3 form. `ets:new/2` sets the name/kinds through the same builder and only records the owner after the build (`table.set_owner(Some(resolve::caller_owner(ctx)))`).

### The verb families
- **`lookup_element/3,4` route a MULTI kind through the list forms.** `src/ets.rs` branches on `Table::kind().is_multi()`: `set`/`ordered_set` keep the scalar `lookup_element`/`lookup_element_or`; `bag`/`duplicate_bag` use `Table::lookup_element_all`/`lookup_element_all_or` and render the result as a **list** (`ets:lookup_element(Bag,1,2)` => `[a,b]`, `duplicate_bag` preserves duplicates). `/4` on an absent key returns the caller's `default` verbatim; `pos == 0`, an absent key on `/3`, and a present object shorter than `pos` are `badarg` — for every kind.
- **The `select` family carries continuations.** `select/1,2,3` (and the `match*`/`match_object*` `/1` forms) decode a continuation from a `Ref` thing (`CONTINUATION_ID_BASE = 1<<40`) into the registry's `continuations` map, run `beam_ets`'s `*_continue` forms, and re-render: `(results, None)` => the bare atom `'$end_of_table'` when `results` is empty, else `{Results, '$end_of_table'}`; `(results, Some(c))` => `{Results, ContinuationTerm}`. `limit == 0` is `badarg`; the spec construct form must be a 1-tuple holding the clause tuple.
- **A `Continuation` records its DIRECTION.** `Continuation { table: u64, state: MatchContinuation, reverse: bool }`; `insert_continuation(table, state, reverse)` mints it, `finish_chunk(..., reverse)` re-stamps a minted follow-up chunk, and `dispatch_continuation` (shared by `ets:select/1` and `ets:select_reverse/1` — the oracle treats them as **one** BIF) resumes a reverse continuation through `Table::select_reverse_continue` and a forward one through `Table::select_continue`. The resume is **read**-gated as the calling process, and `continuation_table(handle)` resolves the table before the traversal runs.
- **A live continuation is an immutable value (repeatable, and it survives unrelated table operations).** `insert_continuation` dedups by equal traversal state for the same table and direction, and `resume_continuation` reads the state through the borrowing `continuation(handle)` accessor — it does **not** consume it — so a continuation can be resumed any number of times with an identical result term and an intervening `ets:select`/`ets:insert`/`ets:info` does not destroy it. The registry's `take`/`insert` no longer touch the continuation map; only `remove(handle)` drops the continuations of the table being permanently removed. `take_continuation` remains on the surface (a consuming accessor) but no BIF path uses it.
- **`select_reverse/1,2,3` (`src/ets/reverse.rs`) is the descending variant — a thin wrapper over `beam_ets`'s NATIVE reverse family** (`Table::select_reverse`/`select_reverse_limit`/`select_reverse_continue`). For an `ordered_set` the results come in **descending key order**; a hash kind (`set`/`bag`/`duplicate_bag`) has no backward walk — its interior's `iter_objects_rev` **is** `iter_objects` and its `last`/`prev` are `first`/`next` (`erl_db_hash.c:853-856`) — so `select_reverse` yields the very same sequence as `select`, element for element. There is no BIF-layer reverse registry and no recompute: `MatchContinuation` carries the direction internally, and the shared registry stores the direction alongside it.
- **`first_lookup/1`/`last_lookup/1`/`next_lookup/2`/`prev_lookup/2` (`src/ets/nav.rs`)** return `{Key, [Objects]}` or the bare atom `'$end_of_table'` (read-gated; a bad/unknown/deleted table is `badarg`). They delegate straight to `Table::first`/`last`/`next`/`prev`: the oracle's hash-kind alias (`last_lookup == first_lookup`, `prev_lookup == next_lookup`) is `beam_ets`'s own hash-interior `last_key`/`prev_key` (`erl_db_hash.c:853-856`), so the BIF layer holds no kind branch. A hash kind with an absent anchor key is `badarg` (matching `Table::next`/`prev`); an `ordered_set` additionally rejects the `'$end_of_table'` anchor (`is_end_of_table_key`, the C `db_next_tree_common`/`db_prev_tree_common` `DB_ERROR_BADKEY`); an empty table is `'$end_of_table'`.
- **`ets:last/1` and `ets:prev/2` carry the same hash-kind alias as the `*_lookup` pair** (`src/ets.rs::last_1`/`prev_2` just call `Table::last`/`Table::prev`): for `set`/`bag`/`duplicate_bag` those answer `first`/`next` (`erl_db_hash.c:853-856`) and only an `ordered_set` reads the true end/predecessor — so the two verb pairs can never disagree. Both keep the `table.kind().is_ordered()`-gated `'$end_of_table'` anchor rejection (`next_2`/`prev_2`).
- **`rename/2` (`src/ets/extra.rs`)** is write-gated and delegates to `beam_ets::Table::rename(name, is_taken)`. A `named_table` rekeys the registry name map and returns the **new name atom** (`RenameOutcome::Named`); a table without `named_table` leaves the registry untouched and returns the **unchanged handle** (`RenameOutcome::Unnamed`). A non-atom name, an unknown/deleted table, and an already-taken name (including the table's own) are `badarg` with nothing changed. `ets:whereis(old)` becomes `undefined` after a named rekey.
- **`internal_delete_all/2`** returns the deleted-object count for a holder of `undefined`, else the holder term verbatim (the C trap protocol), and `internal_select_delete/2` returns the deleted-object count for a raw spec; both are write-gated and `badarg` on a bad table (checked before the holder/spec).
- **`match_spec_run_r/3` (`src/ets/specs.rs`)** runs a **compiled** spec handle over a proper list and PREPENDS each match onto `Acc` (so the output is the reversed match-prefix with `Acc` as the list tail); `[]` returns `Acc` verbatim; a non-list/improper list/raw spec/non-ref spec is `badarg`.
- **`ets:match_delete/2` returns the atom `true`, not a count** (a stdlib `ets.erl` function, not a BIF); `select_delete/2` returns a count and `select_replace/2` the number replaced, with **`bag` => `badarg`** checked before the spec.
- **The raw-vs-compiled spec rule is asymmetric (oracle-verified, must not be "fixed")**: the `select` family accepts **only a raw clause list** (a `match_spec_compile/1` handle is `badarg`), while `match_spec_run/2` and `match_spec_run_r/3` accept **only the compiled handle** (a raw list is `badarg`). `match_spec_compile/1` returns an on-heap `Ref` thing and stores the **raw** spec term; a raising match-spec body surfaces as the atom `EXIT`.
- **The adopted verbs (`src/ets/adopt.rs`):** `ets:all/0` (the registry's tids, sorted by ascending id — see the divergences section), `ets:setopts/2` (`{heir, none|Pid|Pid,Data}` **and** `{protection, public|protected|private}`, owner-only; a dead heir is accepted and clears the heir; an install **deep-copies** the gift through `Table::install_heir` — see the heir-installation section), `ets:give_away/3` (a live, *different* pid, owner-only), and `ets:foldl/3`/`ets:foldr/3` (the stdlib `do_foldl`/`do_foldr` wrappers: a *key* walk from `first`/`next` for `foldl` and from `last`/`prev` for `foldr` — which only an `ordered_set` actually reverses, since a hash interior's `last`/`prev` are its `first`/`next` — plus each landed key's objects folded left-to-right for `foldl` and right-to-left for `foldr`; every direction is decided **while collecting**, so the fun is applied in visit order. The fun goes through the `FunCaller` seam and an **empty table returns `Acc0` without calling the fun**).
- **`ets:setopts/2`'s `{protection, P}` is implemented**: `parse_setopts` accepts exactly the three access atoms, rejects a duplicate `{protection, _}` and any other mode with `badarg`, and applies the new mode through `Table::setopts(Some(owner), SetOpt::Access(Access))` — the owner-gated access setter — so `ets:info(T, protection)` reflects it immediately. The change does **not** re-normalize the creation-time concurrency flags (the oracle's rule: a `public` table created with `{write_concurrency, true}` and switched to `private` still reports `write_concurrency => true`). The whole option list is validated and the owner check passed **before** anything is applied.

### The three remaining `ets` gap keys (each a typed gap, never a wrong result)
- **`ets:internal_request_all/0`** — the helper `ets.erl`'s own `all/0` drives: it mints a fresh `make_ref()` (`erts_make_ref`) and has **each scheduler** reply `{Ref, Tables}`, so `ets.erl`'s `receive_all/3` waits for `system_info(schedulers)` messages. A `BifFn` can neither mint a reference nor send messages, and a single reply would leave that `receive` **blocked forever** — so it stays a typed gap. (`ets:all/0` itself is served directly in `adopt.rs`.) Registered seam-backed in `../runtime/other.rs`.
- **`ets:fun2ms/1`** — **not** a `bif.tab` BIF: a pure `ets.erl` `parse_transform` pseudo-function (`erl_eval:fun_data/1` + `ms_transform:transform_from_shell/3`, i.e. shell-fun introspection over the Erlang AST). The registry can never dispatch it; unregistered.
- **`ets:repair_continuation/2`** — **not** a `bif.tab` BIF either: a pure `ets.erl` function that rewrites the *oracle's tuple-shaped* continuation `{Table, Lastkey, EndCondition, …, MSRef, …}` in place. This layer's continuation is an opaque `Ref` thing, so no `BifFn` could ever be reached for it; unregistered.

### Heir installation — the gift-data copy boundary (both flows adopted here)
`ets:new/2`'s creation-time `{heir, …}` option and `ets:setopts/2`'s install form both store an heir in the table's own storage; the gift term (`{heir, Pid, Data}`'s `Data`) is **deep-copied into table-owned storage** (the A.1 copy boundary, the C `set_heir`'s `DbTerm`) so the table never aliases the installing process's heap — the C `set_heir` (`erl_db.c:5324-5364`) copies the same way.
- **Creation-time** (`resolve.rs::parse_options`): the `{heir, Pid}`/`{heir, Pid, Data}` options are recorded through `TableOptions::set_heir(...)` (so `Table::new`/`build_with` runs the copy via `Table::copy_heir`); **never** a post-build `Table::set_heir(...)`, which does not copy.
- **`ets:setopts/2` install** (`adopt.rs::setopts_2`): an install goes through `beam_ets::Table::install_heir(owner, data)` (which deep-copies), **not** the raw `SetOpt::Heir`/`Table::set_heir` primitives (which store the caller's term verbatim and can dangle once that heap is reused); a clear (`{heir, none}`, or an install onto a **dead** pid) goes through `Table::set_heir(None)`, which reclaims the outgoing gift copy. The owner check (`badarg` for a non-owner) is preserved.
- **The two arity forms differ in `Heir::data`**: `{heir, Pid}` (arity 2) is a **silent** gift (`data == None`, the C's `THE_NON_VALUE`); `{heir, Pid, Data}` (arity 3) carries `Some(copied_data)`. Only the arity-3 form owns storage, and only it produces a transfer message on the owner's death.
- **A gift outside the store's copyable subset** (a fun, an off-heap bin ref, …) is the store's typed `badarg` — the same limit as any `beam_ets::Table` insert.
- **`{'ETS-TRANSFER', Tid, FromPid, Data}` delivery is a `beam_rt` handoff** (do NOT implement here): the runtime sends it on the owner's **death** (the heir stepping in) and on `ets:give_away/3`, and **only** when the arity-3 form supplied `Data`; an arity-2 heir inherits in silence. This crate stores the gift and performs the observable ownership transfer; the delivery is message-passing, and the owner-death adoption contract below already spells out when `Data` is present.

## The owner→handle roster and the process-death adoption contract
The runtime (`../../beam_rt/src/runtime/ets_owner.rs`) owns process death and therefore must reclaim a dead owner's tables, but it cannot see this registry's private table map. The two public entry points close that:
- **`TableRegistry::owner_of(pid: ProcessId) -> OwnerId`** — `OwnerId::new(pid.to_eterm().raw() as u64)`, a **lossless** function of the pid immediate and the *same* encoding `resolve::caller_owner` records at `ets:new/2` time (and `beam_rt`'s own `owner_key` computes). It is an associated function on the re-exported `TableRegistry` because `mod ets` is private: a free `pub fn` in `resolve.rs` would not be reachable from another crate, and `src/lib.rs` is not ours to edit.
- **`TableRegistry::handles_owned_by(owner: OwnerId) -> Vec<u64>`** — every handle whose table's `Table::owner()` is `Some(owner)`, **ascending by handle**. It covers **unnamed** tables too (their handle is not derivable from any public term), which is exactly the reclamation gap a `named_table`-only index could not close. An ownerless table (one inserted straight into the registry) is never reported for any owner.

**The adoption contract.** On a process death, the runtime:
1. lists the dead pid's handles with `handles_owned_by(owner_of(dead_pid))`;
2. per table calls `beam_ets::Table::owner_died(dead_owner, is_alive)` and acts on the returned `beam_ets::OwnerDeath`:
   - **`NotOwner`** → nothing to do;
   - **`Deleted`** (no heir, a self-heir, or a dead heir) → drop the table through the **existing** `TableRegistry::remove(handle)`, plus `remove_name(table_name)` when it was a `named_table` (the handle→name map is the caller's to clean, exactly as `ets:delete/1` does);
   - **`Transferred(heir)`** → the heir is already the table's owner (the transition moved it and left the heir installed). Deliver `{'ETS-TRANSFER', Tid, FromPid, Data}` **only when `heir.data` is `Some(Data)`**; an arity-2 `{heir, Pid}` inherits in **silence** (the C's `THE_NON_VALUE`).
3. `ets:delete/1` already drops the profile and the name registration, so an index handle for a table deleted since is stale: `TableRegistry::get_mut` is `None` and the entry is skipped. No new removal path exists or is needed.

No table is ever dropped by *this* module on an owner's death: the registry exposes the roster, and the deletion is the runtime's decision (it owns the process-liveness oracle `owner_died` needs).

## Guard-scoped views — not needed here (audited)
`beam_ets` also offers an escape-proof `SharedTable`/`TableRead`/`TableWrite`/`TableTerm` view layer, but this bridge deliberately uses the **raw, owned `Table`** primitives.
**The invariant that makes that sound:** every `Eterm` this bridge returns is either (a) freshly constructed on the caller's heap through `BifContext` (a small int, an interned atom, a `make_ref_thing` handle, a tuple/list), or (b) a **copy** produced by `copy_out`/`copy_out_list` (`beam_message::copy_struct_simple` onto `ctx.heap()`). No `Eterm` that lives in `beam_ets` table storage is ever returned, and none is held across a `restore_table`. That is enforced structurally, not by convention: between `take_table`/`take_table_gated` and `restore_table` the `Table` is owned **by value**, so the borrow checker forbids any `&` derived from it from outliving the restore; and the storage itself is a **never-relocating bump arena** of stable block pointers, so a term's source address stays valid for the whole of the copy (`table.tab2list()` → `restore_table` → `copy_out_list` is therefore safe, as is `key_objects`' copy just after a restore).
A full audit of every table-derived `Eterm` return path in `ets.rs`/`nav.rs`/`reverse.rs`/`matches.rs`/`specs.rs`/`extra.rs`/`adopt.rs` found no escaping site, and the bridge does not use the raw `iter_keys*`/`iter_objects*`/`foldl`/`foldr`/`tab2list_into` families at all (it drives `lookup`/`match`/`select*`/`first`/`next`/`last`/`prev`/`tab2list`, each returning owned `Vec`s that are copied out). Adopting a view for style would add a borrow-scoped API surface without changing the safety argument (and would trip the borrow checker where a BIF needs `ctx.atoms()`/`ctx.heap()` while iterating), so the raw primitives stay.

## Known divergences vs the oracle (live `erl` probes, OTP 29.1.1 / erts-17.1)
These are **wrong or environment-bounded values**, not typed gaps — the only kind of ets defect that matters, since a gate-pinned `agree` would otherwise hide a fabricated result. Neither is currently pinned by the differential corpus.
- **`ets:all/0` answers only this crate's registry, in ascending-id order.** The oracle's `all/0` returns the node's **system tables** (`logger`, `ac_tab`, `code_server`, `inet_db`, …) plus the user tables in an **unspecified** order (probe: `A =:= lists:sort(A)` is `false`, and the list starts `[logger,ac_tab,code_server,#Ref<…>,inet_db,…]`). `all_0` (`adopt.rs:173-186`) renders `TableRegistry::all_tids()` (`ets.rs:617`) — registry keys **sorted ascending**, system tables absent. The order is deterministic where the oracle guarantees none; the missing system tables are tables this runtime does not create.
- **`ets:info(T, memory)` MATCHES in unit (words) — do not "fix" it to bytes.** The C counter is bytes (`erl_db_util.h:335`) but `ets_info_1/2` divides by `sizeof(Sint)` (`erl_db.c:4497`, `:4570`), so the oracle reports **words**; `info_field` (`ets.rs:1624`) renders `beam_ets`'s own word count raw. The `unit` agrees (oracle empty `set` = 306 words; a 2-word object adds ~6 words). Only the **numeric value** is a crate-specific allocation model and may differ from the allocator-derived oracle figure — the corpus pins only `is_integer`.
- **Everything else probed MATCHES** (`ets:info/1`'s 15-field order; unknown-table `undefined` vs live-table unknown-item `badarg`; `lookup_element/3,4`; `internal_delete_all/2`; `internal_select_delete/2`; `rename/2`; `give_away/3`; a `setopts/2` heir install and a `setopts/2` protection change; `select/3` chunk shapes incl. `limit 0` ⇒ `badarg` and the bare `'$end_of_table'` on an empty final chunk; `ets:last`/`prev` and `last_lookup`/`prev_lookup` hash-kind aliases; repeatable, non-consuming continuations; `ets:give_away/3`'s **ownership transfer** and its four `badarg` cases — the *gift* is a separate defect, below).

- **`ets:give_away/3` discards its third argument (MEDIUM).** `adopt.rs::give_away_3` reads only `args[0]`/`args[1]`, and `beam_ets::Table::give_away` takes no gift, so `GiftData` is never validated, retained or surfaced. The oracle delivers `{'ETS-TRANSFER', Tid, FromPid, GiftData}` to the new owner with the gift intact (probed: `ets:give_away(T,P,{complex,[1,2,3],self()})` carries that term), and no crate intercepts `give_away` (`beam_rt/src/runtime/ets_owner.rs` only comments on it), so the gift can never reach the recipient. The heir path has the counterpart store (`Table::install_heir` deep-copies into table-owned storage); `give_away` needs an equivalent retained term for the runtime to build the message from.
- **Sibling `../match_spec.rs` map gap — now narrowed to a variable/`'_'` map KEY.** Head patterns containing a map ARE delegated to `beam_ets`'s compiler and agree with the oracle (a map head, a map-valued sub-pattern, a map nested in a tuple head), so `erlang:match_spec_test/3` succeeds there. The one remaining map-related gap is a head map with a **variable or `'_'` key** (`#{'$1' => V}`, `#{'_' => V}`): `beam_ets::select::pattern::decode` refuses the spec with a plain `badarg`, which `test_table` maps to the typed `unsupported_bif`, where the oracle's linter reports `{error,[…]}` — a typed gap, not a value divergence.
- **`ets:info/2`'s `stats` is the one item answered as the typed `unsupported_bif` gap** (`info_field`, `../ets.rs:1746`) — the oracle renders it from `beam_ets`-unexposed interior counters. `fixed` (`../ets.rs:1732`), `safe_fixed`/`safe_fixed_monotonic_time` (unfixed ⇒ `false`, `../ets.rs:1737`) and `binary` (bitstring-free ⇒ `[]`, `../ets.rs:911`) ARE served; their only residue is the documented typed gap on a *fixed* table (`safe_fixed*`) and on a table that really holds a bitstring (`binary`). A real caller now succeeds: `lib/runtime_tools/src/observer_backend.erl:494,530` calls `ets:info(Id, fixed)`.

## The match-spec evaluation seams (installed here)
`beam_ets` evaluates a match spec's `self/0` through a thread-local `SelfHook` (`beam_ets/src/select/expr/guard.rs::set_self_hook`) and its arithmetic through a thread-local `ArithHook`.
This crate serves both, and `./self_hook.rs::SpecEval` is the **one** aggregate guard every match-spec-evaluating BIF opens — so a site cannot install one seam without the other.
`SpecEval::install(ctx.self_pid())` installs the private `PidHook` (the calling `ProcessId` as its own internal-pid immediate, via `ProcessId::to_eterm`) and holds the `./arith_hook.rs::PrecisionArith` guard.
The 12 open sites are `../ets.rs`'s `select_2`/`select_3`/`resume_continuation`, `./matches.rs`'s `select_count_2`/`select_delete_2`/`select_replace_2`, `./reverse.rs`'s `select_reverse_2`/`select_reverse_3`, `./specs.rs`'s `match_spec_run_2`/`match_spec_run_r_3`, `./extra.rs`'s `internal_select_delete_2` and `../match_spec.rs`'s `test_table` — the `/1` continuation resumes reach the guard through the shared `resume_continuation`, so a resumed traversal keeps both seams.
The installed pids are kept on a thread-local **stack**, so a nested evaluation (`ets:foldl/3`'s fun running `ets:select/2` through the `FunCaller` seam, or another spec run nested inside one) answers **its own** pid and its `Drop` restores the **outer** pid — only the outermost drop restores the seam's own default (the typed `badarg`, whose body rendering in `beam_ets` is the `EXIT` sentinel).
The hook never fabricates a value: `self/0` outside a spec run still answers the seam's default, never a stale pid.
`ets:match_spec_compile([])` is `error:badarg` (the oracle raises it), rejected in `./specs.rs::match_spec_compile_1` **only** — `beam_ets::compile` keeps mapping `[]` to an empty spec because the *select* family legitimately accepts it (`ets:select(T,[])` ⇒ `[]`, `ets:select_count/delete/replace(T,[])` ⇒ `0`, `ets:select_reverse(T,[])` ⇒ `[]`).
`erlang:match_spec_test(1,[],table)` answers the linter's `{error,[{error,"Match programs are not in a list."}]}`, not `badarg`.

## Constraints
- Errors are `beam_common::{Result, BeamError}` only — `BadArg` for every argument/semantics failure (the oracle's own reason), `unsupported_bif` only for an uninstalled seam or a genuine capability gap. Never a panic, never a wrong result.
- `#![deny(unsafe_code)]` at the crate root; no `unsafe` here — raw term movement goes through `crate::access` and `beam_message::copy_struct_simple`.
- Table state, the access predicates, the reverse/traversal primitives, the heir/ownership transitions and the match-spec engine are `beam_ets`'s; the metric/`info` field mapping, the handle registry, the option parsing and the direction bookkeeping are this module's. Never re-implement `beam_ets` semantics here.
- All term storage a `beam_ets::Table` hands back lives in a never-relocating bump arena, so a BIF may take the table out of the registry, work on it and restore it — even on the error path.
- Registration order: `crate::ets::register` (which calls the `matches`/`specs`/`extra`/`adopt`/`nav`/`reverse` sub-registers) runs BEFORE `crate::runtime::register`; `src/runtime/other.rs` registers only `ets:internal_request_all/0`, so no key registered here is shadowed.
- The registry hot path stays allocation-free: the roster methods allocate one `Vec` per call and are **not** on any BIF path.

## Handoff to beam_ets
- The `TableProfile` sidecar (2 forms) exists only because `TableInfo::write_concurrency` is a boolean; exposing the resolved `WriteConcurrency` mode (or the normalized lock count) on `TableInfo` would retire it.
- The hash-kind reverse-navigator **alias is owned by `beam_ets`'s interiors** — `Table::last`/`prev` are `first`/`next` (and `iter_objects_rev` is `iter_objects`) for `set`/`bag`/`duplicate_bag`, per `erl_db_hash.c:853-856` — so the BIF layer holds no kind branch: `last_1`/`prev_2`, `nav.rs` and `adopt.rs`'s `collect_objects` all delegate to `Table::last`/`prev` for every kind.
- **No `ArithHook` handoff remains.** `beam_ets`'s thread-local match-spec `ArithHook` seam is served here: `./arith_hook.rs`'s `PrecisionArith` installs an arbitrary-precision hook (delegating to `../arith.rs::match_spec_arith`), opened through `./self_hook.rs`'s `SpecEval` around every match-spec-evaluating BIF, so a bignum operand or an out-of-range integer result yields the oracle's value instead of `DefaultArithHook`'s typed `unsupported_ets`; `oracle_arith_class` maps the operators' `badarith`/`system_limit` to the `badarg` the executor treats as an unmet guard / `EXIT`.
- **No `SelfHook` handoff remains.** The counterpart `self/0` seam is served by the same `SpecEval` install (`./self_hook.rs`), so a spec's `self/0` guard/body answers the calling pid instead of the seam's typed `badarg`.
