# `beam_rt::runner` — measured workload record (slice charge · growth loops · collection cadence · off-heap reclamation)
The current-state measurement record behind [`CONTEXT.md`](CONTEXT.md) *Measured*, which carries the headline ratios and the structural pins.
This file carries every table, per-call counter, estimator and caveat: the per-workload speed ratios, the per-iteration collection/major rates and nursery geometry, the boundary door's rationing, the slice budget's exact charge, the `foreign` mechanism, the off-heap prune's per-fixture envelope and the `emqx_base62:encode/1` end-to-end record.
Nothing here is a change log: a figure is evidence for the current tree, and the cited command or test re-derives it.

## Method discipline
- **A wall-clock figure is only as good as the host.** The bench host is shared and loaded, so a ratio read at a named `/proc/loadavg` band is the durable signal and the absolute wall time is not; re-run the cited command for a live number.
- **Prefer the deterministic counter.** Every `case_*_ops`/`case_*_calls`/`case_*_elements` count and every per-call counter-table row is contention-immune, so a *shape* survives a loaded host even where the absolute walls do not.
- **Never compare two trees measured in different processes on this host.** A ON-vs-OFF comparison is taken out of **one** build, as interleaved `A B A B …` legs, with the OFF side reached by a throwaway `#[cfg(test)]` early return that is removed with the measurement.
- **A per-workload speed and memory figure is measured, never modelled.** The full cross-runtime record is [`../../PERF.md`](../../PERF.md), its dated snapshots [`../../PERF_HISTORY.md`](../../PERF_HISTORY.md), the per-call dispatch/trace cuts [`../../TRACE_AND_PERF.md`](../../TRACE_AND_PERF.md), and the bench driver's own record [`../../../../tools/bench/RESULTS.md`](../../../../tools/bench/RESULTS.md).
- **`rust`** always means this runtime's release `beam_rt` on its default baseline-JIT tier; **`sys`** the system OTP 29.1.1 / erts-17.1 oracle.
- **A figure this file does not measure is not claimed.** The one figure the counters here cannot reach — the boundary door's ON-vs-OFF `Δ` — is named as unclaimed (see *What is not claimed: the door's ON-vs-OFF `Δ`*) instead of being carried forward as a number.

## Growth-shaped loops: the per-call work is FLAT in N (deterministic counters, never wall clock)
`the_churn_workloads_per_call_counters_are_flat_in_n` and `the_heap_growth_workloads_per_call_counters_are_flat_in_n` each drive their fixture at three (resp. five) increasing iteration counts and print a `counter_table`: N vs slices / yields / waits / collections / major / fallbacks / peak young-nursery geometry / debt boundaries, plus the derived per-call ratios — every geometry figure quoted here is re-derived by that line, so read it rather than this prose for the mature-space numbers.
The same `churn` shape is pinned at *three* counts by [`tests/boundary_cost.rs`](tests/boundary_cost.rs).

### `churn`, native (default) tier
- collections/call **0.6387 / 0.6401 / 0.6420**, `major`/call **0.0085 / 0.0087 / 0.0093**, `reductions`/call **780.57 / 780.76 / 780.88**, boundary checks/call **0.1949 / 0.1950 / 0.1952** at N = 2 000 / 4 000 / 10 000 (the row set [`tests/boundary_cost.rs`](tests/boundary_cost.rs) pins; `tests.rs` drives the same shape at its own counts and prints the same per-call figures).
- The per-call collection rate is **flat**: 1 278 / 2 561 / 6 421 collections and 17 / 35 / 93 majors over the 2 001 / 4 001 / 10 001 calls, so both totals are linear in N at a fixed per-call rate — the shape's live set is constant and so is the capacity the nursery rule installs from it. The residual ~0.5 % drift (0.6387 -> 0.6420) is the collection cycle's phase against the slice length, which is why the suite pins a rate *rail* rather than a constant.
- Neither total is a closed form: the door pins a young-only `CollectionKind::Minor` collection and escalates to an unpinned `collect` only when the promotion cannot fit the mature space, and the native tier charges its blocks per block (which sets the slice and pre-emption counts these rates are expressed against).
- The young nursery holds **3 000** words of capacity in **one** space at every N (peak, boundary-sampled), 2 611 of them used, and the mature generation holds **10 958** words of capacity with **10 932** used, at every N.
### `heap_growth`, native (default) tier
- collections/call **0.500100 / 0.500050 / 0.500020 / 0.500010 / 0.500005**, slices/call **0.000800 / 0.000800 / 0.000760 / 0.000760 / 0.000760** at N = 5 000 / 10 000 / 25 000 / 50 000 / 100 000.
- The 401-word request fits the settled nursery twice and not three times, so the admission door collects once per two iterations (plus the one the run takes before its first iteration) — the derived relation the assertion pins: `collections == 1 + N / K` with `K == 2`, exact on all five rows (**2 501 / 5 001 / 12 501 / 25 001 / 50 001** collections against **3 / 7 / 18 / 37 / 75** yields).
- `major` is **0** on the rows that stay on the 843-word capacity and **1** on those that take a fullsweep: each of those collections is a minor whose promotion (the live set at that admission point is empty or one iteration) fits the mature region, and only the one the mature region cannot absorb escalates.
- Its young nursery settles at **843** words (`2 x 401 = 802` of them, which is what makes `K == 2`) until a row's one fullsweep re-sizes the mature region to **2 586** words (holding the single 401-word iteration that did not fit); every row after that settles at **987** words (`987 / 401 == 2` as well). The rows below N = 10 000 stay on 843 with the spawn policy's initial **233** words of mature capacity (`emulator_default_policy().initial_mature_words`) and **0** of them used.

### Both shapes
`peak_young_spaces == 1` at every N, so the retired-nursery chain the `collection_debt` trigger protects stays collapsed rather than N-dependent; `yields == slices − 1` with `waits == 0` and `debt_bounds == 0` throughout (neither loop ever parks, and neither leaves an un-settled collection debt at a boundary).
Neither loop's cadence is this node's to set: the door decides *whether* a collection may run (and the counters above show it declining nothing), the collector's post-collection nursery sizing decides *how often* — [`../context/IMPLEMENTATION.md`](../context/IMPLEMENTATION.md) *What the doors do NOT decide*.

## The reduction/yield-boundary door's rationing on the hot shapes
`collect_at_reds_boundary` (`../context/gc/reds_door.rs`, reached from the `Yield` arm only) fires on a **publishing** slice-end park when `REDS_BOUNDARY_MIN_REDS` reductions have elapsed since that process's last boundary check **and** the young heap is **seven eighths** used (or the collector's `collection_debt` is set).
The watermark is seven eighths because the C's own rule (`ERTS_VBUMP_ALLOC_REDS`) fires when the allocation area is **exhausted**, not when it is half used, while `7/8` still leaves the growth seam room between two checks.

### The estimator and the regime
- Every counter here is a **deterministic count** (the runner's own tallies plus the collector's geometry), so a repeated leg reads byte-identically; the shape's own call count `N + 1` is the denominator of each per-call figure.
- `door checks/call` counts the publishing `Yield` parks handed to the door; `door colls/call` those that became a collection; `door.unpublished` is **0** on every shape (no hot shape ends a slice with a live float-register prefix); `fallbacks/call` is 0.
- The default-tier sweep is the native baseline JIT, where a shape that reaches no **refusing** seam never pre-empts (so most rows show ≤1 slice for the whole run — the residual under `CONTEXT.md` *Known Issues / Handoffs*); the interpreter sweep (`BEAM_RT_TIER=interpreter`) is where a compute-bound shape really pre-empts every ~4 000-reduction budget, which is the only regime in which the door is reached often.

### `gc_bound` churn at the seven-eighths watermark (default tier)
At N = 2 000 / 4 000 / 10 000 the shape's retired chain stays collapsed (one young space at a **3 000**-word capacity peak, 2 611 words of it used) while the door fires **48 / 95 / 238** times out of the **390 / 780 / 1 952** boundary checks handed to it — one in 8.13 / 8.21 / 8.20, i.e. 0.0240 / 0.0237 / 0.0238 firings per call and **3.76 / 3.71 / 3.71 %** of the run's own 1 278 / 2 561 / 6 421 collections.
The ration *is* the nursery's geometry: a boundary collection leaves the checks after it below the seven-eighths watermark, which is why the upper edge `door.collections * 8 <= door.checks` is the structural half of the band the assertion pins — the settled 3 000-word space must refill to `7/8 x 3 000 = 2 625` words before the next firing, and the 2 611 words a boundary sample reads are just under that. The lower edge is only a non-no-op floor (`door.checks <= door.collections * 12`, the observed refill length plus a margin): the ratio holds at one in 8.13–8.20 across the three rows rather than drifting, because a fixed per-call allocation refills a fixed capacity, and a thinner ration is strictly cheaper anyway, since a door firing only duplicates a collection the iteration was going to take.
### What is not claimed: the door's ON-vs-OFF `Δ`
Establishing that the door's collections *substitute for* the heap-admission door's rather than adding to them needs a door-disabled build — a throwaway `#[cfg(test)]` early return inside `../context/gc/reds_door.rs` — so **no `Δ` is claimed in this file**.
What the counters do pin is the rationing itself (one firing in 8.13–8.20 boundaries, 3.71–3.76 % of the run's own collections), a collapsed retired-space chain (one young space of 3 000 words at every N) and the exact per-row totals of [`tests/boundary_cost.rs`](tests/boundary_cost.rs)'s `MEASURED` table, which are off any closed form for three structural reasons: the door pins a young-only `Process::collect_kind(CollectionKind::Minor)` first and escalates to the unpinned `Process::collect` only when the promotion cannot fit the mature space (so a boundary firing does not force a fullsweep of its own), the native baseline tier charges its blocks per block (which sets the slice and pre-emption counts the per-call rates are expressed against), and the BIF-result copy-out's learned hint grows the nursery **before** each copy (`RuntimeContext::copy_out_hint` + `hint_grow_gate`, `../context/calls.rs`) — whose one-off room request the next minor collapse then carries (`Nursery::pending_growth_need` → `minor_collapse_target`).

### Shapes the watermark cannot move
- `reds_boundary` (interpreter tier) reports one collection per pre-emption (`yields == collections`) with `major` 1 / 3 / 22 at N = 2 000 / 20 000 / 200 000 (8 / 84 / 849 collections) and a flat `heap_size` of **4 185** words at all three — the **carried** minor target, not the plain live-set one: the copy-out's forced growth records the room it asked for (`Nursery::pending_growth_need`) and the next minor collapse spends that request one-shot through `minor_collapse_target`, clamped above by the carriage bound `max(MINOR_SHRINK_FLOOR_WORDS, YOUNG_SHRINK_FACTOR x young_minor_target_words(1 201)) = max(3 000, 8 x 1 598 = 12 784)`, which does not clip it. The boundary window's live figure is the whole in-flight iteration (400 cons cells from `lists:seq/2` plus the 401-word tuple `list_to_tuple/1` builds from them, 1 201 words), so the plain live-set rules would give `young_after_fullsweep` = `young_target_words(1 201) = next_words(2 466) = 2 586` and a minor floor of `young_minor_target_words(1 201) = next_words(1 265) = 1 598`; the settled 4 185 is a fixed point of `young_after_collection` at that live set and above both, and it is a function of the iteration's footprint and never of the loop count. The mature region sized from the same live figure (`mature_target_words(1 201, 4 185) = next_words(2 x (1 201 + 4 185 + 64)) = next_words(10 900) = 10 958`) is flat at every row too, which is what makes the live figure a derivation rather than a guess.
- The no-heap-admission shape is **debt-driven**: every check reports `collection_debt`, so the occupancy arm never decides it and one collection per pre-emption follows from the loop's per-iteration reduction price over the `REDS_BOUNDARY_MIN_REDS` interval — the measured **17.004 / 16.9978 / 16.9972** reds per iteration (`tests/reds_door.rs`, read from the run's own `reductions` counter), i.e. ~235 iterations per 4 000-reduction slice.- The remaining shapes of the whole-shape sweep have `door checks/call` of 0 or ≤1 per run, so no gate ever decides them and the door contributes no collection there: `send_recv`/`send_recv_plain` on both tiers (the ping-pong parks through the **`Wait`** arm, never `Yield`, so no boundary is ever offered) and, on the default tier, `etf_roundtrip`, `list_walk` and `slice:fib/1` (each completes inside one slice or never pre-empts at all).
- **Below measurement resolution**: `heap_growth` on the default tier runs **4 / 8 / 19 / 38 / 76** slices, only **3 / 7 / 18 / 37 / 75** of them ending at a `Yield` arm, over **2 501 / 5 001 / 12 501 / 25 001 / 50 001** collections, so the boundaries the door is offered there are at most 75 against 50 001 collections.

### Nursery resizing is a real effect of one collection
A minor collapse installs `Nursery::minor_collapse_target` = `HeapPolicy::young_after_collection_with_need(capacity, live, need)`, where `capacity` is the chain sum the collapse is collapsing, `need` is the one-off room a growth could not wait for, and the result is capped by the **carriage bound** `max(MINOR_SHRINK_FLOOR_WORDS, YOUNG_SHRINK_FACTOR x young_minor_target_words(live))` computed from the **plain** live-set target so it does not move with the request.
`need` is the room the BIF-result copy-out asked for before a copy (`RuntimeContext::copy_out_hint` + `hint_grow_gate`, `../context/calls.rs`): `Nursery::grow_for_one_off` records it on `Nursery::pending_growth_need` when it really retired a space, and the next **minor** collapse spends it one-shot; a **fullsweep** collapse consumes it without folding it in (`collapse_after_fullsweep`), and the growth seam's own upper bound stays the plain live-set target.
So a shape that copies a result out settles on the carried figure, one that does not on the plain rule, and nothing is a quantity the counters deduct from — `beam_alloc::Heap::capacity` returns the capacity a space was constructed with verbatim and `HeapSpace::capacity_words` only forwards it.
- `churn` settles at **3 000** words in one space at every N: its live figure is **95 / 94 / 94** words (`live_words`, the mean copy volume per collection — 120 246 / 1 277, 239 692 / 2 558, 600 974 / 6 420), `young_minor_target_words(95) = next_words(159) = 233`, so the carriage bound is `max(3 000, 8 x 233 = 1 864) = 3 000`; the request drives the need-augmented target past that bound and the bound clips the installed capacity to `MINOR_SHRINK_FLOOR_WORDS` itself, which is why the plateau is **not** a growth-table entry (the table runs `12, 38, 51, 90, 142, 233, 376, 610, 987, 1 598, 2 586, 4 185, 6 772, …`).
- `reds_boundary` settles at **4 185** words, the same request **unclipped**: at its 1 201-word live figure the bound is `max(3 000, 8 x young_minor_target_words(1 201) = 8 x 1 598 = 12 784)`, so the need-augmented target is installed as it stands — a growth-table entry, and a fixed point of both sizing rules at that live set (it lies inside the fullsweep keep band `[young_target_words(1 201) = 2 586, 8 x 2 586 = 20 688]` and inside the minor band `[1 598, 12 784]`, so `young_after_collection` and `young_after_fullsweep` each return it unchanged).
- `heap_growth`'s young nursery peaks at **843** words on the rows that never take a fullsweep and **987** after one, each carrying the iterations its own capacity derives: `843 / 401` and `987 / 401` both floor to 2 (`heap_growth_iterations_per_nursery`, `tests.rs`), which is the `K == 2` of the cadence above; 987 is also `young_target_words(401) = next_words(2 x 401 + 64)`, the fullsweep target at the one-iteration live set.
- The **233**-word nursery floor survives as exactly two facts: an **un-collected** fresh spawn (and `slice_charging`'s N = 0 row, `value=233`), and the **initial mature** capacity `initial_mature_words`.

### Residual: what is still missing is a young-only collection that GROWS the mature space
The door's action is a young-only `Process::collect_kind(CollectionKind::Minor)` (`../context/gc/reds_door.rs:317`) and it escalates to the unpinned `Process::collect` only when that minor refuses because the promotion cannot fit the mature space, so a cadence fullsweep comes only from a mature generation too small to take the promotion.
What is still missing is a young-only collection that **grows** the mature space instead of refusing: `beam_gc::AnyCollector::collect_minor` reports typed heap exhaustion when the mature space cannot absorb the whole nursery, so every refusal on these shapes escalates.
The handoff is `beam_gc::AnyCollector::collect_young(&mut self, roots: &mut [Eterm]) -> Result<Collection>` (never escalates; grows/reclaims the mature space instead of a fullsweep; reports `CollectionKind::Minor`), recorded in `../../M1_GAPS_GC.md` *GC / heap model*.
The pinned, current fact is `churn`'s **3.76 / 3.71 / 3.71 %** share of the run's own 1 278 / 2 561 / 6 421 collections at one collapsed **3 000**-word space.

## The slice budget's charge on the native tier (slice/pass cost)
A natively executed compiled block is charged at a deopt, a heap-admission point and each **priced** BIF/call seam; only a *refusing* seam can end its slice, because the per-instruction charge belongs to the interpreter's loop and what a native block's budget drains is `budget`'s `spend` (`call_bif`/`call_bif_in_machine` after the dispatch, `resolve_external_call`/`resolve_local_call` before the forward) plus the two `ensure_heap` doors and any deopt.
- The non-allocating BIF-and-call fixture prices exactly `reductions == 4N + 9` (4 units per iteration + a constant 9 for the entry/epilogue seams, at N = 0/10/100/400/700/997 — the N = 0 row is that constant alone) and above the budget it saturates at exactly **4 006** (`budget` 4 000 + the epilogue's measured 6). The per-iteration 4 is the seams the body reaches — the two `call_ext` resolutions and the two BIF dispatches they resolve to; its same-module local `call_last` charges **nothing** after the run's first consultation of that callee (the engine's memoized local-call verdict).
- The allocating `heap_growth` shape prices **3 units per iteration** (`reductions == 3N + 5` on every single-slice row) and pre-empts into `slices` **2 / 3 / 4 / 16 / 61**, `yields` **1 / 2 / 3 / 15 / 60** and `collections` **1 001 / 1 501 / 2 501 / 10 001 / 40 001** at N = 2 000 / 3 000 / 5 000 / 20 000 / 80 000 — a slice holds at most `4 000 / 3 = 1 333` iterations, with `collections == 1 + N/K` and `K == 2` iterations carried by its settled nursery (one admission collection per two iterations plus the one before the first).
  Across slices `reductions` reads **6 005 / 9 008 / 15 008 / 60 020 / 240 065**: `3N + 5` plus one unit per pre-emption (measured surplus 0 / 3 / 3 / 15 / 60, the ±1 being what `spend`'s no-op can add or remove at a boundary).
  Both capacities a row can settle on carry `K = 2` — 843 words while every boundary's promotion is empty, 987 after the row's one fullsweep — and the rows split exactly that way (`peak_young_capacity` 843 on the first three, 987 on the last two, which is also `young_target_words(401) = next_words(866)`).
  That 1 333 is **not** a multiple of `K`, so a slice end lands mid-cycle on roughly half the rows and the boundary door's firings cannot be dismissed as cycle-boundary coincidences: the count is preserved by the door's occupancy watermark instead — it may only fire once seven eighths of the settled capacity is used (`7/8 x 843 = 737.6` words, cleared by the 802 words two iterations fill and not by 401), so a firing lands exactly where the next admission would have collected and takes that collection rather than adding one.
- The interpreter-tier control on the same fixture reads 9 slices / 8 yields / 8 collections / 1 major / `reductions` 34 020 / `heap_size` **188 686** at N = 2 000 and 85 / 84 / 84 / 3 / 339 968 / **304 635** at N = 20 000 — sublinear in the work (a 10x step moves it **1.61x**) and far below the **1 341 315** words the native tier's *uncollected* 997-row reports; the N = 798 row is 4 / 3 / 3 / 1 / 13 588 / 117 344.
- **Residual**: a non-allocating BIF-and-call-only loop still ends no slice of its own on the native tier — `spend` never refuses and is a silent no-op once the budget is gone, so the *single* `Yield` those rows read is the run's **epilogue** seam (a same-shape fixture with no epilogue ends **zero** slices: `slices=1 yields=0 reductions=4 000` at N = 8 000) and the boundary collection door stays unreachable for the loop; the one `Yield` it does take collects, so `heap_size` sits at the capacity that boundary collection installs (**3 000** words — the carriage bound, every saturated row reading `peak_young_capacity=3000 value=3000`) rather than tracking N, and **233** survives only on the N = 0 row, which reports the space a fresh, un-collected process starts with.
- A **refusing** charge cannot be taken at a call seam today: the native tier publishes `machine.current_code` at **block** granularity (`crates/beam_engine/src/jit/baseline/runtime.rs:993`) and its call paths consult the seam before storing any position of their own (`jit/baseline/call.rs:210` vs `:232`; `runtime.rs:948`; `runtime.rs:818`), so a refusal parks at block entry and the resume re-executes the block prefix — measured with a draft `charge()?`: `-eval 'halt(0).'` and `run slice.beam` both exited 3 with `unsupported: opcode: run: process blocked (no message available)`.
- **Handoff (out of this crate)**: `beam_engine` must store the instruction address (`machine.set_current_code(func, pc)`) before consulting the seam at those three sites, after which a call seam may refuse and the third pin of [`tests/slice_charging.rs`](tests/slice_charging.rs) is the assertion that must change.

| `emqx_base62_encode` | 10 512 ns | 206.3 ns | 51.0× |
| `emqx_base62_decode` | 10 111 ns | 282.5 ns | 35.8× |

The per-call cost of a build-a-binary loop is **not** this table's figure — there is no per-slice off-heap mirror — so the controlled A/B is [`../../PERF_HISTORY.md`](../../PERF_HISTORY.md) *The per-call cost is independent of the iteration count* (`BEFORE` `3aa42c0e41` → `AFTER` `72d778dcf1`: `emqx_base62_encode` **138 544.3 → 5 667.6 ns/call** at `loadavg` 18–89, `decode` 20 698.3 → 10 028.7).

The mechanism is the **literal-area tagging**: `Nursery::grow` retires the old space into `retired` and only `Nursery::collapse` — reached at a collection — clears it, so a runtime that never collects keeps every retired space's capacity resident (RSS grows per call) and pays the valve's per-word scanned test (`root_is_unscanned` → `outside_scanned`) over a longer chain on every admission — that test is `O(1)` for an address outside the aggregate `scanned_bounds` and `O(log #spaces)` otherwise (`Nursery::contains` reads its ordered `retired_regions` index, `beam_gc/src/nursery.rs:194-213`; it never walks `spaces()`).
`beam_loader`'s `tag_literal_area` (`crates/beam_loader/src/literal.rs`, the safe form of the C load-time `erts_set_literal_tag`) tags the decoded literal area, so the walk recognizes these modules' constant literal-area binary as an off-heap literal — not a container in a region the collector does not scan at all (`context/gc.rs::word_region` answers `None` for a literal, which no relocation touches) — so the valve never declines, the descent latch stays closed, and the retired chain stays collapsed instead of growing with the iteration count.
A constant payload a module *builds* would instead be a foreign container that forwards nothing scanned: also inert, so also collected.

## The off-heap reclamation end to end — `emqx_base62:encode/1` on the unmodified EMQX module
All legs run the **identical** `.beam` — the unmodified `emqx_base62.erl` plus a driver loop — release builds, this runtime's default execution tier, **21 interleaved rounds** each.
`PRE-FIX` is `dc63fd7f49`, the commit immediately before the reclamation change; the oracle is the system ERTS (`erl` on `PATH`, OTP 29.1.1 / erts-17.1) at its own loop count.
The estimator is the **startup-cancelled paired marginal**, `median(wall@N − wall@0)/N`, each round sampling the `N`-op and the `0`-op pass **back to back**; rust loops are `N` = **60 000**, the oracle's `N` = **3 000 000**.
The host is **shared and loaded** (`/proc/loadavg` 7–19 across the session), so the ratios here and the memory figures are the durable signal and the absolute wall times are not.
These are **measured** figures rather than ones a test asserts: the mechanism's in-repo pin is the per-fixture suite named at the end of this section.

| leg | ns/call | `erlang:memory(binary)` @N=1 000 | @N=10 000 | `VmHWM` @N=10 000 | `VmHWM` @N=600 000 |
|---|---:|---:|---:|---:|---:|
| `PRE-FIX` (`dc63fd7f49`) | 6 901.8 | 1 072 000 B | 10 720 000 B | 132.1 MB | 878.7 MB |
| `POST-FIX` (current tree) | 6 110.6 | 272 288 B | 315 168 B | 119.9 MB | 119.8 MB |
| system-ERTS oracle | 223.4 | ~22 000 B | ~21 000–32 000 B | 69.9–70.9 MB | — |

**The current effect, stated as such.** `erlang:memory(binary)` is flat in N and the process's `VmHWM` is flat in N: the 9 000 extra calls of the N = 1 000 → 10 000 step add **42 880 B** — a one-off heap growth, not a per-call trend — and `VmHWM` is 119.9 MB at N = 10 000 against 119.8 MB at N = 600 000, a 60× step.
**What the reclamation removed is exactly 1 072 B per call** — a 1 024-byte payload plus its 48-byte off-heap header — and that leak was perfectly linear (`1 072 000` → `10 720 000` over the 10× step), so a process doing 10 M encodes held ~10 GB and its `VmHWM` went 132.1 → 878.7 MB between N = 10 000 and N = 600 000.
**Throughput:** `POST/PRE` = **0.885** and the independent 9-round pass' **0.958** agree in direction, but the size is load-dominated, so only a **4–12 %** speed-up is claimed; `POST/oracle` is **27.4×** against `PRE/oracle`'s **30.9×**.
**This is a memory fix, not a throughput fix**: the leaked payloads were unreferenced and never traversed, so the leak cost no measurable time and there is **no throughput cliff at 878 MB**.
The per-fixture envelope — the N-step figures, the sawtooth ladder, the disabled-site A/B and the retained-payload half of [`../../tests/off_heap_reclaim.rs`](../../tests/off_heap_reclaim.rs) — lives in [`../../CONTEXT.md`](../../CONTEXT.md) *Known Issues / Intentional M1 gaps*'s off-heap bullet, which owns those figures.

## The off-heap prune's per-fixture envelope
The release is **park-gated**: the `Yield` (pre-emption) arm is the one site that prunes, while the `Wait` arm and a `BifOutcome::Suspend` park run none, so the window a build-a-binary loop's dead payloads can accumulate in is **one slice's length** — and the bin-vheap budget only *gates* a prune (`OffHeapReclaimer::triggered` is consulted, never asked), so it never bounds that accumulation. Measured on [`../../tests/off_heap_reclaim.rs`](../../tests/off_heap_reclaim.rs)'s direct-recursion shape: **4 144** bytes at N = 1 000 and **4 144** at N = 10 000 with 4 096-byte payloads, **65 584 / 65 584** at 65 536 B — one surviving payload, no growth in N.
**On the `-eval` route a fun-loop body is covered by the OTHER prune, not this one.** `lists:foldl/3`/`lists:foreach/2` is entered as a *nested* external call, and each application of the lambda is served by `RuntimeContext::apply_fun` → `run_label_blocking`'s own short-lived `Machine` (`../context/pump.rs`); when that machine drops, its reservoir is handed to the runtime's **escaped-payload store** (`Runtime::eval_off_heap`), never to the process's `Machine::refc_binaries` — so the park arm cannot bound it, and the nested-run epilogue does: `RuntimeContext::adopt_nested_payloads` publishes the finished machine's own root set and prunes that store against it (`Runtime::prune_off_heap`, `O(1)`-gated), releasing only the handles the run itself adopted.
On the **`run`** route the same call is entered **in-machine**, so the lambda's applications run inside the process's own engine and their payloads land in `Machine::refc_binaries` — where this park arm does bound them.
Measured: **377 104** bytes at both N = 1 000 and N = 10 000 (4 096-byte payloads, ~91 surviving of the run's own out-of-scope entries) and **393 504** at both with 65 536-byte payloads, against a linear **4 144 000** → **41 440 000** before that epilogue pruned, with the process's own reservoir at **0** handles throughout and its `erlang:statistics(reductions)` delta **0** (it neither pre-empts nor parks).
What is measured, and where the figures live: `erlang:memory(binary)` (`binary_alloc`'s live bytes) and the process's RSS across a build-a-binary loop, against the oracle's — the measured envelope and its caveats are [`../../CONTEXT.md`](../../CONTEXT.md) *Known Issues / Intentional M1 gaps*'s off-heap bullet, whose suite is [`../../tests/off_heap_reclaim.rs`](../../tests/off_heap_reclaim.rs) (the bench driver's [`../../../../tools/bench/RESULTS.md`](../../../../tools/bench/RESULTS.md) carries the loop workloads' RSS).

## Not like-for-like: a matched-N `ns_per_call` against a runtime that never collects
On an allocation-shaped loop, a runtime that never collects runs **zero** collections — the admission declines and the nursery grows instead — whereas this one collects **1 278** times and majors **17** over the same 2 001-call `churn` run (**0.6387** collections and **0.0085** majors per call; the rate is unchanged at N = 10 000: 6 421 / 93 over 10 001 calls = **0.6420** / **0.0093**), so the difference is the memory management this runtime performs and the unbounded heap the other retains, not dispatch or tier.
The 1.25×–1.60× band the allocation-shaped `foreign` rows once read here at matched N is a **dated** figure from before the per-slice off-heap mirror was removed (that removal's A/B reads `emqx_base62_decode` 20 698.3 → 10 028.7 ns/call — [`../../PERF.md`](../../PERF.md)), not a current ratio.
