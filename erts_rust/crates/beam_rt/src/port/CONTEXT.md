# `beam_rt::port` — the runtime's A.4 port layer (`port.rs` provider · `driver.rs` host · `ops.rs`/`exit.rs`/`info_extras.rs` side tables)
## Intent
The runtime side of contract A.4: `port.rs` — the **port provider** (`open_port/2`'s `Name`/`Options` decoding, the poller/registry `PortRegistry`, the port-task round and the `{Port,{data,..}}` pump behind `beam_io`) — plus its child modules: `ops.rs` (the operations treating a port as a **table entry** — `port_set_data/2`/`port_get_data/1`, the registered name, `port_connect/2`'s owner transfer — over one `PortExtras` side table), `exit.rs` (the `'EXIT'`/`'DOWN'` messages a closing port owes its links and monitors), `info_extras.rs` (the **derived** `port_info/2` items, each carrying the C's own derivation) and `completion.rs` (the **driver→owner completion channel** — `beam_io`'s term-free `PortCompletion`s turned into the `{inet_reply, …}`/`{inet_async, …}` messages a socket port's owner is owed, the channel that makes `prim_inet:send/4` return).
`driver.rs` is the runtime's **own** driver C-ABI host for `{spawn_driver, Name}` ports over `beam_abi`'s frozen `DriverHost` seam; `watch.rs` is the **delivery half** of `os:set_signal/2` and `tty.rs` the same half of `prim_tty:tty_select/2`'s `enif_select` interest.
It is **separate** from `beam_io`'s own host layer (`beam_io::abi`), so end-to-end `.so`-driver traffic goes through this tree.
## API Surface
### `port.rs` — the `PortHook` provider (A.4)
Public: `PORT_INFO_ATOMS`, `PortName{Spawn,SpawnExecutable,Fd,SpawnDriver,SpawnDriverBuiltin}`, `StreamType{List,Binary}` (list default), `IoCounters` (behind `erlang:statistics(io)`), `PortEvent`, and `RuntimePorts` (the `beam_bifs::PortHook` impl: `open_port/2`, `port_close/1`, `port_info/1,2`) over `Rc<RefCell<PortRegistry>>` + the shared `Rc<AtomTable>` + the owning `ProcessId`.
`PortEvent::{Data,Line,Exited,Term,Completion,Signal,Select}`; `PortEvent::port()` is the **one** port-bearing roster (`Data`/`Line`/`Exited`/`Term` → `Some`; `Completion` → `None` because its recipient is already resolved, `port.rs:775-843`; `Signal`/`Select` → `None`), read by `drain_pending_events` and the suites' drain helpers.
`PortRegistry` (private fields) exposes `new()` (anchors the `driver_*` codegen unit, builds the **one** `beam_io::DriverRegistry::with_static_spawn_drivers` table — the emulator's own `tcp_inet`/`udp_inet`/`ram_file_drv`), the queries/commands (`is_live`, `write_command`, `is_busy`/`soft_busy`, `port_control`, `has_driver_control`, `is_empty`/`has_nothing_to_poll`/`awaits_port_reply`, `has_pending_driver_atoms`, `io_counters`, `ids`, `close`, `create_static_spawn_driver`, `refresh_liveness`, `arm_tty_select`) and the private pass (`register`, `pump(timeout) -> Vec<PortEvent>`, the `take_*` harvests, the line-channel helpers, `info`, `fold_notifications`, `drain_pending_events`, `report_pending_closes`, `drain_io_completions`, `closed_snapshot`).
`ProcessLiveness` (crate-internal) is the runtime's most recent **process-liveness observation** — the state behind `driver_monitor_process`'s positive `ERL_DRV_MONITOR_NOT_ALIVE` — `is_alive(pid) -> Option<bool>` being `try_borrow`-based because it runs *from* a driver callback that may hold unrelated runtime state borrowed.
`refresh_liveness(&ProcessTable)` republishes it from `table.pids()`, **gated on a live `{spawn_driver, Name}` port** and run at the **start of every port round**, so a callback reached **before any round** sees `None` — which `monitor_process_result` answers by installing the monitor anyway, never a fabricated `NotAlive`.
**Static emulator-driver resolution.** `open_port`'s `PortName::SpawnDriver` arm resolves the name against `create_static_spawn_driver` **before** any `dlopen`, as the C resolves it against its loaded-driver list (`io.c:599-628`), so `open_port({spawn_driver,"tcp_inet"},[])` opens a real live port. The membership test is `beam_io`'s static set (`driver::is_static_driver` over `STATIC_SPAWN_DRIVERS`, the C's `driver_tab.c` entries whose `handle == NULL`) — **not** "is a factory registered here": `fd`/`efile` are this crate's own *internal* drivers and an invented name is nothing at all, so both take the `dlopen` route and end as the oracle's `badarg`. A **hit** registers the static `Box<dyn Driver>` through the same `register`/`PortMeta` path with `kind = PortName::SpawnDriverBuiltin`, a **miss** keeps the `dlopen` path, and a factory failure surfaces that typed error, never a fabricated port.
`PortName::bytes_from_driver_output` routes the byte paths (an exhaustive `match`): a driver port's reply — built-in or `dlopen`ed — reaches `pending_events` as an ordinary `PortNotification::Data` produced by the **port-task round** (`Port::take_input_notifications`, one notification per `driver_output*` call), never by a pre-round harvest off `beam_io`'s flat byte queue (see *the retained-events lane*). `PortMeta::has_driver_control` answers the driver-**`control`-capability** question behind the `port_control` gate from the `driver_has_control` bit `open_port` captures off the driver object itself (`beam_io::Driver::has_control`, or the `dlopen`ed adapter's entry slot); `spawn`/`spawn_executable`/`fd` are `false` by `Name` form.
`PortRegistry::port_control(id, op, arg)` forwards the verb **verbatim** to `beam_io::PortRegistry::port_control` (`beam_io/src/registry.rs:357`, which reserves the `"close"` verb); a C driver's verb is the decimal `c_uint` string `erts_internal:port_control/3` produces from its integer `Command`.
Two "is it empty" predicates: `is_empty()` counts **ports only** (`system_info(port_count)`), while `has_nothing_to_poll()` is the **nothing-pending** predicate — no live port, no retained event a round harvested but no pump has reported (`pending_events`, which is also where a drained completion sits), no close's `'EXIT'`/`'DOWN'` still owed (`pending_port_signals`), no armed `tty_select/2` interest and no fired, undrained `os:set_signal/2` self-pipe: the honest "a blocked process cannot be woken and a poll round would be pure sleep" test. An **armed but idle** `handle` disposition is **not** pending work, so a runtime that only handles a signal and never opened a port is quiescent and pays no sleep.
`pump` first `watch.sync`s the signal self-pipe into the poller, drains the retained events of earlier rounds, the queued driver output/terms, any due exit status and any handled signal, then — **only** when a real wake source exists (a live port or an armed `tty_select/2` interest) — polls in `PORT_POLL_SLICE` (25 ms) slices clamped by the earliest driver deadline, runs the port tasks and reports each driver's `driver_output` as `PortEvent::{Data,Line,Exited,Term,Signal,Select}`, the sentinel `SIGNAL_KEY` readiness filtered out of the port batch. Its early return comes **after** the unconditional `take_signals` harvest (so a caught signal is returned at once) and mints the outstanding close reports (`report_pending_closes`, because minting a close report is what retires the port's number and releases its signals).
Immediately after every round and **before** its early-return test, `pump` takes the due `exit_status`s and then drains the **line channel** — `flush_line_stream_ends` (`take_eof` on every `line`/`{line,N}` port, whose side effect is `Port::flush_linebuf`, the C's `driver_eof`) then `take_line_notifications`. A reaped child's `{exit_status,S}` must precede the flush of its own trailing partial line, and the two can land in **adjacent** rounds (the kernel closes the child's stdout inside `do_exit` *before* the zombie transition `waitpid` reports), so `hold_or_report_line` queues a frame on `PortMeta::held_lines` while the port still `owes_exit_status()`, and `release_held_lines` drains it (FIFO, port-number order, exactly once) once the status is taken or `EXIT_STATUS_FLUSH_GRACE` (1 s) expires — the C's `dd->alive == 1` deferral in `port_inp_failure` (`sys_drivers.c:1230-1252`).
`SpawnDriver` is the **single** OS-child implementation (this crate owns only `open_port/2`'s decoding into a term-free `SpawnSpec`/`SpawnOptions`, plus `PortMeta`).
`deliver_port_messages` delivers each event into the **owning** process's mailbox — data/exit-status to `owner`, a driver-emitted term to `to.unwrap_or(owner)`, a `{select,Handle,Ref,ready_input}` to the arming process and `{notify, Name}` (sender `system`) to the pid `whereis` resolves for `erl_signal_server` — each through `deliver_in_table`, so a blocked receiver is woken; `close` calls `beam_io`'s `notify_port_exit(…, Closed)` **before** `registry.close(...)`.
**The retained-events lane.** A port-task round is **destructive** (`beam_io::PortRegistry::execute_port_tasks` drains every live port's buffered input into `PortNotification::Data`), so the one round that runs *outside* a pump — `write_command`'s, where a **built-in** driver (`ram_file_drv`, `efile`) writes its reply from that very `output` call — folds its notifications into `pending_events` through the **single** `fold_notifications` helper the pump also uses, and the next `pump` reports them first through `drain_pending_events`. Delivery is still **exactly once**: the bytes left `beam_io`'s input queue at harvest, the port-task round is their **single** producer (`execute_port_tasks` → `Port::take_input_notifications` → one `PortNotification::Data` per `driver_output*` call, with `fold_notifications` the one renderer), `drain_pending_events` `mem::take`s the buffer as it reports it, and `close` purges the closed port's retained events so a **reused** port number cannot inherit a dead port's messages.
`fold_notifications` credits a payload in **both** places at the one harvest instant — the node-global `IoCounters::note_input` behind `erlang:statistics(io)` and the port's own `PortMeta::input` behind `port_info(Port, input)` — while `output` stays credited in `write_command`, at the write instant.
The **read path** is one `{Port,{data,Data}}` per driver read, rendered from `PortEvent::Data { port, read, stream, shape, owner }` by `RuntimeContext::port_data_message_shaped` → `make_stream_payload`. `Data` is the read's **own** `hbuf`/`buf` split (`beam_io`'s `ReadMessage { header, body }`, the C's `driver_output2` operands): on a `[binary]` stream a body-only read (a child's byte stream, an `fd` port) is the bare `binary` at whatever width the child wrote (up to `READ_CHUNK`, 64 KiB, built on the pointer-stable `eval_heap`), a read carrying both halves is the improper `[H1..Hh|<<Body>>]`, one with **no** body (`body: None`, the C's `NULL`) the proper `[H1..Hh]`, and a header-less read of nothing `[]`; a `[list]` stream is the flat int list of `ReadMessage::flattened()`. `StreamShape` carries the one producer fact a read cannot — `Data` (the read's own split decides) for every producer but a built-in driver port, `DriverOutput` for one (see  Known Issues).
A port opened with **`{packet, N}`** (`N` ∈ `{1,2,4}`, `packet.rs`) is **framed by the emulator**, for the spawn/spawn_executable/fd family only (`PortName::frames_packets()`): `write_command` prepends the big-endian length header (`PacketFraming::frame_output`) and `fold_notifications` reassembles the child's bytes into whole packets (`PacketFraming::push`), so the owner receives one message per complete packet, header stripped, out of one read or across several — both counters counting **payload** bytes only. A driver port carries `PortMeta::packet = None` (the option belongs to its driver; measured: a `{packet,4}` `ram_file_drv` port answers a bare `SIZE` byte exactly as an unframed one). A partial packet at end of stream is **dropped** (the reassembler dies with the port at `close`); a `{packet,1}` payload past 255 bytes or a `{packet,2}` past 65535 is a typed `unsupported` where the C kills the port with `einval`.
**The read path never blocks on the child.** A spawn/spawn_executable/fd port's stdout is put in `O_NONBLOCK` *before* it reaches the poller (`beam_io/src/drivers/spawn.rs:791-795`; the `{fd,N}` arm at `:730`) and its readiness is an `Interest::READABLE` registration (`:1088-1090`), so `SpawnDriver::ready_input` (`:1105-1137`) loops `read(fd, buf, READ_CHUNK)` (64 KiB, `:179`) only while bytes come back and returns on `EAGAIN` — a 19-byte reply costs one non-blocking syscall. `{packet, N}` reassembly never waits for a body either: `PacketFraming::push` `break`s while `rest.len() - width < length` (`packet.rs:192-194`) and the incomplete bytes stay buffered for the next read.
**The boot's `inet_gethost` child is that shape** — `lib/kernel/src/inet_gethost_native.erl:416` opens `[overlapped_io,{args,["4"]},{packet,4},eof,binary]`, every one of which `RuntimePorts::port_options` accepts (`overlapped_io`/`eof` hit the accept-and-ignore arm at `port.rs:285-300`/`:2860-2861`; `binary` at `:2844`; `{packet,4}` after the `PACKET_WIDTHS` check at `:2914`; `{args,…}` at `:2883-2885`), so no `badarg` — hence no `inet_gethost_native` retry-without-`overlapped_io` fallback — is ever raised. Its three consequences: `eof` is inert (`{Port,eof}` is never synthesized, `port.rs:114-116`, `:2083-2092`; the driver's `StreamOptions::eof` is `self.line.is_some()`, `port.rs:2557-2560`, so only a `line` port even asks its driver), so the Erlang side's `{Port,eof}` recovery can never fire; no `exit_status` option ⇒ `notify_exit == false` ⇒ `take_due_exit_statuses` (`:2216-2238`) never polls that port, so no round ever reaps it; and a **live but idle** child port keeps `has_nothing_to_poll()` false for the rest of the run, so a scheduler round that ran no slice still polls it — a zero-timeout poll for the boot drive, whose `TimerWait::ImminentWithin` policy is gated on [`PortRegistry::awaits_port_reply`] (`runtime/scheduler.rs`, the comment there names this very child; see *Measured*). A port opened with **`line`/`{line,N}`** delivers the **framed** shape instead — `{Port,{data,{eol,Data}}}` for a newline-terminated frame, `{Port,{data,{noeol,Data}}}` for a length-limited chunk or the trailing partial line released at end-of-stream — through `port_line_message` (the C's `deliver_linebuf_message`, `io.c:3454`), an **empty payload being a real frame** (`{eol,[]}`) with `input`/`IoCounters` bumping per frame. A frame is a `ReadMessage` whose **body** is the frame's bytes and whose **header** is the prefix of the read that produced it (`PortEvent::Line`'s `header`), so a `driver_output2("HDR",3,"a\nb\n",4)` yields two frames each consing `"HDR"` in front of its content (empty for a plain read and for the end-of-file flush).
**A line-mode read's header is charged only as its frames' content bytes** — `beam_io` stamps the producing call's prefix on **every** frame that call completed, where the C counts `hlen + len` once per `driver_output*` call (the `beam_io` seam ask, Handoffs).
The child's **stderr is inherited** by default (never port data); `stderr_to_stdout` duplicates descriptor 1 onto 2, so its diagnostics arrive as port data interleaved with stdout in true write order (`sys/unix/sys_drivers.c:500`).
### `port/completion.rs` — the driver→owner **completion channel** (A.4)
A socket driver cannot answer a `port_command/2` (nor a queued async op) in a control op's return value: the C *sends a message* to the port's owner. `completion.rs` is that half — `beam_io::PortCompletion` (`beam_io/src/completion.rs:289`) turned into the two families (`InetReply` → `{inet_reply,…}`, `InetAsync` → `{inet_async,…}`), which is what makes `prim_inet:send/4` and its siblings (blocked in `receive {inet_reply,S,Status,Mref}`) return.
`CompletionPacket { port, owner, stream, event }` (`:105`) is a **term-free** drained completion whose recipient and stream are snapshotted at **drain** time: a completion staged around a teardown outlives its `PortMeta` (the C's `async_error_am_all`), and a message with no recoverable recipient would be lost. `ClosedPortSnapshot { port, owner, stream, line }` (`:129`) is taken by `close` **before** `meta.remove` (`port.rs:1589`) and consulted only for the very number closed, so a recycled number inherits nothing. `PortEvent::Completion { packet }` (`port.rs:783`) rides `pending_events`, so `has_nothing_to_poll` (`port.rs:1543`) covers it and both delivery routes keep their exhaustive matches (`Runtime::deliver_port_messages`, `port.rs:3416`; `RuntimeContext::poll_port_messages`, `port.rs:3549` — the evaluator takes only a completion addressed to itself).
**Drain points.** `PortRegistry::drain_io_completions(fallback)` (`completion.rs:175`) is the **one** entry point both of a callback's message channels share: it composes `drain_failures()` **first** (`failure.rs`, the driver-closed-its-own-port channel), folds every `ClosedPortSnapshot` that drain answered **plus** the caller's own `fallback` into one list, and runs the completion sweep over them (`sweep_completions(&fallbacks)`) — so an operation a teardown answered through `async_error_am_all` is still attributed through the snapshot of the port a driver closed. The same one call therefore follows **every** point a driver callback can run, and the six rows below are unchanged: **no new row is needed for the failure channel**, because it rides behind the same call.
| drained at | where | why a completion is staged there |
|---|---|---|
| `pump`'s round, right after `execute_port_tasks` | `port.rs:1756` | the task (or the `output`/`control` it runs) stages it |
| `pump`'s "nothing live to poll" early return, after `report_pending_closes` | `port.rs:1690` | minting the last port's close report is what answers its queued operations |
| `write_command`, inline `registry.output` (a `.so` driver) | `port.rs:1257` | the driver's own `output` stages a `gen_udp:send` reply |
| `write_command`, `execute_port_tasks` branch (a built-in) | `port.rs:1288` | the `OUTPUT` task that carries the command |
| `port_control` (defensive) | `port.rs:1356` | `prim_inet`'s `recv`/`accept` arms queue an operation that completes later |
| `close`, after `registry.close` | `port.rs:1614` | the teardown's `async_error_am_all`, harvested by `beam_io` into a registry-owned queue |
`beam_io` keeps a completion on its port until drained, so a drain sees everything any earlier round staged, and each one is delivered exactly once.
**Rendering** — `RuntimeContext::{completion_message, inet_reply_message, inet_async_message, decode_caller_tag}` (`completion.rs:303-462`), on the pointer-stable `-eval` arena after the registry borrow is released, every atom interned in the runtime's **one shared** table:
| completion | message |
|---|---|
| `InetReply::Ok` | `{inet_reply, Port, ok}` |
| `InetReply::Error(R)` | `{inet_reply, Port, {error, R}}`, `R` the atom from `InetReason::atom_name()` (`beam_io/src/completion.rs:125`) |
| `InetReply` + a caller tag | the 3-tuple **plus the decoded tag as a 4th element** (the C's `inet_reply_finish`, `inet_drv.c:2614-2637`); no tag stays 3-wide, and a failed decode keeps the 3-tuple rather than fabricating one |
| `InetAsyncResult::Ok` | `{inet_async, Port, Id, ok}` |
| `InetAsyncResult::Data(read)` | `{inet_async, Port, Id, {ok, Data}}` — `Data` through `make_stream_payload(read, stream, StreamShape::Data)`, so a UDP datagram's 7-byte packed address (`wire::pack_address`) is one flat int list on `[list]`, the improper `[1,H,L,A,B,C,D|<<Payload>>]` on `[binary]` |
| `InetAsyncResult::Port(P)` | `{inet_async, Port, Id, {ok, P}}` — the adopted descriptor's new port |
| `InetAsyncResult::Error(R)` | `{inet_async, Port, Id, {error, R}}` |
`Id` is the 16-bit id the operation's control-op reply handed out, as a small integer. `decode_caller_tag` (`:435`) decodes the `term_to_binary(Mref,[local])` image through `crate::nif::with_decode_scratch` (the per-thread memoized table image `DriverPort::binary_to_term` uses) and interns any name it appended back into the live table, so a tag that carried a name cannot resolve against a scratch index the runtime does not hold.
**`Accepted { fd }` adoption.** `PortRegistry::adopt_accepted` (`completion.rs:241`) is the runtime half of the C's `tcp_inet_copy` (`inet_drv.c:11834`), which a driver cannot do here itself: `beam_io::TcpInetDriver::from_socket(fd)` in the same `PortMeta` block `open_port/2`'s built-in arm builds (`PortName::SpawnDriverBuiltin`, no OS child, the driver's own `control` capability, the **listening** port's `stream`/`line` inherited) registered through `PortRegistry::register` (`:281`). After registration the accepted port's **whole inherited option block** is installed — `data_mode(listener, stream)` resolved first, then `seed_inet_mode(new, mode)` and `inherit_inet_options(listener, new)` (see the `inet_opts.rs` section below) — and a replay the driver rejects closes the new port and fails the accept `{error, einval}` so nothing leaks. the result rewritten to `{ok, Port}` before any term is built. The descriptor is **owned by the completion** from the moment it is staged (`beam_io` neither stores nor closes it), and every path either hands it to a driver (which closes it on teardown) or releases it through `discard_descriptor(fd)` (`:299`, `FdDriver::read_only`; a failed `register` tears its driver down) — **never leaked**. An indescribable descriptor answers `{error, ebadf}`, a table with no port number left `{error, emfile}`, and a completion whose port has neither metadata nor a matching snapshot releases the descriptor and is dropped.
### `port/ops.rs` — the port **table** operations (`port_set_data/2`, the name registry, `port_connect/2`)
`PortExtras` (`pub(crate)`, keyed by **port number** like `meta`) holds the state `open_port/2` does *not* establish: `data` (the C's `prt->data`, `erl_bif_port.c:687-760`; absent means never set, rendered `undefined`), `names` and `links` (the C's `ERTS_P_LINKS(prt)`); `forget_port(number)` drops all three from `PortRegistry::close`, the single place a port leaves the runtime.
Accessors: `set_port_data`/`port_data` (`badarg` for a port the registry does not hold, `erl_bif_port.c:693-695`), the name entries, `resolve_port` (the C's `lookup_port`, `:126-143`: an internal port term **or** an atom naming a registered port), `extra_links` (`None` = the port's only link is its owner) and `connect_port` — the C's `set_port_connected` (`io.c:2330-2419`) in its non-`!` form, which **adds** a link (the previous owner's stays) and moves `PortMeta::owner`, the one field every delivery site reads.
The free `connect(ports, table, port, target)` is `erlang:port_connect/2`'s whole body, shared by its two entry points (the floor's `erlang:` spelling and the `RuntimeHooks` bridge's `erts_internal:` one), and its steps are the C's (`erl_bif_port.c:435-470`): resolve the port, require an internal **live** pid target (a dead one ⇒ `badarg`), then transfer — a nested registry borrow being the typed capability gap. The `RuntimeHooks` bridge serves `port_set_data/2`/`port_get_data/1`/`erts_internal:port_connect/2`; the `ProcessHook` bridge (`../context/process_bridge.rs`) serves the name registry, consulting the **process** table first and the port registry second, so one name can only ever be held by one of them (`register(init, Port)` is `badarg`).
The badarg matrix is the oracle's throughout: a pid/integer/dead port as the port argument, a dead target pid, a port that already has a name, a name another entity holds, an unregistered name; `port_get_data/1` of a fresh port is `undefined`.
### `port/exit.rs` — a closing port's `'EXIT'`/`'DOWN'`
A port is linkable and monitorable, so a close owes what a dying process owes its peers: `{'EXIT', Port, Reason}` to a **trapping** link and `{'DOWN', Ref, port, Port, Reason}` to every watcher, `'EXIT'` before `'DOWN'`.
A port leaves the runtime through exactly **two** closers, and both carry a reason: `port_close/1` (`PortRegistry::close`) always closes with `normal`, while a driver that closes its own port supplies its own (`failure.rs`: an atom name, an errno's POSIX name, or a bare integer). The reason therefore rides the signal (`PortSignal::reason: PortSignalReason`) instead of being fixed here, so one close's `'EXIT'` and `'DOWN'` can never disagree.
The policy: a **trapping** linked process gets that `'EXIT'`; a non-trapping one gets **nothing** when the reason is `normal` (the link family *ignores* a `normal` reason rather than terminating, so the peer survives) and is **terminated with that very reason** otherwise; every watcher gets its `'DOWN'` and has its outgoing `PortWatch` removed; a recipient the table does not hold is skipped.
`PortSignalKind{Exit, Down(MonitorRef)}` + `PortSignal{port, to, kind, reason}` are per **recipient**, so a route that can only observe its own mailbox takes its own entries and leaves the rest queued, in `PendingPortSignals{unreported, ready}`.
The obligation is discharged in **two steps** because `beam_process`'s own `ProcessTable::port_closed` frees the port number at its first step (`PortTable::close`), while `beam_io` keeps a closed port's number allocated until its `PortNotification::Closed` report is minted (`take_closed_notifications` → `ids.release`), so a `close`+`open` pair in one slice cannot make a deferred report name a different, live port. `port_exit_signals(id, reason, signals_owner)` is the pure reader of that obligation (from the metadata, the link set — `extra_links`, or the owner for a never-reconnected port — and the incoming monitors, the authoritative `beam_process::PortTable::monitors`, **not** the always-empty `PortMeta::monitors`). `capture_port_exit(id)` — called from `close` while all three are still readable — wraps it with `normal`/`signals_owner = true` and only **stashes** the snapshot, and `fold_notifications`'s `PortNotification::Closed` arm moves it into `ready`, the one point at which the port has genuinely left the runtime. The failure channel bypasses that second stage entirely (`push_port_signals` → `PendingPortSignals::push_ready`), because `beam_io` has already closed *and* reported its port by the time `take_failures` answers.
Delivery is **pull-based**: `Runtime::deliver_port_signals` takes every deliverable entry (the scheduler `run` route, through `RuntimeContext::deliver_in_table`, so a parked receiver wakes) and `RuntimeContext::poll_port_signals()` takes only its own process's entries (`take_port_signals_for`, the `-eval` `receive` route); `PendingPortSignals::prune(alive)` drops an undeliverable entry, which would otherwise hold `has_nothing_to_poll()` false for ever.
### `port/failure.rs` — the driver-failure channel's runtime half (A.4)
A driver closes its **own** port through the C's `driver_failure*` family or `driver_exit` (`io.c:7196-7278`). That is a **port-closing request**, not a return value: `beam_io` latches it from inside the callback (`DriverContext::signal_failure`), runs the ordinary teardown (`reap_failures` → its `PortRegistry::close`, so the driver's `stop` runs, the port leaves the live map and its `PortNotification::Closed` report is minted) and queues the term-free `PortFailure` (`take_failures`). This module is the half `beam_io` cannot do — it owns no terms and no process table.
`signal_reason(&FailureReason) -> PortSignalReason` (`pub(crate)`) is the **one** reason rule: `Eof`/`Normal` ⇒ `PortSignalReason::Normal` (not `Atom("normal")`, so the link family's *`normal` is ignored* policy applies to it), `Atom(name)` ⇒ that name, `Posix(errno)` ⇒ the crate's single errno→atom rule (`InetReason::from_errno(..).atom_name()`, i.e. the lowercase POSIX name, never `{error, ·}`), `Code(n)` ⇒ `Integer(n)`.
`PortRegistry::drain_failures()` takes every queued failure and answers the `ClosedPortSnapshot` of each port it finished (for the completion sweep that follows); `fail_port(id, failure)` is `close`'s bookkeeping **minus** the two steps `beam_io` has already performed — it does not call `registry.close` (the port is gone) and does not call `notify_port_exit` (the driver already saw its port exit — that is what a failure *is*) — and otherwise runs the same steps in the same order through the same helpers: `closed_snapshot`, `port_exit_signals(id, reason, failure.signals_owner)` **before** the metadata goes, `meta.remove`, `extras.forget_port`, the purge of the port's retained events, then `push_port_signals`.
Signals are published **straight into the deliverable queue** (`PendingPortSignals::push_ready` via `push_port_signals`), never stashed, because by the time `take_failures` answers `beam_io` has already closed **and** reported the port: the coincident `PortNotification::Closed` report finds nothing to release, so one failure yields exactly one `'EXIT'` and one `'DOWN'`.
**Delivery policy** — the C's single `erts_deliver_port_exit(prt, id, reason, 0, 0)` path. `exit.rs`'s `PortSignalReason { Normal, Atom(String), Integer(i32) }` rides `PortSignal::reason`, so the `'EXIT'` **and** the `'DOWN'` of one close render the same reason: a **trapping** recipient gets `{'EXIT',Port,Reason}`; a **non-trapping** one gets **nothing** when the reason is `normal` and is otherwise **terminated with that very reason**; every **watcher** gets `{'DOWN',Ref,port,Port,Reason}` (and has its outgoing `PortWatch` resolved); `signals_owner == false` (the `driver_exit` family, which runs `unlink_proc` first, `io.c:7244`) produces **no `Exit` entry at all** while every monitor still gets its `'DOWN'`. `RuntimeContext::port_exit_reason_term` interns the atom name in the runtime's one shared table (so a `receive` clause can match it) or builds the bare small integer.
### `port/info_extras.rs` — the derived `port_info/2` items
`queue_size` is the C's `erts_port_ioq_size(prt)` (`erl_bif_info.c:3868-3874`), the driver's own staging area in both directions; `beam_io::Port` holds exactly those two queues, so the answer is `input_len() + output_len()` (a fresh port `0`).
`memory` is the C's `am_memory` arm (`:3838-3860`): the port's link nodes, its monitor records, its `port_set_data/2` heap and its line buffer, **deliberately excluding the `Port` struct itself**, with the C's `link_size`/`monitor_size` callbacks **assigning** rather than accumulating (`:3648-3660`), so N links report one link node and N watchers one monitor half; its constants are the C struct sizes on a 64-bit build (`allocate_linebuf`'s `LINEBUF_INITIAL` 100, `io.c:3155-3166`), and the oracle answers `48` for a bare port (one link), `90` at `{line,10}`, `180` at bare `line` and `72` with one watcher.
`monitored_by` is the C's `am_monitored_by` arm (`:3735-3765`) read from the port table's incoming monitor list — the same authority `erlang:monitor(port, Port)` writes and `Runtime::port_monitors` reports.
`locking` is `port_level` for a `spawn`/`spawn_executable`/`fd` port (the C's own drivers set `ERL_DRV_FLAG_USE_PORT_LOCKING`, `sys_drivers.c:251`) and `driver_level` for every `{spawn_driver,Name}` port (see Known Issues); `parallelism` is truthfully `false`, this runtime never granting `ERTS_PTS_FLG_PARALLELISM` (`erl_bif_info.c:3895-3905`).
`PortRegistry::info` chains them after the seven `/1` items.
### `port/driver.rs` — the driver C ABI host (A.4)
`Driver{library, host: Box<DriverPort>}` pairs a loaded driver with the host its callbacks run against (**field order is load-bearing**: the library's `Drop` runs the entry's `finish` before the host drops); `DriverPort` is the concrete `beam_abi::DriverHost` behind the opaque `ErlDrvPort_`, whose handle **is** the per-port `DriverEnv`'s address.
`load_driver(candidates, name)` delegates to `beam_abi::driver::loader::load` (a real `ErlDrvEntry` loader, distinct from the NIF loader and needing no host), tries each candidate and reports the **last** typed error. The loader appends the shared-object suffix to **every** candidate unconditionally (the oracle's `erts_sys_ddll_open` copies `FILE_EXT` after the given name, `erl_unix_sys_ddll.c:104-118`), so `driver.rs::shared_object_stem` strips one trailing `.so` from each candidate first: both the bare `…/t` and the spelled `…/t.so` resolve `…/t.so`, and neither asks for `…/t.so.so`. That normalisation is what keeps the runtime's own documented `{spawn_driver, "…/t.so"}` form (and every fixture that loads its test driver by object path) loadable.
`binary_to_term` (`erl_drv_binary_to_term`) decodes into a **per-thread memoized image** of the shared table (`crate::nif::with_decode_scratch`, validated in O(1) by an `AtomSnapshot` witness), records an appended name on the pending interner at its predicted index (`intern`, never `intern_atom`, since the interner's `base` is fixed when the host is built), and answers the C's `ERTS_DDT_FAIL` (`None`) for an invalid image, never a raise; the registry hooks carry the C's codes (`add_driver_entry` → `0`, `remove_driver_entry` `1`/`0`/`-1` per `io.c:7698`, `lock_driver` off the load state at `:7324`, `create_port` = the invalid-port sentinel).
`DriverPort` owns the per-port **driver-private state** the frozen seam has no term/home for, in `driver/state.rs`: the C's `prt->ioq` (`io.c:6790-6919`) byte queue — one enqueue chunk per successful `driver_enq`/`driver_pushq` — behind `enq`/`pushq`/`deq`/`sizeq`/`peekq`, plus the `pdl_created` one-PDL guard, distinct from both `beam_io`'s Erlang→driver output queue (`prt->queue`) and the port's *input* queue.
`with_port_flags` carries the port's **state** stream bits (`StreamType::port_flags` → `PORT_FLAG_BINARY` (1) for a `binary` port, else `0`), a **different** cell from the `control_flags` `set_control_flags` records (`io.c:5325-5344` vs `:5318`); `clear_driver_state` (from `stop` **and** the adapter's `Drop`) drops the queue so a late drain never reads bytes of a port that has gone away.
`DriverPortAdapter` is the **port lifecycle** the host alone lacks — a `beam_io::Driver` over a loaded C driver: `start` runs the entry's `start` (the `ErlDrvPort` **is** the environment's address, kept in a `Box` that never moves); `output` hands the port's queued bytes to the entry's `outputv` when it declares one (**the C's preference**, `io.c:1782`/`:1597`) and to `output` otherwise, so an **`outputv`-only** entry really receives `port_command`; it queues the `driver_output` reply as the port's **input**; `stop` runs the entry's `stop` and the drop runs `finish` + `dlclose`.
It also seizes the host's `Rc<DriverMonitors>` at `load` and overrides `has_pending_async`/`drive_async`, that per-round drive point firing the entry's `process_exit` once per marked monitor (`driver/monitor.rs`), the tree cleared in `stop` **and** at the top of `Drop` so no callback can run after the library unloads.
An `OUTPUT` port task (`Port::run_task` → `ready_output`) **always** drains the output queue through the single `output` write path and *then* runs the entry's `ready_output` slot, when declared, as the write-**readiness** notification (the C's `ERTS_PORT_TASK_OUTPUT` arm, `erl_port_task.c:1793-1797`).
`build.rs`'s `-Wl,--export-dynamic` publishes the `driver_*`/`erl_drv_*` symbols; `open_port({spawn_driver, Name}, Options)` routes here for a name no built-in driver answers, an unknown or empty driver name being `badarg`.
The adapter also carries the per-port monitor tree, the `has_process_exit` flag, the shared `Rc<ProcessLiveness>` and the `BusyFlag` `set_busy_port` writes (`busy_flag`, stamped with `ERL_DRV_FLAG_SOFT_BUSY` by `load`), and maps `load`/`name`/`state`/`selected` plus the lifecycle callbacks: `control(command: &str, arg: &[u8])` parses the verb as a `c_uint`, `control_reply(reply, request, rbuf, len)` resolves the reply source, and `notify_ready(ctx, fd, read)` runs one **already-resolved** descriptor's `ready_input`/`ready_output` while `dispatch_ready` keeps the resolution half.
`DriverPort` implements **32 of the 43** `DriverHost` hooks declared in `beam_abi/src/driver/host.rs` (measured from the two blocks, not quoted), all four registry slots among them (`lock_driver` = `0` iff the driver is loaded else `-1`, `create_port` the invalid-port sentinel), and the failure channel's three — `failure`, `port_exit` and `port_term` — are among the implemented ones.
The other **11** keep the frozen trait default (the C's own failure code) in three groups — the **async** pair (`r`, `async_port_key`), the **lifecycle** family (`set_os_pid` / `busy_msgq_limits` / `init_ack`, plus the PDL refcount family `pdl_lock` / `pdl_unlock` / `pdl_inc_refc` / `pdl_dec_refc` / `pdl_get_refc`) and **`now`** — because each needs runtime structure a per-port host holds no handle to (the exit/OS-pid state lives in `beam_io::Port`; a refcounted PDL *lock object*; `std::time` for `now`), so a C driver calling any of the 11 gets the C's failure code, never a fabricated success.
**The failure latch, and the `ERL_DRV_PORT` resolution state.** `FailureLatch` (`driver.rs:599`) is the shared handle a driver's port-closing request is latched in: `set` is **first-wins** (a second request answers the C's `-1` rather than overwriting the first reason — in the C the first call already closed the port), `take` is the drain, `is_pending` the quiescence probe, `clear` the teardown's forget. `DriverPort::failure` maps the seam's `PortFailure` onto `beam_io::DriverFailure` (`Eof`/`Atom`/`Posix`/`Error`), flushes the driver-private `ioq` (`queue.clear()` — the C's `driver_failure_term`, `io.c:7220`) and answers `0`/`-1`; `DriverPort::port_exit` latches `DriverFailure::exit(code)` (`signals_owner = false`) the same way. Neither can close a port — a host owns no port table — so `DriverPortAdapter::settle` drains the latch inside the port lifecycle: **output first, then the request** (`beam_io::DriverContext::deliver_read` refuses a read once a failure is latched, so the reverse order would turn a legitimate data-then-failure into a capability gap, and it is the oracle's delivered order), a refused hand-off **re-latched** so the next callback retries it, and `clear_driver_state` clearing it so a port that is going away never leaves a request nobody will drain.
`PortTerms` (`driver.rs:670`) is the per-port `ERL_DRV_PORT` resolution state behind `DriverHost::port_term` — the C's `{ERL_DRV_PORT, driver_mk_port(port)}` idiom (`erl_driver.h:523`) — because this crate's `driver_mk_port` answers the **handle** (a `DriverEnv` address) while the term-data layer has no port table. It is stamped with the handle/`PortId` pair in `DriverPortAdapter::start` (the one place both are known), read back by the hook, and `mark_gone`'d from `clear_driver_state` so a driver that cached its `ErlDrvPort` cannot turn it back into a dead port's id term; an unstamped host answers `None`, and the decoder then refuses the whole spec (the C's `ERTS_DDT_FAIL`) rather than inventing a term.
The timer family matches the C for **every** live port: the C substitutes a silent `no_timeout_callback` when the entry declares no `timeout` slot (`io.c:7601`), so `io.c:6918`'s `-1` stands only for an invalid port; a fired deadline runs the entry's `timeout` or is the C's silent no-op.
### Driver-emitted terms (`erl_drv_output_term` / `erl_drv_send_term`) — `TermQueue`
`beam_abi` decodes the driver's term-data stack machine into a real term on the host's arena and calls `DriverHost::send_term(port, to: Option<Eterm>, term)`; the C delivers there and then (`driver_deliver_term`, `io.c:5664`), and the frozen seam gives the host no route to a receiver's mailbox, so the term is **queued** in a per-port shared `TermQueue`, `None` = the connected process (`erl_drv_output_term`, `io.c:6254`) and `Some(pid)` an explicit destination (`erl_drv_send_term`, `:6289`).
A queued term's words live on the host arena, so the adapter empties the queue in both `beam_io::Driver::stop` (`deliver_term_check_port`, `io.c:6213`) and its `Drop`; `PortRegistry` seizes the handle as `meta.driver_terms` at `open_port/2`, and `take_driver_terms` surfaces each as `PortEvent::Term{port, to, term, owner}`, which the pump copies onto the pointer-stable arena (`stabilize_driver_term`) and delivers.
### `port/watch.rs` — the `os:set_signal/2` delivery half (`pub(crate)`)
One `thread_local!` `FACILITY: RefCell<FacilitySlot>` holds the facility the first `os:set_signal/2` creates and production **never drops** (a per-call facility would drop at the end of the call, and `SignalFacility::drop` restores the prior dispositions); `HANDLED: RefCell<BTreeSet<Signal>>` mirrors which signals hold `Disposition::Handle`, so `is_pollable` answers without a syscall. `SignalWatch{token, fd}` is the poller registration: `sync(poller)` registers the facility's `read_fd()` under `SIGNAL_KEY` (= `u64::MAX - 1`) on the first round after a `handle` disposition; `is_pollable()` is the **poll-set** half and `has_pending_signal()` the **pending-work** half — a non-destructive zero-timeout readiness probe of the self-pipe, whose byte is the *whether* and the facility's private bitmask the *what*.
`crate::context::signal` owns the oracle answer surface (`{ok, OldDisposition}`/`badarg`, the kernel-only `sigstop` rule) and delegates the facility here; the message is `signal_notify_message(name)` → `(from, {notify, Name})` with `subject` interned as `system`.
### `erlang:port_command/2,3` and the port **busy state** (A.4)
A driver marks its port busy with `set_busy_port` (`io.c:5208-5264`); `port_command/2,3`'s answer then depends on that bit and on whether the loaded **driver entry** advertises `ERL_DRV_FLAG_SOFT_BUSY`.
`BusyFlag` (`driver.rs`) is the one shared handle for both halves: `busy` (`Rc<Cell<bool>>`, written by `set_busy_port` from inside a driver callback) and `soft_busy` (`Rc<Cell<bool>>`, stamped by `load` from `library.entry().driver_flags`).
`PortMeta.driver_busy` seizes it at registration from `host.busy_flag()` — `Some` only for a `{spawn_driver, Name}` C-driver port, `None` for a `spawn`/`fd` port and for a **built-in** driver port (whose entry flags the built-in registry does not expose), the C's "never busy, no `SOFT_BUSY`" case.
`../native/port.rs`'s `port_command` reads both (under one borrow, after the liveness check) and picks the arm the C picks (`erts_port_output`, `io.c:1749-1764`; `erl_bif_port.c:192-220`):
| port | options | answer |
|---|---|---|
| idle | `[]` / none / `[nosuspend]` | the atom `true` |
| idle | `[force]` | the atom `true` iff the **driver entry** advertises `ERL_DRV_FLAG_SOFT_BUSY`, else `error:notsup` |
| busy | `[nosuspend]` (no `force`) | the atom `false` — the command is dropped, nothing written |
| busy | `[force]` | the atom `true` iff the entry advertises `ERL_DRV_FLAG_SOFT_BUSY`, else `error:notsup` |
| busy | neither | the typed capability gap (see Known Issues) |
The `force` rule is a property of the driver **entry**, **not** of the busy state: `erl_bif_port.c:195-198` rejects `[force]` with `notsup` whenever the entry lacks the flag, **idle or busy alike**.
The busy check precedes the iodata conversion (`io.c:1760-1764`), so a busy port's `[nosuspend]` answers `false` even for non-iodata; a malformed/unknown option is `badarg`, validated **before** the port is looked up, and a dead port with `[force]` is `badarg`, not `notsup`.
## Constraints
- Crate is `#![deny(unsafe_code)]`: the registry slots operate over a **thread-local** entry list `DRIVER_ENTRIES`, not a process-global `DriverTable`, because the runtime drives every port on one thread.
- Every driver callback runs under `publishing` → `beam_abi::with_current_host` (`start`/`ready_*`/`output`/`timeout`/`stop`), which is what lets the two port-less registry slots reach a host during a callback.
- The `SignalFacility` is a `thread_local` (not a `Runtime` field) because the runtime is single-threaded (`!Send`), so the slot *is* the process's one facility.
- Never a fabricated success: failures are typed `BeamError`s, and a state/lifecycle it cannot serve returns the C's own failure code; the `Rc<RefCell<..>>` handles are the ETS pattern so a port operation never needs a runtime borrow a `fun` argument already holds — a nested borrow is a typed gap, never a panic.
- A payload is credited where it is harvested and the queue it came from is empty afterwards (`fold_notifications` + `drain_pending_events` for the data lane, `PortNotification::Closed` for the signal lane).
## Measured — the poll budget a pass hands this layer (`startup_ms`)
The largest wall-clock cost this layer can impose on a CLI start-up is **not work**: it is the
*blocking budget* a zero-slice scheduler pass hands [`PortRegistry::pump`]. Read this before touching
`PORT_POLL_SLICE`, `pump`'s wait clamp, or `has_nothing_to_poll`.

- **`PORT_POLL_SLICE` is 25 ms** and doubles as *both* the poller's inner clamp *and* the
  `port_timeout` a pass that ran no slice passes in (`../runtime/scheduler.rs::scheduler_pass`), so a
  live-but-idle port costs a whole `epoll_wait(…, 25)` per such pass — `strace -f -w` measures five
  `epoll_wait(3, [], 1024, 25) = 0` at 25.07–26.2 ms each when it does.
- **The predicate that separates the two cases lives in this layer** —
  [`PortRegistry::awaits_port_reply`] (`info_extras.rs`) over the per-port byte counters kept for
  `port_info(Port, input)`/`output` (`PortMeta::{input, output}`). A port with `output > input` has
  bytes written to it that it has not answered, so the wait is justified; a port that has answered
  everything (the boot's `inet_gethost` child, idle for the rest of the run) cannot speak again until it
  is written to, so waiting on it is pure sleep.
- **The budget cannot simply be zeroed** under a blocked round: that poll is what resolves the kernel's
  `inet_gethost` round trip, and with the budget forced to zero `drive_scheduler` returns `0` on its
  first pump, so the `{apply,{application,start_boot,…}}` directive folds to
  `unsupported: opcode: run: process blocked` (exit 3 — measured). The predicate therefore *shortens*
  the wait only for a port that owes nothing, which is exactly the case the reply cannot be in.
- **The gate is applied** at `../runtime/scheduler.rs` (`Runtime::awaits_port_reply`): a
  `TimerWait::ImminentWithin(_)` pass — only the boot drive uses that policy — gets `Duration::ZERO`
  when the predicate is false, and stays patient when the table cannot be borrowed. Measured on that
  combination: blocking rounds **8 → 1** and `strace -f -c -w`'s `epoll_wait` total
  **130.8 ms → 4.1 ms** over the same **15** calls, with `read` 233 ms → 104 ms; the lookup is
  unchanged (**98** `.beam` opens, `inet_gethost_native` included, and exactly one `execve` of
  `<erts>/bin/inet_gethost`), and the CPU cost is identical either side of the gate. The paired wall/CPU
  medians and both sides of the comparison are in [`../PERF.md`](../PERF.md) *The boot path's one
  live-but-idle port, and the poll budget* — not reproduced here.
- **The rule for any future change**: a pass may block on the poller only when something can actually
  answer — a port with a reply in flight, an armed driver deadline
  ([`beam_io::PortRegistry::next_deadline`], already clamped) or an armed `tty_select/2` interest.
  Blocking merely because a port is *live* costs a slice per pass for ever.
- **Re-measure with deterministic counters, not timings**: non-zero `port_timeout` rounds per run,
  `strace -f -c -w`'s `epoll_wait` total, the `.beam` openat count (**98**) and `execve` of
  `<erts>/bin/inet_gethost` (**exactly 1**).
- **The pinning unit test** is `tests.rs::a_port_awaits_a_reply_exactly_while_a_written_command_is_unanswered`
  (an empty registry and a live-but-idle port answer `false`, a written-but-unanswered command `true`,
  the consumed echo `false` again); the runtime side is
  `../runtime/scheduler/tests.rs::the_port_poll_blocks_only_for_a_round_that_ran_nothing`.
## Known Issues (this is a floor, not the full C `io.c`)
- **`erlang:port_control/3` is live end to end, behind the **driver-entry capability gate** stated in the API Surface** (`PortRegistry::has_driver_control`): the reply renders as a **list of byte integers** at every length, and as a **binary** only once the driver set `PORT_CONTROL_FLAG_BINARY` through `set_port_control_flags` (a per-port flag persisting across calls), a `NULL` reply pointer being the C's `NIL` (the bare `[]`, `io.c:4126`); the residual is a reply the driver answers from **its own** memory, the typed *unsupported* (Handoffs).
- **The one `port_command/2,3` divergence: a plain command on a busy port.** The C **suspends** the caller (`erts_suspend` + `ERTS_BIF_YIELD3`, `erl_bif_port.c:211-220`) until the port goes idle and re-runs the BIF, so the oracle eventually answers `true`; this runtime's BIF seam has no block channel, so that arm raises the typed capability gap (exit 3, reason naming the busy state); every other arm (`true`, `false`, both `notsup`s) matches the oracle.
- **A NULL driver reply with `PORT_CONTROL_FLAG_BINARY` set answers `<<>>` where the C answers `[]`**: `write_port_control_result` (`io.c:4126`) returns `NIL` for a NULL reply pointer **before** it looks at the flag, while the adapter collapses "the driver left `*rbuf` NULL" and "the driver answered zero bytes" into one empty `Vec`; closing it needs that bit threaded to `PortRegistry::port_control`.
- **`driver_async` schedules nothing**: `r#async` keeps the frozen default `-1`, because `Runtime` is `!Send`, no worker thread can call back into it, and the C's in-band path when the pool is empty (`erl_async.c:604-613`) needs the entry's `ready_async`, which only the adapter's loaded library holds.
- `beam_io`'s `EfileDriver`/`FdDriver` are implemented and tested but do open/read/write only and are **never constructed by this runtime** (only `SpawnDriver` is); file I/O here is the `std::fs`/`std::env` native floor under `../native/prim*.rs`.
- **Driver-interned atoms land at the port boundary, not inline**: a name first interned *inside* a driver callback gets a **predicted** index (the live table is borrowed for the whole callback); `commit_driver_atoms` commits it at that exact index, and a prediction the table has moved past is **reported** (`dropped`, printed), never interned at a foreign index. `has_pending_driver_atoms`'s guard runs **before** any `atoms_mut` borrow, so the shared table is deep-cloned only in a round where a driver really interned a new name (`tests.rs::an_idle_port_round_does_not_clone_the_shared_atom_table`).
- `take_exit_status` is always `Ok(None)` — a driver port owns no child, so no `{Port,{exit_status,…}}`.
- **The monitor family is live end to end**: `DriverPort` keeps the per-port `DriverMonitors` tree (keyed on the C's 24-byte reference identity, through the safe `beam_abi::monitor_identity`/`monitor_from_identity`), seized as `PortMeta.driver_monitors` at `open_port/2`; `monitor_process_result` answers the C's `0`/`1`/`-1` over a five-way split (no `process_exit` slot ⇒ `-1`; a non-local pid ⇒ `-1`; an observed-alive local pid ⇒ `0` plus a fresh holder; an observed-dead local pid ⇒ `1` with nothing installed; **no observation** ⇒ `0`, the non-regression fallback).
  The **marking** half: `note_driver_monitor_exits(&ProcessTable)` walks every live port's tree and calls `note_process_exit(pid)` for each watched pid the table no longer holds; `Runtime::drain_driver_monitor_exits` **defers** with `Ok(0)` on a live borrow, and the scheduler pass runs it immediately before `deliver_port_messages` so the same round's probe fires the entry's C `process_exit`.
- **`PORT_FLAG_LINE` (2) is reachable, and line framing is adopted end to end.** `open_port/2` decodes `line`/`{line, N}` into `PortOptions::line` (a bare `line` is `LINE_DEFAULT_MAX_LEN` = `512`) and carries it as a separate `PortMeta::line` field, armed through `beam_io`'s `set_line_mode(id, Some(max_len))`.
  `StreamType::port_flags(line)` ORs `PORT_FLAG_BINARY` (1) and `PORT_FLAG_LINE` (2) independently, so `[line]` answers `2`, `[binary]` `1`, `[binary, line]` `3` and no stream option `0`; the exclusivity rules are checked after the whole list is parsed (`line` + `{packet, N}`, `stderr_to_stdout` without `use_stdio` ⇒ `badarg`), and `stream_options` asks the child driver for its **end-of-stream observation** on exactly the line-mode ports, which lets `flush_line_stream_ends` release the trailing partial line.
- **`get_port_flags` is answerable from inside `start` where the oracle answers `0`.** The oracle ORs `ERTS_PORT_SFLG_BINARY_IO`/`_LINEBUF_IO` into `port->state` only **after** `open_driver` returns (`erl_bif_port.c:1139-1143`), while `with_port_flags` sets the bits at host construction; no corpus case calls it from `start`.
- **`driver_async_port_key` stays unimplemented** (`async_port_key` keeps the trait default `-1`): the C body (`erl_async.c:518-525`) returns the port's internal data word truncated to 32 bits, an address-derived opaque value whose only defined use is the pool bucket selector (`:585-593`), and the seam has no handle to it.
- A driver that armed **more than one** registration per direction is a typed `unsupported` (`armed_event`), never a wrong descriptor.
- `os:set_signal/2`'s notification is **dropped when no `erl_signal_server` is registered** — the C's own behaviour (`sys.c:589-604`), never an error; the `-eval` receive path drops a `PortEvent::Signal` (it observes only its own mailbox), while the scheduler path delivers it.
- **A built-in driver port's `{data, D}` renders as list elements on either stream.** A `PortName::SpawnDriverBuiltin` port reports `StreamShape::DriverOutput`, rendering its **flat, header-less** queue as list elements (the C's `deliver_read_message`, `io.c:3404-3435`), so every header-only reply is the oracle's **exact** list. The one residual is a **producer** fact: an in-tree driver hands its bytes up through `beam_io`'s flat `DriverContext::input()`, which cannot say which of the four `driver_output*` entry points wrote them, so `DATA`'s improper binary tail (`driver_output_binary`, `ram_file_drv.c:448`) renders as a proper list of the same bytes; closing it needs `beam_io`'s in-tree drivers to hand bytes up through `DriverContext::deliver_read(header, body)` (Handoffs).
- **A `dlopen`ed driver's split read survives end to end.** `impl DriverHost for DriverPort` (`driver.rs`) implements `output2`, recording the C's `hbuf`/`hlen` + `buf`/`len` halves as `(header, Option<body>)` (`body == None` is the C's `buf == NULL`; `Some(&[])` a present, empty tail), while `output` records the header-less `(Vec::new(), Some(data))` shape; `DriverPortAdapter::collect_outputs` hands each recorded call to `beam_io::DriverContext::deliver_read` as **one** read. The reply therefore reaches the owner under `StreamShape::Data` with the C's boundary intact — `driver_output2`'s `[72,68,82|<<"abc">>]`, `driver_output_binary`'s improper tail, `driver_outputv`'s vector — oracle-identical (`tests/driver.rs`'s `recv_split/0` over the `eventsplit` fixture mode).
- **A zero-byte read produces no message**: `fold_notifications` drops a read `ReadMessage::is_empty()` reports (no header and no byte — the C's `hlen == 0 && len == 0`), right for the `{packet, N}` arm it precedes (a zero-length *packet* is a real frame) but leaving `driver_output2(NULL,0,NULL,0)`/`driver_output("",0)` silent where the oracle delivers `{Port,{data,[]}}`/`{Port,{data,<<>>}}`; both shapes are built by `make_stream_payload` and pinned at the builder level (`stream_shape_tests.rs`).
- **`port_set_data/2`'s term words are not counted by `port_info(Port, memory)`**: the C copies the term onto a private heap, while this runtime keeps it on its pointer-stable store, so `port_set_data(P,{foo,1})` reports `120` where the oracle reports `136`; no number is fabricated.
- **`locking` reports `driver_level` for every `{spawn_driver, Name}` port.** The C decides on the driver entry's `ERL_DRV_FLAG_USE_PORT_LOCKING` (`erl_bif_info.c:3875-3894`), but the bit does not cross the `beam_io` seam (`DriverFlags` keeps only `SOFT_BUSY`); the OS-child drivers report `port_level`, the oracle's own answer.
- **A tagged port monitor's `'DOWN'` carries the default head.** `erlang:monitor/3`'s `{tag, Tag}` for a **port** monitor lives in `beam_process`'s private `ProcessTable::tags` map, which no API of that crate exposes; the untagged shape is byte-exact.
- **The `-eval`/action process starts with `trap_exit = false`** (`../runtime.rs::as_action_process`), where the oracle's `-eval` process reports `{trap_exit,true}`, which is why every port-exit fixture sets the flag explicitly.
- **The inet stack reaches this node end to end, and the completion channel is what closes the send path.** Agreeing with the oracle: `gen_udp:open/1,2`, `gen_tcp:listen/2` (the `[binary]` form included), `inet:getstat/1,2` and a two-socket **UDP round trip** — `gen_udp:recv(A,0,5000)` answers `{ok,{{127,0,0,1},Port,<<"hi">>}}` (exit 0, modulo the ephemeral port), because `prim_inet:send/4`'s `{inet_reply,…}` arrives.
  `gen_tcp:connect/2,3,4` runs too: `inet:timeout/1` reaches `erlang:read_timer/1`, which the `RuntimeHooksBridge` serves over `Timers::remaining` (`../timers.rs`), so a connect to a closed loopback port answers `{error,econnrefused}` and one to an in-runtime listener `ok`, as the oracle does.
  Two residuals, both typed: (a) a **nested blocking call on the `-eval` route** with no deadline to wait for still folds to `beam_engine::error::blocked()` (exit **3**, `unsupported: opcode: run: process blocked`) — a `gen_udp:recv/3` with no datagram yet, any `gen_tcp:accept`; that is the `-eval` pump's inability to resume a *still* parked nested call (`../context/pump.rs`, sibling-owned), **not** a channel gap, and the scheduled `run` route pumps and resumes. (b) the driver's **async-op queue** (`INET_MAX_ASYNC`) is not modelled: a control-op `recv` is a synchronous read-now substitution answering `[1]` where the oracle returns an op-id (`[1,0,0]`) and later delivers `{inet_async, Port, Ref, {ok, Data}}` (M1_GAPS *Ports, drivers and the send family (A.4)*); the completion channel's `InetAsync` family renders the message shape for the ops that do stage one.
- **A completion's recipient is the port's `owner`, not the C's `desc->caller`.** The C addresses the reply to the process that issued the control op/command; the frozen `beam_io::Driver` seam exposes no `driver_caller`, so `drain_io_completions` resolves `PortMeta::owner` (`completion.rs:67-73`). The two coincide for every `prim_inet` caller — the owner issues the control op — so the divergence is unobservable in practice.
- **`{mode, list}` after `open_port/2` does not re-render a completion as a list.** `PortMeta::stream` is fixed at open time (`prim_inet:open/5` always passes `[binary]`) and a `{mode,…}` `setopts` request travels as a control op this node forwards **verbatim**, never folded back into `PortMeta`; the drained packet carries that stale snapshot (`completion.rs:176-181`), so an `{inet_async,…}` payload stays a `binary`/improper list for the port's whole life (the driver's own mode would have to cross the `beam_io` seam).
- **`port_command/2,3` and `port_control/3` take only a **port term**, where the C also resolves an atom name.** Both decode with `PortId::from_eterm` (`beam_process/src/pid.rs:129` — `is_internal_port` only) → `badarg`, while the C's `lookup_port` (`erl_bif_port.c:129-141`) maps an atom through `erts_whereis_name_to_id` and the specs are `Port :: port() | atom()` (`erts/preloaded/src/erlang.erl:12006,12207`); `port_info/1,2` and `port_connect/2` **do** resolve a name, so the gap is confined to these two.
- **`driver_failure_atom/2`'s name crosses the `beam_abi` seam as UTF-8, while the C interns Latin-1 bytes.** `beam_abi/src/driver/drv/lifecycle.rs::driver_failure_atom` answers `-1` for a name that is not valid UTF-8 (the seam's reason is a `&str`, so the C's raw Latin-1 bytes cannot be spelled at all), and a valid multi-byte UTF-8 name becomes **one** atom carrying those codepoints where the C interns the individual bytes. Only the ASCII rows are oracle-identical.
- **The data-then-failure row and the non-trapping owner's fate are pinned end to end by `tests/port_failure.rs`** (a real C driver, both delivery routes, oracle-cross-checked): the read a failing callback wrote with `driver_output*` reaches its owner **before** the exit signal (`fold_notifications`' `Data` arm falls back to the recipient facts `fail_port` snapshots in `failed_read_recipients`, consumed once, dropped at the port's `Closed` report and cleared on `register`, so a recycled number inherits nothing), a non-trapping owner is terminated for a non-`normal` reason and survives `normal`, and `driver_exit` never signals a linked owner.

## Notes for Agents
- **A new driver-callback site must add a row to the completion channel's drain-point table.** `has_nothing_to_poll` only sees what has already been **drained** into `pending_events`, so a site that folds notifications without draining loses the `{inet_reply,…}`/`{inet_async,…}` its driver staged, and no later round reports it.
- **How the `inet` stack reaches this node — exactly two doors.** `erts/preloaded/src/prim_inet.erl` is the only module in the tree that opens an `{spawn_driver, …}` port (`:103`), with **one** option, `[binary]`; every socket option travels separately through `prim_inet:setopts/2`, and every *request* is `erlang:port_control(Port, Req + 16#03f1a300, Buf)` via `ctl_cmd` (`:2972-2984`), whose `[1|Reply]`/`[2|ErrAtom]` bytes this node renders as `int_list` — so `gen_tcp`/`gen_udp`'s option and statistics surface reaches the driver through `PortRegistry::port_control`, never through `open_port/2`.
  A **send** is a `port_command` whose payload *begins* `<<RefLen:16, term_to_binary(Mref, [local])/binary>>` (`prim_inet:send/3`, `:578-588`; `sendto/4`, `:660-680`), after which the caller blocks in `receive {inet_reply, S, Reply, Mref}`. The inet drivers stage that reply as `CompletionEvent::InetReply` through `beam_io`'s `DriverContext::deliver_completion` (`beam_io/src/drivers/inet/async.rs:901`), which `PortRegistry::drain_io_completions` turns into the message; the ref prefix itself reaches the driver **verbatim**, and `PortMeta::driver_terms` stays `None` for `PortName::SpawnDriverBuiltin` (`port.rs:3168`).
- The colocated signal tests share **one** `watch::test_guard()` lock so they serialize on the process-global signal dispositions, and signal tests send with `Command::new("kill") -USR1 <pid>` on `std::process::id()` — **never** `libc::raise`, which would need `unsafe`.
- A test that calls `run_scheduled` must account for the port loop parking (`Runtime::is_nt` reads `has_nothing_to_poll`; see `../runtime/CONTEXT.md`), and a test that closes a linked port must drain **both** lanes — the `run` route needs a further pass for `deliver_port_signals`, the `-eval` route a further `poll_port_signals`.
- A new `port_info` item belongs in `PortRegistry::info` **and** in `../native/port.rs`'s `PORT_INFO_1_ITEMS` decision: the `/1` roster is the C's `ERTS_PORT_INFO_1_ITEMS` and nothing else.
- **The sibling `../../tools/differential/divergences.md` A.4 entries are STALE** against `driver.rs`/`port.rs` (the driver-monitor family, an `outputv`-only entry, `driver_set_timer/2` without a `timeout` callback, `commit_atoms/1`): all four agree with this node — escalate a correction to that node's owner.

## Known divergence from the oracle: no child-exit auto-close
- ERTS **auto-closes** a `{spawn, Program}` port once its child exits: after the child is reaped, `erlang:port_info(P)` is `undefined`, `lists:member(P, erlang:ports())` is `false`, and `erlang:port_close(P)` raises `error:badarg`.
- This runtime does **not** auto-close on child exit: `PortMeta.notify_exit` is only set by the `exit_status` option, so nothing reaps or removes the port until an explicit `port_close` — `close` kills+reaps, `meta.remove`s, forgets the extras and releases the id, synchronously.
- The child is therefore reaped at exactly two points, both of which **`SIGKILL` it and then block in `wait`**: `PortRegistry::close` → `beam_io` `Driver::stop` (`drivers/spawn.rs:1139-1154`) → `kill_and_reap` (`:1225-1246`), and — for a port nobody closed — the driver's `Drop` (`:1165-1175`) when the `Runtime` drops. Because `main` evaluates `cli::run` and only then calls `std::process::exit` (`src/main.rs:29`), the `Runtime` in `cli::run`'s `source` **is** dropped on the `halt()` path, so the boot's idle `inet_gethost` child is killed and waited for there; a `wait4` after the last poll round in a trace belongs to that teardown, not to a round.
- The corpus **sidesteps** the divergence rather than pinning it (the five `driver/port_*` close cases each open a child alive until the explicit `port_close/1`), so the gate's 0-mismatch verdict is consistent with it.
## Handoffs (owned by OTHER nodes)
- **`beam_abi`** — `r#async` adoption needs a **safe** route from the hook's three raw operands to an `AsyncJob`: the runner and `DriverLibrary::ready_async` exist, but `AsyncJob::new` is that crate's one `unsafe` entry point.
- **`beam_abi` / `beam_io`** — a **safe reply-copy** helper for a `control` reply the driver answered from memory of its own (today an `unsafe` slice read inside `impl Driver for DriverPort`, `beam_io/src/abi/port.rs:710-747`); until it exists `control_reply` answers the typed *unsupported*.
- **`beam_io`** — the driver-entry flag `ERL_DRV_FLAG_USE_PORT_LOCKING` would have to cross the seam (`DriverFlags` keeps only `SOFT_BUSY`) for `port_info(Port, locking)` to answer `port_level` for a driver that asks; a **line-mode** read must name its producing call (or stamp the header on the **first** frame only) so a frame's prefix can be charged once, as the C charges `hlen + len` per call; the **in-tree** drivers must hand bytes up through `DriverContext::deliver_read(header, body)` rather than the flat `input()` for a `DATA` reply to render the oracle's improper `[2,0,0,0,2|<<97,98>>]` (see the read-path bullets); firing the driver's `process_exit` needs no new seam, since `execute_port_tasks` already calls `drive_async` each round (`beam_io/src/registry.rs:291-317`).
- **`beam_io` (the completion channel's two seam asks)** — a `driver_caller` on the frozen `Driver` seam would let a completion be addressed to the C's `desc->caller` instead of `PortMeta::owner` (see Known Issues), and the driver's own `{mode, list|binary}` would have to cross the seam for a post-`open_port/2` `{mode,…}` to re-render an `{inet_async, …}` payload.
- **`beam_bifs`** — `erlang:read_timer/1,2` was the connects' blocker (`inet:timeout/1` calls it unconditionally, `lib/kernel/src/inet.erl:4953-4957`); it is served now by this crate's `RuntimeHooksBridge`, so the connect path needs nothing further from that crate.
- **`src/context/**` (sibling node)** — the `-eval` pump cannot resume a parked nested call, so a completion that arrives for a nested `gen_udp:recv/3`/`gen_tcp:accept` has no waiter and the route folds to the typed `blocked()` gap (`../context/pump.rs`); the channel delivers the message, the resume is that node's.
- **`beam_process` — no seam needed for the marking** (its single exit observer stays `EtsExitObserver`), **but** a tagged port monitor's `'DOWN'` needs that crate to expose the monitor's `{tag, Tag}`, and `ProcessTable::port_closed`'s `PortTable::close`-first order is what keeps the exit signalling out of that crate — an API that snapshots relations without freeing the port number would move the whole obligation there.

## `port/active_input.rs` — the `{active, …}` input channel (A.4)
`beam_io`'s **active-mode input channel** is the driver→owner path of an `{active, true|once|N}`
socket: a socket in active mode never parks its input in the port's byte queue, so the driver
*sends a message to the port's owner* from its read-readiness callback. The driver half
(`beam_io`'s `drivers/inet/active.rs`, `drivers/inet/udp/active.rs`) is complete and stages one
`ActiveInput { port: PortId, event: ActiveInputEvent }` per delivered unit through
`DriverContext::deliver_active_input`; `active_input.rs` is the runtime half, shaped exactly like
the completion channel beside it.

| event | port kind | message | C |
|---|---|---|---|
| `ActiveInputEvent::Data(read)` | `tcp_inet` | `{tcp, S, Data}` | `tcp_message`, `inet_drv.c:3979-4020`; `tcp_binary_message`, `:4022-4055` |
| `ActiveInputEvent::Data(read)` | `udp_inet` | `{udp, S, IP, Port, Data}` | `packet_binary_message`, `:4105-4160` over `load_address`, `:1916` |
| `ActiveInputEvent::Passive` | `tcp_inet` | `{tcp_passive, S}` | `packet_passive_message`, `:4215` |
| `ActiveInputEvent::Passive` | `udp_inet` | `{udp_passive, S}` | the same builder, the other branch |

**Oracle-verified shapes** (OTP 29.1.1 / erts-17.1, real loopback traffic; `#Port<P>` for the
port term): `{active,once}` + `<<"hi">>` ⇒ `{tcp,'#Port<P>',<<"hi">>}`; `[list]` ⇒
`{tcp,'#Port<P>',"hi"}`; `{active,1}` + a second datagram ⇒ one `{tcp,…}` then
`{tcp_passive,'#Port<P>'}`, and re-arming `{active,once}` delivers again; `{packet,2}` strips the
2-byte frame header ⇒ `{tcp,'#Port<P>',<<"hello">>}`; `{header,2}` over `<<"hello">>` ⇒
`{tcp,'#Port<P>',[104,101|<<"llo">>]}`, `hsz == len` ⇒ `[…|<<>>]`, `hsz > len` ⇒ the flat `"h"`;
`{active,false}` delivers nothing here (the bytes stay for `gen_tcp:recv/2`); UDP binary ⇒
`{udp,'#Port<P>',{127,0,0,1},39846,<<"hi">>}` from a socket bound to 23456 (`0x5BA0`) ⇒ the source
**port field is big-endian**; UDP `{active,2}` + three datagrams ⇒ two `{udp,…}` then
`{udp_passive,…}`; an empty datagram is `{udp,'#Port<P>',{127,0,0,1},50339,<<>>}`.
**The rendering is proven end to end over real loopback traffic** (`active_input_e2e_tests.rs`);
what is *not* yet wired is the packet's delivery into the owner's mailbox — see *Wiring* below.

The module is declared from **`ops.rs`** (`#[path = "active_input.rs"] pub(crate) mod
active_input;`, beside the `#[path]` declaration of `inet_opts`). It has two suites, reached with
`... -p beam_rt --lib -- active_input`: the matrix (`#[path = "active_input_tests.rs"] mod tests`,
16 cases over made-up reads) and the end-to-end suite (`#[path = "active_input_e2e_tests.rs"] mod
e2e`, 9 cases, 8 of them real traffic).

**What the end-to-end suite drives, and how far.** Each case opens a real `{spawn_driver,
"tcp_inet"|"udp_inet"}` port through `RuntimePorts::open_port`, drives the driver's own numeric
control requests (`INET_REQ_OPEN`/`BIND`/`CONNECT`, `INET_REQ_SETOPTS` with the `INET_LOPT_*`
records), really connects a `std::net` peer or really sends a datagram to it, then
`pump` → `drain_active_inputs()` → `RuntimeContext::active_input_message` → the registered `~w`
printer. That is the whole channel up to the message term; wrapping a packet in a `PortEvent`,
publishing it and writing the mailbox is `src/port.rs`'s and is not exercised. Asserted against the
oracle's own printed rendering (one case re-runs every probe live): `{active,once}` binary ⇒ one
`{tcp,S,<<104,101,108,108,111>>}` per grant, a write under the spent grant ⇒ nothing, a re-arm ⇒
the next write delivered; `{mode,list}` ⇒ `{tcp,S,[104,101,108,108,111]}`; `{packet,2}` ⇒ the
frame header stripped; `{header,2}` ⇒ `{tcp,S,[104,101|<<108,108,111>>]}` with the read's own
`hsz`/body split; `{active,2}` ⇒ two payloads, then exactly one `{tcp_passive,S}` in the same
drain, then nothing, and a later `{active,false}` owes no second passive message; a passive socket
⇒ nothing on this channel; a real datagram ⇒ `{udp,S,{127,0,0,1},<client's own port>,<<"hi">>}`
with the source port decoded big-endian out of the packed address, an empty datagram ⇒ `<<>>`, and
UDP `{mode,list}` ⇒ `[104,105]`.

**Two measured differences from the oracle, both recorded by the suite.** (a) A write arriving
while an `{active,once}`/`{active,N}` grant is spent: the C disarms the descriptor
(`sock_select(desc, FD_READ, 0)`), so the *re-arm's* inline read delivers those bytes; `beam_io`'s
poller stays armed, so `async_ready_input` harvests them into the port data queue instead and the
re-arm's inline burst finds the socket empty. The suite asserts only what both sides agree on (a
spent grant delivers nothing; the write after a re-arm is delivered), and its oracle case prints
the oracle's own differing value. (b) `{mode,list}`'s effective mode is not in the packet: see the
`data_mode` seam below.

**Every `setopts` in the e2e suite is followed by an explicit `PortRegistry::note_inet_setopts`
with the reply's own success tag** — the documented stand-in for the hook `src/port.rs`'s
`port_control` will make (`accept_inherit_tests.rs`'s pattern). Once that hook lands, the explicit
calls are redundant, not wrong.

**`ActiveInputPacket { port, owner, data_mode, kind, event }`** mirrors `CompletionPacket`: the
owner, the stream mode and the port's **kind** are all resolved at **drain** time
(`PortRegistry::drain_active_inputs`, from `PortMeta`), because a delivery staged around a
teardown outlives the metadata. `drain_active_inputs` returns `Vec<ActiveInputPacket>` — its own
term-free type, **not** a `PortEvent`: the packet already names its recipient, so the provider
needs no event variant to carry it and no second table read to deliver it. `ActivePortKind
{ Tcp, Udp, Other }` comes from the driver name — `driver_path_name(&meta.command)` matched
literally against `tcp_inet`/`udp_inet`, the same first-blank rule the driver search applies.
`Other` is a **typed capability gap** for both events (`crate::error::unsupported`, naming the
port), never a fabricated `{tcp,…}` and never a silent drop. A delivery whose port has already
left the runtime is **dropped**, the completion channel's rule, and the drop is final: the packet
carries the `owner`/`port` it resolved, so nothing can be re-attributed to a later port that
reuses the number, and the draining `Vec` is the only thing that carried it.

**The mode seam is `PortMeta::data_mode`** (`impl PortMeta`, in `active_input.rs`), whose body is
`self.stream` today — the port's **open-time** stream option. `{mode, list|binary}` never reaches
`beam_io` (`drivers/inet/CONTEXT.md` §"Shape"), so a post-`open_port/2` mode change lives only in
the Erlang-side `{mode,…}` mirror (`inet_opts.rs`), and `prim_inet:open/6` always opens `[binary]`:
a `{mode,list}` socket is a `[binary]` port whose *driver* holds `INET_MODE_LIST`. The effective
mode is therefore `PortRegistry::data_mode(id, fallback)` (the mirror), and a delivery arm must
resolve it before rendering — the e2e suite pins both halves (the packet says `Binary`, the
resolved mode is `List`, and the rendered payload is a char list). Do not add a second
`PortMeta::data_mode` in `port.rs` — a duplicate inherent method is a compile error.

**One delivered unit is `beam_io`'s decision, not this module's**: under a framing `{packet, N}`
one delivery is **one frame** with the framing header **already stripped**, under `{packet, raw}`
one read burst; and a read's `header` is the `{header, N}` option (`desc->hsz`) for a stream port
and the 7-byte packed source address for a datagram port — never the framing header. So `Data` is
rendered from the read's own header/body split and nothing is re-framed.

**Payload rendering goes through the one stream shaper**: TCP calls `make_stream_payload(read,
mode, StreamShape::Data)` directly; UDP decodes the address out of the read's header
(`decode_packed_address`: `[INET_AF_INET(=1), port_hi, port_lo, a, b, c, d]`, port big-endian) and
shapes the **body alone** through the same shaper from a header-less `ReadMessage`, so header
consing / improper lists / list flattening cannot drift into a second byte-list builder. A
header that is not exactly one packed IPv4 record is a typed gap — an address is the one element
of `{udp,…}` that must never be invented.

**Wiring still owed by the parent node (`src/port.rs`)** — the module compiles and both suites
pass without any of it, because the drain is called directly by the tests; nothing yet delivers a
packet into its owner's mailbox: (a) call
`drain_active_inputs()` immediately after each of the six `drain_io_completions(...)` sites
(`write_command`'s two branches, `port_control`, `close`, `pump`'s round and `pump`'s "nothing
live to poll" early return) and hold the returned packets as pending work, and (b) the two
delivery arms (`Runtime::deliver_port_messages` → `packet.owner` via `deliver_in_table`, so a
blocked receiver wakes; `RuntimeContext::poll_port_messages` → only `packet.owner == self.pid()`),
calling `RuntimeContext::active_input_message` on the public path. Until (a) lands, a staged
active delivery is never drained, so `src/port.rs` currently reports the module's items as dead
code (10 of the crate's 31 build warnings, the other 21 being `inet_opts`'s);
`PortRegistry::has_nothing_to_poll` will then need the pending packets counted (they are not a
`PortEvent` and so are invisible to `pending_events`).

**Known residual — `hsz > len`, a `beam_io` seam.** The C's list branch is `(mode == LIST) ||
(hsz > len)`, so a `{header,N}` wider than the payload is one flat string with no binary tail (the
oracle's `"h"`). `beam_io`'s `split_payload` clamps `hsz` to the payload and hands that case up as
a whole-payload header with a present-but-empty body, which renders `[104|<<>>]` where the oracle
prints `"h"`. Fields are preserved in order and `[list]` mode is exact; closing it needs
`beam_io` to carry the raw `hsz` (the seam is not revisable from this crate), and every shape the
e2e suite exercises has `hsz <= len`, so it is not observable over the wire. Pinned at the
renderer level by `active_input_tests.rs::a_header_as_wide_as_the_payload_keeps_an_empty_binary_tail`.

## `port/inet_opts.rs` — the accepted socket's inherited option block (A.4)
`prim_inet:open/6` opens every `inet` driver port with **one** option, `[binary]`
(`erts/preloaded/src/prim_inet.erl:99-137`), and applies every other socket option afterwards through
`setopts/2` — an `erlang:port_control/3` call carrying the C's `[opt_code, val_be32]` records. So
neither `open_port/2`'s options nor `PortMeta::stream` know what the **driver** has been told: a
`{mode, list}` socket is a `[binary]` port whose driver holds `INET_MODE_LIST`.
`inet_opts.rs` is that knowledge, per port, keyed by **port number**.

**What is recorded.** Every **successful** `setopts` argument verbatim and in arrival order
(`PortInetOptions::records`, the replay source) plus the driver's current `{mode, list|binary}`
(`PortInetOptions::mode`, [`INET_LOPT_MODE`]). One entry point does the recording —
`PortRegistry::note_inet_setopts(id, arg, ok)` — so a rejected `setopts` can never be inherited: only
a reply whose leading tag is the C's `INET_REP_OK` is stored. The mirror is held **inside**
`PortExtras` (`inet: InetOptions`), so a port has exactly one post-`open_port/2` lifecycle and
`PortExtras::forget_port` drops it with the rest — a recycled port number never inherits a dead
socket's options.

**The wire reader.** `walk` splits an argument into records while `rest.len() >= RECORD` (5, the C's
`while (len >= 5)`, `inet_set_opts`, `inet_drv.c:6908`) and answers `None` if **any** byte is left
over: the C silently ignores a partial trailing record because it has already applied what it
consumed, but this walker's output is **replayed**, and an argument that is not a whole number of
records did not come from `prim_inet:encode_opt_val/1` — replaying the subset that happens to parse
could claim a configuration the listener does not have. `record_len` is the C's per-code span:
`linger` `RECORD+4`, `multicast_if` the whole `RECORD`, membership `RECORD+12` (IPv4) /
`RECORD+20` (IPv6) and `None` for any other domain, `{active,N}` `RECORD+2`, `raw`
`RECORD+8+arg_sz` with `arg_sz` at `RECORD+4..RECORD+8`, `netns`/`bind_to_device` `RECORD+value`.

**What is replayed onto an accepted port.** Exactly the set the C's `tcp_inet_copy` copies into the
new descriptor (`inet_drv.c:11810-11827`) — `is_inherited_record`: packet type, packet size, header
size, mode, `deliver`, `exit_on_close`, the buffer size, both TCP watermarks, the send-timeout pair,
the busy-message-queue pair and the three `tcp_add_flags` bits (`show_econnreset`, `read_ahead`,
`linger_zero`). Two families are deliberately **not** replayed, each for a reason the C gives:
`{active, …}` (`tcp_inet_copy` copies no active counter, and `prim_inet:accept_opts/3`
(`:502-517`) re-applies it from the listener — replaying it would **double-arm** the counter, since
the C's `INET_LOPT_ACTIVE` arm *adds* its operand, `inet_drv.c:6968-7000`), and the **kernel-backed**
options (`nodelay`, `keepalive`, `linger`, `reuseaddr`, `priority`, buffers…), which `accept(2)`
gives the new descriptor anyway and `accept_opts/3` re-applies six of. `{line_delim, …}` is not
copied for the same reason the C does not copy `desc->delimiter`.

**The mechanism is a replay, not a copy.** `beam_io::TcpInetDriver::from_socket(fd)` takes no option
set and `beam_io` cannot create a port, so `PortRegistry::inherit_inet_options(from, to)` sends each
inherited record through the ordinary named `setopts` verb of `PortRegistry::port_control` — the same
path the original call took, re-recorded onto the destination by the same `note_inet_setopts`. The
listener's records are snapshotted first (a replay borrows the registry mutably).

**The replay's failure rule.** A record the driver **rejects** cannot be ignored — half a
configuration is a socket whose `{packet, N}`/`{mode, …}` disagree with the listener's — so
`adopt_accepted` stops, **closes** the freshly adopted port (whose driver owns the descriptor, so the
close releases it; nothing leaks) and completes the accept as `{error, einval}`, the errno the driver
itself answers for a bad option. The C cannot fail here because it copies a struct; a replay can, and
a typed `{error, einval}` from `gen_tcp:accept/1` is the honest report.

**What an accepted port therefore has, and what it does not.** It has the listener's `{mode, …}`
(seeded by `seed_inet_mode` before any record lands, so a listener whose mode came from
`open_port/2`'s own stream option is covered too — `PortRegistry::data_mode(listener, stream)`
resolves it) and every copied record above, on both the mirror and the **driver**. It does **not**
carry `{active, …}` (by design, Erlang re-applies it), the kernel `SO_*` state (the kernel's
`accept`), or `line_delim`. Proven end to end over a real loopback `accept(2)` by
`accept_inherit_tests.rs` (4 cases): the accepted port's `data_mode`, its mirror, and its **driver's**
`getopts` answers for packet/packet_size/header/mode all equal the listener's, its active counter is
**not** doubled, a real `{packet,2}` write is framed off the socket an un-inherited port would not
frame, a rejected record leaves the mirror untouched, and a poisoned replay closes the port and fails
the accept — with one case comparing against the live `erl` oracle's own
`inet:getopts(A,[packet,packet_size,header,mode])`.

**Two residuals, both typed, neither silent.**
(a) `PortRegistry::note_inet_setopts` has **no call site yet** — the hook belongs in
`src/port.rs::PortRegistry::port_control` (after the completion drain, on the driver's own reply), which
is the parent node's file; until it lands the mirror is fed only by the two test suites, which call
`note_inet_setopts` themselves with the same reply reading (`setopts_succeeded`). Adding the hook makes
those explicit calls redundant, and `accept_inherit_tests`'s `records().len() == 5` assertion would
surface a double-record immediately.
(b) There are **two** mode lookups — `PortMeta::data_mode` (in `active_input.rs`, body =
`PortMeta::stream`) and `PortRegistry::data_mode(id, fallback)` (the mirror) — and a payload renderer
must consult the second with the first as the fallback. One seam, two accessors: a caller that reads
the wrong one renders an `inet` list payload as a binary. `src/port.rs::make_stream_payload`'s callers
(`port_data_message_shaped`, `port_line_message`) are where the consolidation lands.
