# `beam_process` — Processes, Scheduler, Run Queues, Signals
## Intent
Owns the **OS-thread-level concurrency plumbing** of the Rust ERTS rewrite (Stage 5, Part II §H): the per-process control block (PCB), the four-level run queue, the cooperative scheduler loop, the **multi-scheduler (SMP) pool** (`SchedulerPool`: N scheduler threads over one shared table, per-scheduler run queues with work stealing, the `ThreadProgress` cross-scheduler barrier, the `TimerService` and two `DirtyPool`s), the **exit-signal / link / monitor** machinery (the decoupled per-process signal queue + its signal-message builders), the process table (`ptab`) with its local name registry, the **port-id table** and its ownership/link/monitor surface, and the local records for **remote (distributed) links/monitors**.
It is what makes Erlang **processes** real — isolation, `spawn`, links, monitors and exit propagation — the process half of workspace `../CONTEXT.md` §1 **A.1**.
It is consumed by `beam_bifs` (spawn/send/receive/`process_info`/`monitor`/`link` BIFs), `beam_io` (ports + the process side of I/O completion) and `beam_rt` (boot/CLI/`system_info`).
It **drives** `beam_gc` (collector + MSO) at safepoints and **uses** `beam_message` (`Queue` mailbox + `send`/`receive` copy engine) — it reimplements neither.
Legacy C ground truth (read-only `../../erts/emulator/beam/`; the Routing Table maps each to its module): `erl_process.{c,h}` (PCB/scheduler/run queues), `erl_proc_sig_queue.c`, `erl_monitor_link.c`, `erl_ptab.{c,h}`, `erl_process_dict.c`, `erl_vm.h` (`MAX_REG`/`MAX_ARG`), `erl_thr_progress.c`, `erl_hl_timer.c`, `erl_nfunc_sched.c`.
**Attribution boundary** (a C-deletion record must not attribute these here): the allocators (`erl_alloc*.c`, `erl_goodfit/bestfit/afit/ao_firstfit_alloc.c` → `beam_alloc`), the message copy engine (`erl_message.c`/`copy.c` → `beam_message`), crash dumping (`erl_process_dump.c`/`erl_crash_dump.c` → `beam_rt`'s `crash_dump.rs`); microstate accounting (`erl_msacc.c`) and flexible counters (`erl_flxctr.c`) are modelled by no crate (`beam_rt` lists the `mc_*`/`scheduler_wall_time` BIFs as a native gap); `erl_thr_queue.c`, `erl_sched_spec_pre_alloc.c`, `erl_process_lock.c` are unmodelled; time services (`time.c`/`erl_time_sup.c`) are `beam_bifs`'s time BIFs / `beam_rt`'s, and this crate's `timer.rs` is the `erl_hl_timer.c` analogue.
## Milestone-1 scope
Two scheduler fronts share the **same** slice logic — `scheduler::{slice_begin, slice_end}` (with `run_one` = both halves around one full-budget runner call) plus `drain_woken_into`: the single-threaded `Scheduler` loop (slice semantics frozen) and the SMP `SchedulerPool` (N threads over one shared table), so SMP adds *concurrency* and a bounded lock hold (one reduction **quantum**, `SchedulerConfig::set_lock_quantum`, default `DEFAULT_LOCK_QUANTUM = 256`), not a second scheduler.
"Correct" means the pid table, the four-level run-queue order, message delivery, the decoupled per-process signal queue, the monitor/registration surface, the process-dictionary and saved-argument sub-rootsets, the port ownership/link/monitor surface, remote links/monitors through the `DistSignalRouter` seam, and a safepoint GC over the process root set all match the C/oracle for the common cases and are test-covered; deliberate gaps are under Known Issues.

### Cross-module binding rules
- **Eager-vs-queued signalling (`ptab.rs`).** A signalling operation **enqueues** a `PendingSignal` on the receiver (copying the reason into its own heap) — never applies it inline; servicing happens at the receiver's schedule-in (`service_signals`, from `run_slice`) and **eagerly at the end of the sending operation** for a receiver that is *not* the currently `Running` process (ERTS's early signal handling): `apply_exit_signal`/`terminate`/`send_exit` share one rule — every receiver joins the service worklist unless `ProcessState::Running`. `apply_exit_signal` returns the `exit_policy`-predicted `ExitEffect` for a merely-queued signal. A **remote** (external-pid) or **port** signal bypasses the queue entirely (no `trap_exit` policy to defer), so `node_down`/`port_closed` materialise it straight into the mailbox.
- **Collect-then-apply worklist (`ptab.rs`).** `ProcessTable` is the single place that mutates ≥2 processes (the C ptab lock domain); its cross-process operations collect the intended effects into a worklist and apply it after the mutation pass. M1 is single-threaded, so the table holds `Process` values directly.
- **Split borrows (`process.rs`).** `heap_and_off_heap_mut()` (young heap + off-heap table, drives `beam_message::Fragments::move_into`) and `heap_and_mailbox_mut()` (young heap + mailbox, drives `beam_message::send_fragmented`) are the only two `*_mut` pairs with a real caller need; each destructures `self` into two disjoint `&mut` fields in safe Rust and **must not** be joined into one raw-pointer accessor.
- **Frozen field sets.** `Monitor`/`MonitoredBy`/`PortWatch` are constructed by struct literal from `beam_rt`, so no field may be added (the `monitor/3` user tag lives in a private `ProcessTable` side table instead); `Process`'s field shape and `ProcessExit<'a>`'s private-fields-plus-accessors shape are frozen the same way.
- **`DistSignalRouter` is OUTBOUND only** (local → remote); inbound decoded control messages belong to `beam_rt`.
- **`Message::from` must be an immediate** — a producer contract, reasoned in Known Issues below.
## Constraints
- **Errors:** `beam_common::{Result, BeamError}` only — never a crate-local error enum, never `panic!`/`unwrap()` on runtime data. Unknown pid/name/ref ⇒ `BeamError::TermNotFound`; a malformed pid term or out-of-range register index ⇒ `BeamError::BadArg`; pid/port space exhaustion ⇒ `BeamError::SystemLimit`; `beam_term::TermError` is reconciled upstream, so `?` crosses the boundary.
- **Heap exhaustion (`AllocKind::Heap`) is collect-grow-and-retry, not fatal OOM.** During a delivery **or a signal build** the receiver's nursery is collected, grown on demand, and the operation retried **once** (propagating the retry's own `BeamError::Alloc`) — the policy `Process::deliver` and the `ptab.rs` signal builders (through the shared `grow_receiver_for_signal`) implement. A **relocation-exempt** receiver cannot collect or grow **on demand** (the collect-then-grow `ensure_capacity` route; the no-relocation `grow_nursery` is unaffected by the flag), so an **apply-time** signal build (`build_signal_message`/`enqueue_fragment_signal`, via `deliver_head_signal`) puts its `{'EXIT',…}`/`{'DOWN',…}` in a `beam_message::HeapFragment` instead (no collection, no growth, no relocation — the C's model, `erl_proc_sig_queue.c`), while the **enqueue-time** reason copy (`copy_reason_onto`), which must land on the receiver's own heap, still surfaces the raw `AllocKind::Heap`/`Message` refusal; a collection/growth refused for an exempt process is the typed `relocation_exempt` raise. Because the nursery grows on demand, a refused delivery — the raw `AllocKind::Message` a caller's heap-fragment fallback keys on (`../beam_rt`'s `deliver_message`) — means the receiver's heap policy could NOT grow the nursery to fit the payload (e.g. a `max_heap_words` cap, or a collection that cannot make room); with an unbounded policy every payload is delivered into the grown young heap.
- **Inside `terminate_into` a per-peer signal-build (or `route`) failure is *not* propagated** — the process is already reclaimed, so it is logged via `beam_common::beam_error!` and the cascade continues.
- **`unsafe` is confined** to the modules that touch raw words: `signal.rs`/`monitor.rs` message builders and `remote.rs` (the external-pid thing via `beam_term`'s `unsafe` predicates, tuple/ref words via `beam_alloc::Heap::alloc_words`), plus `src/smp/mod.rs`'s two documented `unsafe impl Send`/`Sync for SharedProcessTable` — nothing else in the SMP pool. Every `unsafe fn` has a `# Safety` section and every `unsafe` block a preceding `// SAFETY:` rationale (`../beam_common/src/safety.rs`); `unsafe_op_in_unsafe_fn` stays clean. Safe Rust: `pid.rs`, `registers.rs`, `run_queue.rs`, `link.rs`, `monitor.rs` set logic, `ptab.rs` bookkeeping, `signal_queue.rs`, `port.rs`, `progress.rs`, and all of `smp/`'s `queues.rs`/`worker.rs`/`stats.rs`/`pool.rs` + `timer.rs`/`dirty.rs` (synchronisation via `parking_lot` mutexes/condvars + atomics).
- **Never assume a different term layout** — build/inspect terms only through `beam_term`'s public accessors + `beam_alloc::Heap`'s builders; pid/port immediates are bit-exact with `beam_term::immediate` (`make_internal_pid`/`pid_number`/`pid_serial`).
- **Reuse, do not reimplement:** the mailbox is `beam_message::Queue`; the copy engine is `beam_message::{send, receive, CopyContext}`; the heaps are `beam_gc::AnyCollector`/`beam_gc::HeapSpace`/`beam_alloc::Heap`; the off-heap objects are `beam_gc::MsoHandle`/`beam_message::OffHeapTable`.
- **Deps (fixed by `Cargo.toml`):** `beam_common`, `beam_term`, `beam_alloc`, `beam_gc`, `beam_message`, `libc`, `parking_lot`; adding a dependency edge requires reporting to `../`. `beam_engine` is **NOT** a dependency (the `ProcessRunner` trait keeps the DAG acyclic).
- Files target ~1000 lines, one responsibility per file, Apache-2.0. The `src/smp/*` files, `src/timer.rs` and `src/dirty.rs` are each well under that figure; `src/ptab.rs` (the table + signal hub) is the only file over it and deliberately stays whole because the signal/link/monitor servicing is tightly coupled to `ProcessTable`'s private fields (`slots`/`atoms`/`refs`/`ready`), which a sibling module cannot reach — a structural-debt candidate to extract if it grows further or field visibility widens.

## Known Issues (intentionally NOT covered in Milestone-1)
- **Reference aliases are unsupported on a port monitor and on a remote target.** `monitor(port, P, [{alias, _}])` and `monitor(process, RemotePid, [{alias, _}])` are typed `unsupported`s rather than accepted aliases: `alias_reply_delivered` holds no `&mut PortTable`, so a `reply_demonitor` port alias could not remove the port's incoming `PortMonitor`, and a later `port_closed` would deliver a `{'DOWN', …}` the oracle never does — a **wrong result**, so it is refused instead (reason string `error::unsupported_port_monitor_alias()`, mirroring the pre-existing remote-tag diagnostic). No OTP caller combines either.
- **The `{tag, Tag}` monitor option accepts only an immediate.** The oracle accepts any term; this crate refuses a non-immediate tag with a typed `unsupported`, because a tag lives in the `tags: HashMap<MonitorRef, Eterm>` side table, which is **not** a GC root — a per-process-heap tag could not be relocated and would dangle after a collection. Making it faithful needs a gather/scatter of the tag table in the collection walk. (The `aliases` side table is the same concern but its entries are plain values — no term — so it needs no rooting.)
- **The `from`/`token` envelope roots are gathered and relocated, but no in-tree producer enqueues a heap word there yet.** `beam_message::Queue::enqueue`'s debug `debug_assert_enqueue_terms` tripwire still rejects a non-immediate `from`/`token`, so a host storing a heap word (the C permits a heap `token` tuple, `erl_message.c:388-390`, and a heap Info-tuple `from`, `erl_proc_sig_queue.c:2272`) must (a) opt into the gather — done: `run_rooted_collection` pushes `Message::from`/`token` and scatters them back through `set_from`/`set_token` — **and** (b) deliberately relax that tripwire in the sibling `beam_message`, which has not happened. Until then every envelope word stays an immediate and this rooting is defensive.
- **A host holding unpublished live roots is why the relocation exemption exists — and the `beam_rt` defect it mitigates is owned there.** `Process::deliver`'s on-exhaustion collect relocates the young heap against the crate root set only (registers/stack + mailbox payloads + dict + saved args + pending signals), so a host holding live terms from that heap in Rust locals / nested-`Machine` registers (the `-eval` evaluator environment; a nested `Machine` from `RuntimeContext::run_export`) can see a recycled word — the `beam_rt` WRONG-RESULT defect reproduced by three sequential `io:scan_erl_exprs/4` calls then reading the FIRST result. This crate provides the **fix seam** (`set_relocation_exempt(true)` makes `deliver` surface the raw refusal and `collect`/`ensure_capacity` refuse); **adoption is `beam_rt`'s** — it must mark the affected process from its own GC valve and fall back to its fragment path (`RuntimeContext::deliver_message` → `send_fragmented_message`); until then, the defect stands. Full mechanism/repro in `../beam_rt/M1_GAPS.md`.
- **Multi-scheduler / SMP (remaining gaps)**: lock-free/threaded run queues, scheduler **balancing**, and the `+S`/`+SDcpu`/`+SDio` flag parsing are not modelled. The table lock is narrower (one reduction quantum, not a slice) but still exclusive, so a process **does not run in parallel** across schedulers (exactly one executes at a time). Dirty-job **term plumbing** is absent (a `DirtyJob` carries no live heap data) and a timer message must be thread-valid (no heap-resident terms). `ThreadProgress` implements the barrier but has **no** delayed-dealloc coupling with `beam_alloc`, and **port tasks are not load-balanced** across schedulers.
- **The signal queue is not cross-ordered with the mailbox.** A trapped `{'EXIT', …}`/`{'DOWN', …}` becomes a mailbox message only when the queued signal is *applied*, so an ordinary send already queued can be seen before it; remote (external-pid) and port signals bypass the queue entirely. The C's per-*sender* signal-queue granularity and the signal-vs-message ordering barrier remain follow-ups. The queue itself is unbounded (a `VecDeque`, matching the oracle's effectively-unbounded signal queue) with total, defensive GC gather/scatter — no overflow or panic path.
- **Off-heap refc-binary reclamation is caller-declared only — no automatic liveness scan (owner: `beam_gc` for a public scan-driven predicate, `beam_rt` to drive it).** `Process` owns the binaries it registers (`owned_binaries`) and **sweeps** them on the process path (`run_rooted_collection`'s last step + `sweep_off_heap_binaries()`) with a deliberately **conservative** predicate: release only when the caller asserts the death (`declare_off_heap_binary_dead`). A faithful liveness walk would need the heap's nested on-heap `BinRef`/`ErlSubBits` containers, and that walk (`beam_gc`'s `copy::move_size`/`for_each_ref` via `live.rs`) is `pub(crate)` to `beam_gc`; a shallow raw-word scan from here would be **unsound** (a `BinRef` may live in the mature space, a message's `Fragments`, or another off-heap payload). Consequences, all leak-not-dangle: an undeclared payload stays owned until the process dies (its `Drop` frees it at reference count 0); an off-heap binary arriving via the **copy engine** is owned by the `Message`/`OffHeapTable`, not `owned_binaries`, so nothing auto-registers it; and a relocation-exempt process never collects, so its declared deaths await an explicit sweep. `retain_off_heap_binaries` is the seam for whoever can walk the heap. Evidence: `tests/off_heap_binaries.rs`; rationale in `DESIGN_DECISIONS.md`.
- **`Message::from` is NOT a GC root — every producer must store an immediate.** `Process::run_rooted_collection` gathers only each queued message's `payload`/`from`/`token` and re-installs the envelope around the relocated payload, so a producer must keep `from` an **immediate**, matching the C's `ASSERT(is_immed(ERL_MESSAGE_FROM(msg)))` (`erl_proc_sig_queue.c:8441`), where the `{Name,node}` pair / external pid live in the message **body** instead. Every in-crate producer does: the send paths store the sender pid immediate; a process-monitor `'DOWN'` the resolved target pid immediate (`deliver_down_message`); a **failed-by-name** named monitor the `system` atom (`deliver_named_noproc_down`, the C's `am_system`); the port builders the port immediate; the **remote** DOWN/EXIT the **node atom** (`enqueue_remote_down_message`/`enqueue_remote_exit_message`, the C's DIST_PROC/DIST_PORT rule). `tests/message_from_is_immediate.rs` pins each. Residual (host contract): a caller handing `Process::deliver` an on-heap `from` gets no relocation — the hardening (a `beam_message::Message` `from` setter + gathering `from` in the root set) belongs to the sibling `beam_message`/host.
- **`Process::exit_reason` is not gathered, but is unreachable by a collection (audited).** It is written only in `terminate_into` (`src/ptab.rs`), immediately **after** `take(pid)` and before the PCB drop, and read only through `ProcessTable::exit_reason` — which needs a live pid `take` has already removed — so no collection can invalidate it. Caveat: a future change that reads it post-collection or re-inserts a terminated PCB would need it rooted. (Divergence from the C, which keeps a dead pid's exit reason observable via `process_info`; here `exit_reason` answers `TermNotFound`.)
- **`Message::token` has no producer in this crate** (always `NIL`) and is likewise not gathered — a future `with_token` of an on-heap term would hit the same class as `from`.
- **The `noproc` DOWN is delivered eagerly (documented deviation).** `monitor/2` on a non-live target materialises `{'DOWN', Ref, process, Target, noproc}` straight into the watcher's mailbox, so `process_info(self(), message_queue_len)` reports 1 right after the call where the oracle reports 0 (it defers the DOWN as a signal and reveals it at the next `receive`). The divergence is against **ordinary messages** too: the crate always reports the DOWN before a later send, whereas the oracle typically reports the send first (its own order is timing-dependent). A born-down also records **no** local monitor entry, so `demonitor(Ref, [info])` answers `false` where the oracle (itself racy here) answers `true`. Deferring would be *wrong* until the runtime services pending signals on entering `receive` (the workaround `beam_rt` already applies to self-directed `exit/2`), so eagerness is deliberate: the receive-visible result and the order against later DOWNs both match the oracle. Servicing `service_signals` at the receive point would make it exact.
- **Priority run queues**: port tasks, and the C's shared NORMAL/LOW physical queue `schedule_count`/`RESCHEDULE_LOW` fairness deferral (this crate uses four physically distinct FIFOs — see `run_queue.rs`), are follow-ups. `Scheduler::set_priority`/`SchedulerPool::set_priority` DO requeue an already-queued process. The `save_calls` *effect* (saving the last `N` calls for `seq_trace`/`dbg`) is not modelled — only the `process_flag(save_calls, N)` value contract.
- **Pre-emption is produced by `beam_rt`'s runner.** `beam_rt::RuntimeRunner::run` honours its `budget` (charged at the machine's heap-admission points through `beam_rt/src/runner/budget.rs`) and returns `RunOutcome::Yield`, parking the process at the exact instruction — `beam_rt/tests/preempt.rs` pins the resulting interleaving. The crate-level contract is unchanged: the scheduler never pre-empts, so a runner that ignored its budget and never yielded would still run to completion in one call (the scheduler half is pinned by `tests/preemption.rs`).
- **Process-dictionary interior and heap fragments.** The dictionary is modelled as a flat key/value list (no hash-array interior), and `erlang:process_info/1`'s view of it is still absent. Saved args are a plain `Eterm` root list and `Process::deliver` fits a message into the receiver's own young heap, growing that heap on demand (collect + grow + retry once — the Constraints policy) rather than falling back to a fragment; the one fragment-resident case is an **apply-time** signal build for a **relocation-exempt** receiver (its own suite, `tests/signal_fragment_fallback.rs`). `tests/signal_exhaustion.rs` covers the collect-grow-and-retry path and the raw `AllocKind::Heap`/`Message` refusal an exempt receiver still meets on the **enqueue-time** reason copy.
- **Distribution-wide links/monitors**: external pids are decomposed into a `remote::RemotePid` and recorded (`remote_links`/`remote_monitors`), and every relationship change routes through the `remote::DistSignalRouter` trait seam (implemented downstream over `beam_dist`; no crate dependency). **Inbound** decoded control messages (`DOP_LINK`/`DOP_MONITOR_P`/`DOP_EXIT`/`DOP_EXIT2`) are **not** yet fed into the table — that interpreter and the `DistSignal`→`Dop` adapter belong to `beam_rt` (a documented handoff); with no router the table is record-only (`has_dist_router()`). The outbound `DistSignal` keeps the link exit (`Exit` → `DOP_EXIT`) and `erlang:exit/2` (`Exit2` → `DOP_EXIT2`) distinct.
- **Port lifecycle driving** — port scheduling, port signals and the port's read path — remains `beam_io`'s; `PortTable` owns only the id plus the ownership/links/monitors, and `ProcessTable::port_closed` delivers the closing port's messages.
- **Port-monitor cleanup on death needs a `PortTable` handle; the `Scheduler` adopts one.** `terminate_into` always drains `Process::port_monitors` (and the exit observer always sees them), but the matching *incoming* `PortMonitor` entries leave the `PortTable` only when a handle is supplied. A `Scheduler` built with `with_ports`/`set_ports` owns one, so its default `run_slice`/`run_ready` service signals through `service_signals_with_ports` and terminate through `terminate_with_ports` — a process dying in a slice cleans its dangling incoming `PortMonitor` (`tests/scheduler_ports.rs`). A scheduler built with `new`/`with_slice` owns none and keeps the port-less behaviour (outgoing watches drained, incoming left in place); the explicit `run_slice_with_ports`/`run_ready_with_ports` override the owned table for one call. The port-less `ProcessTable` entry points (`terminate`, `service_signals`, `apply_exit_signal`/`send_exit` (`erlang:exit/2`), `node_down`) pass no ports, so a process killed through one leaves its incoming `PortMonitor` until the owner runs `service_signals_with_ports` at the peer's next schedule-in. The SMP pool is port-less — a table there would add a **fourth lock family** to the BINDING discipline in `src/smp/CONTEXT.md`, so it is deferred (the pool has no production consumer).
- **Exact exit-reason term from `beam_common::ExitReason`**: signal reasons are carried as live `Eterm` terms (the deliverable form), not the term-independent `beam_common::ExitReason`; the mapping between them belongs to the raising BIF layer (`beam_bifs`).
- **`process_info` source data.** Every item this crate can answer is backed by a public accessor (`tests/process_info_source.rs` pins the mapping): `status` → `Process::status()`, `registered_name` → `ProcessTable::name_of(pid)`, `message_queue_len` → `Process::mailbox().len()`, `links` → `Process::links().iter()`, `monitors` → `Process::monitors().iter()` (+ `port_monitors()` for the `{port, Port}` entries), `monitored_by` → `Process::monitored_by()`, `trap_exit` → `Process::is_trapping_exit()`, `priority` → `Process::priority()`, `reductions` → `Process::reductions()`. Still absent: `current_function`/`current_location` (nothing tracks the running MFA) and the `erlang:process_info/1` whole-dictionary view.
- **Monitor semantics not modelled.** `MonitorKind` has no `TimeOffset` variant (`erlang:monitor(time_offset, _)` is the oracle's `badarg`, raised by the BIF layer); `erlang:monitor_node/2,3` is **out of scope** — node-level distribution needing a local node identity plus an inbound `DOP_*` path, neither owned here; and a **named** port monitor (`monitor(port, Name)`) is a typed `unsupported` (the name registry resolves names to processes only, so a process monitor would be a wrong result). `erlang:monitor/2` on a non-live target yields the oracle's `noproc`; only its **timing** deviates (the DOWN is delivered eagerly — see above). `erlang:monitor/3`'s `{tag, T}` form **is** implemented for an **immediate** `T` on process **and** port targets (the tag lives in the `tags` side table); the remaining gap is a **non-immediate** tag and a tag on a **remote** external-pid target (both typed `unsupported`). The tag-less `monitor/2` form is complete.
- **`process_flag` coverage gap (owner: `beam_rt`/`beam_gc`).** `beam_rt`'s `ProcessBridge::process_flag` answers `badarg` for every flag except `trap_exit`/`sensitive`/`priority`/`save_calls`/`error_handler`, where the oracle returns the **previous value** for `max_heap_size`/`min_heap_size`/`min_bin_vheap_size`/`fullsweep_after`/`message_queue_data`. `Process` has no `max_heap_size` storage and `beam_gc::AnyCollector` exposes only `policy()` (no `policy_mut`), so the setter and the kill/log enforcement are a `beam_rt`+`beam_gc` handoff. No `max_heap_size` enforcement exists in this crate.
- **`spawn_opt` option validation gap (owner: `beam_rt`/`beam_gc`).** `{max_heap_size, N}` with `N != 0` and `N < min_heap_size` is accepted where the oracle is `badarg` (the C `erl_process.c`'s `max_heap_size < min_heap_size ⇒ -1`); and `process_info(P, message_queue_data)` reports `on_heap` regardless of a `{message_queue_data, off_heap}` spawn option.
- **`port_info` item gap (owner: `beam_bifs`/`beam_rt`).** `port_info(P, queue_size)` and `port_info(P, locking)` are `badarg` where the oracle answers `{queue_size, 0}` / `{locking, port_level}`; the 7-item `port_info/1` roster and order already match.
- **The compatibility gate is green.** `tools/differential/gate.sh --strict --allowlist tools/differential/known-gaps.txt` (a sibling, read-only here) reports `total=1328 agree=1327 mismatch=0 unsupported=1 skipped=0 allowed=1 unauthorized=0 stale=0` (exit 0). The single allowlisted gap is `wire/new_fun_ext_encode` (A.5, unclosable by design — an `erl_eval` template closure). Re-run `gate.sh` for the live figure.
