# `beam_process` — Handoffs (owned by sibling nodes, NOT yet adopted)

## Intent
The complete, current-state list of coordination items between `beam_process` and the nodes that consume it, kept here in full so a host can adopt a seam without re-deriving it from this crate's source.
`CONTEXT.md`'s `## Handoffs` section carries the same list in summary and a pointer here.
Each bullet names the owning node, the entry points to call and their preconditions.
Nothing here is done yet: an item listed below is outstanding, and the crate-side half it depends on is named in the bullet.

## Bullets
- **The inbound `DOP_SPAWN_REQUEST` path reserves, then spawns, then replies (owner: `beam_rt`).** `beam_rt/src/dist/inbound.rs`'s `Delivery::SpawnRequest` arm is `DeliveryOutcome::Unsupported`; it becomes, in order: decode `{reference, from, group_leader, mfa, opts, token}` and validate shape + parse `opts` **first** (a parse failure replies `{spawn_reply, Ref, To, 0, badopt}` for `opts_error == 1`, drops the connection as `invalid_message` for `> 1`/bad arity, and commits nothing — no reservation is taken yet); `ProcessTable::reserve_remote(RemotePid…)` (mapping `BadArg` ⇒ a `spawn_reply` carrying `badarg`, `SystemLimit` ⇒ one carrying `system_limit`, `dist.c:3020-3023`); on abandonment `ProcessTable::cancel_reservation`; `ProcessTable::spawn_reserved(reservation, HeapPolicy…)` (which already rolls the claim back on its own failure, so do **not** cancel again), then install the host's `ProcessEntry` keyed by the returned pid — exactly as for `spawn`, which is why the signature carries no entry — and send `{spawn_reply, Ref, To, Flags, pid.to_eterm()}` (`dist.c:1882-1900`). The crate-side reservation API is in place (`reserve_remote`/`reserve_identity`/`spawn_reserved`/`cancel_reservation`, `src/ptab.rs`), and so is its prerequisite: `Runtime::new` installs `ProcessTable::set_local_node` (`beam_rt/src/runtime.rs`, the configured `node@host` or `nonode@nohost`), which is what `reserve_remote` verifies the identity's node against. Residuals **not** closable in `beam_rt`: the `DOP_SPAWN_REPLY` emission and receipt arms (`beam_dist`'s `Dop`), the reply's link/monitor flags, the C's `dist_spawn_init` MFA indirection, `spawn_request_abandon`, and the seq-trace `token`.
- **`beam_message` should relax the enqueue tripwire (owner: `beam_message`).** `Queue::enqueue`'s debug `debug_assert_enqueue_terms` rejects a non-immediate `from`/`token`, so a future host storing a heap word there (the C permits a heap `token` tuple, `erl_message.c:388-390`, and a heap Info-tuple `from`, `erl_proc_sig_queue.c:2272`) must relax it in the sibling crate. The `beam_process` half is already in place: `Process::run_rooted_collection` gathers `Message::from`/`token` and scatters them back through `set_from`/`set_token`.
- **`ProcessId::to_eterm` is the crate's one unchecked narrowing (owners: `beam_process` + `beam_term`).** `src/pid.rs`'s `to_eterm` is an infallible `const fn` built on `beam_term::immediate::make_pid_data`, which does not range-check (it mirrors the C macro, `erl_term.h:655-656`) — so an out-of-range `(number, serial)` is a `debug_assert` panic in test builds and the C's own carry-into-the-serial term in release. Unreachable in-tree: `ProcessTable` bounds every pid it mints at `MAX_PROCESS_NUMBER` (= `beam_term`'s `MAX_INTERNAL_PID_NUMBER`) and every decode (`from_eterm`) is already in range. The checked encoder exists (`beam_term::immediate::try_make_pid_data`, the C's `ERTS_MAX_INTERNAL_PID_*` call-site check); closing the gap means either a fallible `to_eterm` — a signature change rippling through every caller, `beam_rt` included — or a validated constructor beside the total one, which is a cross-crate decision rather than a local edit.
