# `beam_process` — Handoffs (owned by sibling nodes, NOT yet adopted)

## Intent
The complete, current-state list of coordination items between `beam_process` and the nodes that consume it, kept here in full so a host can adopt a seam without re-deriving it from this crate's source.
`CONTEXT.md`'s `## Handoffs` section carries the summary, the two newest entries and a pointer here.
Each bullet names the owning node, the entry points to call and their preconditions.
Nothing here is done yet: an item listed below is outstanding, and the crate-side half it depends on is named in the bullet.
The newest entries are the reference-id-space adoption (a fresh `RefAllocator` is no longer an odometer), the receive-scan switch (`ProcessTable::service_receive_signals` replacing `beam_rt`'s `only_down_signals` gate) and the inbound `DOP_SPAWN_REQUEST` reserve/spawn/reply path (whose prerequisite is installing the table's local node).

## Bullets
- **The reference-id space is one shared source; stop walking a fresh `RefAllocator` as an odometer (owner: `beam_rt`, with `beam_bifs`).** `beam_process::RefAllocator` is now a **zero-sized handle** onto `beam_common::next_ref_id()` — the one process-wide local reference-id space shared with `erlang:make_ref/0`, the NIF `make_ref`, the timers, `seq_trace` and NIF resource terms — so it holds **no counter of its own** and two producers can never issue the same reference id (`tests/reference_ids.rs` pins the source exactly and the absence of a collision). Two sibling call sites still assume the old per-instance `0, 1, 2, …` counter and must be rewritten: (1) `beam_rt/src/context/tests.rs::force_next_reference_id` advances a fresh `RefAllocator` `id` times so the runtime's next draw lands on `id` — impossible now; its test `resolve_send_target_rejects_a_bare_reference_that_collides_with_a_live_alias` should instead assert that a bare `make_ref/0` and a live alias **cannot** share an id (the provenance check it guards stays necessary for a *foreign* id, but the coincidence itself is unreachable); (2) `beam_rt/src/runtime/ets_owner.rs::tid_ref_thing` reaches a table `handle` by drawing `handle + 1` times — now it mints an unrelated id, so the tid no longer decodes back to the handle (see its test `the_tid_substitution_lands_on_the_handle_id`, and `beam_rt/tests/ets_owner.rs`'s unnamed-transfer flow). The minimal fix is an explicit-id mint for a term that is *not* an identity (`MonitorRef` has no public `from_id`, exactly as that file's docs record; a public `MonitorRef::from_id(u64)` or a `pub` `beam_bifs::access::make_ref_thing` would remove the loop — both are cross-crate additive changes). Mirror-point for the other producers: `beam_abi`'s resource mint and any other `AtomicU64`/`AtomicUsize` id space in `beam_rt`/`beam_bifs` should draw from `beam_common::next_ref_id()`.
- **`beam_rt` must drain the `max_heap_size` verdict and own the observable kill/log.** The policy itself (setting, flags, accounting, verdict) lives here (`src/max_heap.rs` + `Process::{set_max_heap_size,max_heap_size,max_heap_usage,heap_limit_verdict,current_heap_limit_verdict,max_heap_verdict,take_max_heap_verdict}`); what remains on the host side is (a) installing the setting on the PCB from `erlang:process_flag(max_heap_size, …)` and `spawn_opt`'s `{max_heap_size, Map}` (the parse and the `size < min_heap_size` `badarg` floor stay there, `MaxHeapSetting::violates_floor` single-sourcing the rule), (b) draining `Process::take_max_heap_verdict` after a collection or a heap admission, (c) performing `HeapLimitVerdict::Kill` as `ProcessTable::terminate(pid, <interned atom `killed`>)` — a self-exit with the bare atom `killed`, never `kill` and never an exception — and `HeapLimitVerdict::Log` as the `=ERROR REPORT====` with `Context: maximum heap size reached`, and (d) at the admission doors that know the capacity they are about to install (`beam_rt/src/context/gc.rs::{ensure_heap_full, alloc_words, alloc_words_rooted}`, `runtime/gc.rs::serve_gc_request`, `runner/budget.rs`), consulting the prospective form `Process::heap_limit_verdict(prospective_words)`, because a current-size-only check grazes below the limit and never fires. It must also **delete** its duplicate `beam_rt::config::{MaxHeapFlags, MaxHeapSetting}` and re-export ours (identical names and field names, so the deletion is a pure move), keeping or moving `Runtime::max_heap` as it chooses.
- **Two sibling instances of the unchecked narrowings this crate no longer has.** `beam_rt/src/dist_client.rs` encodes a remote reference id with `make_small(next_id as i64)`, and `beam_term::immediate::make_pid_data` (behind the infallible `ProcessId::to_eterm`) is unchecked and unmasked — unreachable in-tree because the ptab bounds a process number at `MAX_PROCESS_NUMBER`, but both want the checked `try_make_small` + `SystemLimit` shape `MonitorRef::to_eterm` uses. Owners: `beam_rt` and `beam_term` respectively.
- **`beam_message` should relax the enqueue tripwire** if a future host stores a heap `from`/`token`
  (see Known Issues); the `beam_process` gather/scatter side is already in place.
- **The relocation exemption has two deliberate uses (owner: `beam_rt`):** the host's send-path `deliver_message` fallback (first), and this crate's signal fallback (second) — an exempt receiver's `{'DOWN',…}` and a **trapping** exempt receiver's `{'EXIT',…}` already land in a `beam_message::HeapFragment` whether the refusal came from the apply-time message build or from the enqueue-time reason copy, so the host need not invent one. (An exit signal to a **non-trapping** exempt receiver stays a surfaced refusal — the receiver would have to *terminate*, which is the caller's cascade, not a message.)
- **`beam_rt` installs the `CollectionGate`.** `Runtime::new` wraps its unscanned-root valve (`src/context/gc.rs::root_is_unscanned` + `src/context/gc_walk.rs::any_root_is_unscanned`) in `context/gc_walk.rs::RuntimeCollectionGate` and installs it with `ProcessTable::set_collection_gate` (`beam_rt/src/runtime.rs:730`), so the seam is live and every signal site plus `ProcessTable::deliver` decides identically to the host's heap-admission points. In addition, `beam_rt`'s park-window `relocation_exempt` exemption (`beam_rt/src/runner/run.rs`) covers a term the walk cannot see (a live term the host holds outside the gathered roots).
- **The receive scan should call `service_receive_signals`, not `service_signals`.** `beam_rt/src/context/execution.rs`'s `receive_next` currently gates on "every pending signal is a `PendingSignal::Down`" and then calls `service_signals`; that gate exists only because `service_signals` applies the whole queue and can *terminate* the process from inside its own instruction stream. `ProcessTable::service_receive_signals` is that seam: drop the `only_down_signals` gate, keep a non-empty check (the borrow must be dropped before servicing), call `service_receive_signals(pid)?`, re-read the scan, and let a **stopping** (terminating) head end in `Ok(None)` so the runner parks and its schedule-out net re-queues (the next schedule-in's `service_signals` then applies the terminating signal and cascades). With the gate gone `PendingSignal` is likely unused in that file (drop the import). This is what closes the one-round-late trapped `{'EXIT',…}` / mixed exit+DOWN queue.
- **The inbound `DOP_SPAWN_REQUEST` path reserves, then spawns, then replies.** `beam_rt/src/dist/inbound.rs`'s `Delivery::SpawnRequest` arm (today `DeliveryOutcome::Unsupported`) becomes, in order: decode `{reference, from, group_leader, mfa, opts, token}` and validate shape + parse `opts` **first** (a parse failure replies `{spawn_reply, Ref, To, 0, badopt}` for `opts_error == 1`, drops the connection as `invalid_message` for `> 1`/bad arity, and commits nothing — no reservation is taken yet); `ProcessTable::reserve_remote(RemotePid…)` (mapping `BadArg` ⇒ a `spawn_reply` carrying `badarg`, `SystemLimit` ⇒ one carrying `system_limit`, `dist.c:3020-3023`); on abandonment `cancel_reservation`; `ProcessTable::spawn_reserved(reservation, HeapPolicy…)` (which already rolls the claim back on its own failure, so do **not** cancel again), then install the host's `ProcessEntry` keyed by the returned pid — exactly as for `spawn`, which is why the signature carries no entry — and send `{spawn_reply, Ref, To, Flags, pid.to_eterm()}` (`dist.c:1882-1900`). **Prerequisite:** `reserve_remote` refuses an uninstalled local node (`badarg`) because it cannot verify the identity's node, and `Runtime` never calls `ProcessTable::set_local_node` today — the boot path must install it (as the `monitor/2` name-target path already requires); a caller holding only a `ProcessId` uses the node-less `reserve_identity` instead. Residuals **not** closable here (they live in `beam_rt`/`beam_dist`): the `DOP_SPAWN_REPLY` emission and receipt arms (`beam_dist`'s `Dop`), the reply's link/monitor flags, the C's `dist_spawn_init` MFA indirection, `spawn_request_abandon`, and the seq-trace `token`.
