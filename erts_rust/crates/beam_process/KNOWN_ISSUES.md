# `beam_process` — Known Issues (current state)

## Intent
The complete, current-state list of gaps and deliberate deviations `beam_process` ships with, kept here in full so every bullet's C file:line citation and test pin stays readable in one place.
`CONTEXT.md`'s `## Known Issues` section carries the summary and a pointer here.
Each bullet names the scope, the owner where the fix lives in another node, the refusal it raises (a typed `unsupported`/`badarg`/`relocation_exempt` raise, never a wrong result) and the C file:line / test pins that hold it.
Nothing here is aspirational or historical: every entry describes how the code behaves today.
The bullets keep their original order; where one says "above", it means an earlier bullet in this file, and where it points at "the primitives above" or at a frozen seam, that seam is described in `CONTEXT.md`'s API Surface / cross-module binding rules.

## Bullets
- **Reference aliases are unsupported on a port monitor and on a remote target.** `monitor(port, P, [{alias, _}])` and `monitor(process, RemotePid, [{alias, _}])` are typed `unsupported`s rather than accepted aliases: `alias_reply_delivered` holds no `&mut PortTable`, so a `reply_demonitor` port alias could not remove the port's incoming `PortMonitor`, and a later `port_closed` would deliver a `{'DOWN', …}` the oracle never does — a **wrong result**, so it is refused instead (reason string `error::unsupported_port_monitor_alias()`, mirroring the pre-existing remote-tag diagnostic). No OTP caller combines either.
- **The `{tag, Tag}` monitor option refuses a heap-resident tag (an immediate or a literal-area term is accepted).** The tag lives in the `ProcessTable::tags` side table, which is **not** a GC root, so a per-process-heap term could not be relocated and would dangle after a collection — a **wrong result**, so `check_tag` refuses it with the typed `error::unsupported_tag` rather than storing it; the oracle accepts any term. Accepted: an **immediate** and a **literal-area** term (`is_immediate(t) || ((is_boxed_term(t) || is_list(t)) && is_literal(t))` — a `TAG_LITERAL_PTR` bit test, meaningful only on a BOXED/LIST word, so it is guarded by the pointer-tag test that only a literal arena's tagging walk sets). No OTP caller passes a heap tag. Closing the gap needs the tag deep-copied into a table-owned store instead of a raw heap `Eterm`. A tag on a **remote** external-pid target stays a typed `unsupported` (no wire field).
- **The `from`/`token` envelope roots are gathered and relocated, but no in-tree producer enqueues a heap word there yet.** `beam_message::Queue::enqueue`'s debug `debug_assert_enqueue_terms` tripwire still rejects a non-immediate `from`/`token`, so a host storing a heap word (the C permits a heap `token` tuple, `erl_message.c:388-390`, and a heap Info-tuple `from`, `erl_proc_sig_queue.c:2272`) must (a) opt into the gather — done: `run_rooted_collection` pushes `Message::from`/`token` and scatters them back through `set_from`/`set_token` — **and** (b) deliberately relax that tripwire in the sibling `beam_message`, which has not happened. Until then every envelope word stays an immediate and this rooting is defensive.
- **A host holding unpublished live roots is why the delivery gate exists.** `Process::deliver`'s on-exhaustion collect relocates the young heap against the crate root set only (registers/stack + mailbox payloads + dict + saved args + pending signals), so a host holding live terms from that heap in Rust locals / nested-`Machine` registers (the `-eval` evaluator environment; a nested `Machine` from `RuntimeContext::run_export`) must not have the heap move under it. Two conditions mark such a receiver — together the crate-owned `has_unpublished_roots`: the per-process **relocation-exempt** flag (`set_relocation_exempt(true)` makes `deliver` surface the raw refusal and `collect`/`ensure_capacity` refuse), which the host asserts, and the **`Running`** state, which the crate derives for the process its own engine is executing. `beam_rt` **adopts** the exempt half — it runs the `-eval` driver and the nested-`Machine` scopes under `RuntimeContext::with_relocation_exempt` and exempts the sending context's own pid on the send path (`deliver_message_with_off_heap`), routing a refused delivery to its fragment fallback (`RuntimeContext::deliver_message` → `send_fragmented_message`) — so the `-eval` held-result case agrees with the oracle (`beam_rt/tests/io_scan.rs::a_scan_result_held_across_later_requests_matches_the_live_oracle`). Setting the exempt flag remains a host responsibility (only the host can assert that a process's root set is unpublished); the `Running` half needs no host marking. The host's **`CollectionGate`** is the same policy's third case — a predicate the host installs (`ProcessTable::set_collection_gate`) to decline a relocating collection for a receiver whose live root set is **not** fully scanned by its collector; a decline refuses the relocation only, so the notification is still delivered fragment-resident. Full mechanism and the residual hazards outside this gate: `../beam_rt/M1_GAPS.md`.
- **Multi-scheduler / SMP (remaining gaps)**: lock-free/threaded run queues and the `+S`/`+SDcpu`/`+SDio` flag parsing are not modelled, and work stealing is **opportunistic** — `smp/worker.rs`'s `acquire` steals half a peer's queue round-robin, but a worker parked on its own queue is never woken by a peer's arrival (`src/smp/CONTEXT.md`), so nothing balances a parked worker toward new work. The table lock is narrower (one reduction quantum, not a slice) but still exclusive, so a process **does not run in parallel** across schedulers (exactly one executes at a time). Dirty-job **term plumbing** is absent (a `DirtyJob` carries no live heap data) and a timer message must be thread-valid (no heap-resident terms). `ThreadProgress` implements the barrier but has **no** delayed-dealloc coupling with `beam_alloc`, and **port tasks are not load-balanced** across schedulers.
- **The signal queue is not cross-ordered with the mailbox.** A trapped `{'EXIT', …}`/`{'DOWN', …}` becomes a mailbox message only when the queued signal is *applied*, so an ordinary send already queued can be seen before it; remote (external-pid) and port signals bypass the queue entirely. The C's per-*sender* signal-queue granularity and the signal-vs-message ordering barrier remain follow-ups. The queue itself is unbounded (a `VecDeque`, matching the oracle's effectively-unbounded signal queue) with total, defensive GC gather/scatter — no overflow or panic path.
- **Off-heap refc-binary reclamation is reachability-driven, with two residual gaps.** A process's **own** owned list (`owned_binaries`) is reclaimed automatically by the **reachability** sweep (`sweep_off_heap_binaries_reachable`), the crate half of the automatic liveness decision: `run_rooted_collection` runs it (through `sweep_off_heap_binaries_reachable_from`, over the roots it just gathered) as the **first** half of its off-heap step, so a payload no reachable on-heap `BinRef` names is released — using `beam_gc::AnyCollector::for_each_reachable_object_view`, the public/safe/read-only/whole-heap walk, whose reachable `HEADER_BIN_REF` objects name their payload at `BinRef` word 1 (the frozen `BinRef.val` contract, `RefcBinary::data_ptr()`), read through the safe `ReachableObject::word` accessor. The **conservative** declared-dead sweep (`sweep_off_heap_binaries`, releasing only a caller's asserted `declare_off_heap_binary_dead`) always runs as the **second** half, so a declared death is honoured whether or not the reachability half was sound. Evidence: `tests/off_heap_binaries.rs`, `tests/off_heap_reachability.rs`; rationale in `DESIGN_DECISIONS.md`. Two gaps remain: (1) an off-heap binary arriving via the **copy engine** is owned by the `Message`/`OffHeapTable`, not `owned_binaries`, so nothing auto-registers it — only the process's own registrations are swept; (2) a process with **unpublished roots** — relocation-exempt, or currently `Running` — is **retained entirely** by the reachability sweep (its **decline valve**: `sweep_off_heap_binaries_reachable` returns `Ok(0)` and retains everything), because its root set is incomplete and a missed live `BinRef` would release a live payload (a dangle); only the conservative declared-dead path (or a later non-declined collection) reclaims such a process's payloads. Registration into that list is **O(1) amortized**: `owned_binary_index: HashMap<usize, usize>` maps each live payload's `data_ptr` to its slot, so `register_off_heap_binary`'s dedup is a single lookup (never a scan over the slot space), and the index is pruned of every payload a sweep releases — `retain_off_heap_binaries` is the one release funnel both sweeps go through — so a released slot can never resolve and a re-registration takes a fresh slot (`off_heap_binary_registration_work_is_independent_of_slot_count` / `off_heap_binary_release_prunes_the_index_and_a_fresh_registration_gets_a_new_slot` pin both halves).
- **`Message::from` is NOT a GC root — every producer must store an immediate.** `Process::run_rooted_collection` gathers only each queued message's `payload`/`from`/`token` and re-installs the envelope around the relocated payload, so a producer must keep `from` an **immediate**, matching the C's `ASSERT(is_immed(ERL_MESSAGE_FROM(msg)))` (`erl_proc_sig_queue.c:8441`), where the `{Name,node}` pair / external pid live in the message **body** instead. Every in-crate producer does: the send paths store the sender pid immediate; a process-monitor `'DOWN'` the resolved target pid immediate (`deliver_down_message`); a **failed-by-name** named monitor the `system` atom (`deliver_named_noproc_down`, the C's `am_system`); the port builders the port immediate; the **remote** DOWN/EXIT the **node atom** (`enqueue_remote_down_message`/`enqueue_remote_exit_message`, the C's DIST_PROC/DIST_PORT rule). `tests/message_from_is_immediate.rs` pins each. Residual (host contract): `beam_message::Queue::enqueue`'s debug tripwire still rejects a non-immediate `from`/`token`, so a host storing a heap word there must relax that tripwire in the sibling `beam_message`; the gather/scatter hardening (`run_rooted_collection` pushes `from`/`token` and writes them back via `Message::set_from`/`set_token`) is already in place here.
- **`build_signal_message` reuses its `reason` argument verbatim across its collect-grow retry; `deliver_head_signal` does not.** `src/ptab.rs`'s `build_signal_message(recipient, from, reason, build)` runs `grow_receiver_for_signal` (which can relocate the receiver's **whole** young heap) and then calls `build(recipient.heap_mut(), reason)` with the **same** word, so a caller must pass a `reason` that is an immediate or lives outside the receiver's young heap (every in-tree caller does: the `noproc` atom, a node-down / port-close reason). The queued-signal path is immune because `deliver_head_signal` re-derives the reason from the receiver's own signal queue (`head_signal_reason`) each attempt — precisely because that reason *does* live in the receiver's heap (copied there by `copy_reason_onto` at enqueue time).
- **`Process::exit_reason` is not gathered, but is unreachable by a collection (audited).** It is written only in `terminate_into` (`src/ptab.rs`), immediately **after** `take(pid)` and before the PCB drop, and read only through `ProcessTable::exit_reason` — which needs a live pid `take` has already removed — so no collection can invalidate it. Caveat: a future change that reads it post-collection or re-inserts a terminated PCB would need it rooted. (Divergence from the C, which keeps a dead pid's exit reason observable via `process_info`; here `exit_reason` answers `TermNotFound`.)
- **`Message::token` has no producer in this crate** (always `NIL`) and is likewise not gathered — a future `with_token` of an on-heap term would hit the same class as `from`.
- **The `noproc` DOWN is delivered eagerly (documented deviation).** `monitor/2` on a non-live target materialises `{'DOWN', Ref, process, Target, noproc}` straight into the watcher's mailbox, so `process_info(self(), message_queue_len)` reports 1 right after the call where the oracle reports 0 (it defers the DOWN as a signal and reveals it at the next `receive`). The divergence is against **ordinary messages** too: the crate always reports the DOWN before a later send, whereas the oracle typically reports the send first (its own order is timing-dependent). A born-down also records **no** local monitor entry, so `demonitor(Ref, [info])` answers `false` where the oracle (itself racy here) answers `true`. Deferring would be *wrong* until the runtime services pending signals on entering `receive` (the workaround `beam_rt` already applies to self-directed `exit/2`), so eagerness is deliberate: the receive-visible result and the order against later DOWNs both match the oracle. Servicing `service_signals` at the receive point would make it exact — the runtime still does not, and the consequence is not only this ordering deviation: **every** signal a process queues on itself (a monitor `'DOWN'`, a link `'EXIT'`) stays pending until its next schedule-in, so a bare `receive {'DOWN', …}` in the same slice after a self-issued `exit(P, kill)` misses it and times out (measured; mechanism and fix scope in `../../beam_rt/src/runner/CONTEXT.md` Known Issues).
- **Priority run queues**: port tasks, and the C's shared NORMAL/LOW physical queue `schedule_count`/`RESCHEDULE_LOW` fairness deferral (this crate uses four physically distinct FIFOs — see `run_queue.rs`), are follow-ups. `Scheduler::set_priority`/`SchedulerPool::set_priority` DO requeue an already-queued process. The `save_calls` *effect* (saving the last `N` calls for `seq_trace`/`dbg`) is not modelled — only the `process_flag(save_calls, N)` value contract.
- **Pre-emption is produced by `beam_rt`'s runner.** `beam_rt::RuntimeRunner::run` honours its `budget` (charged at the machine's heap-admission points through `beam_rt/src/runner/budget.rs`) and returns `RunOutcome::Yield`, parking the process at the exact instruction — `beam_rt/tests/preempt.rs` pins the resulting interleaving. The crate-level contract is unchanged: the scheduler never pre-empts, so a runner that ignored its budget and never yielded would still run to completion in one call (the scheduler half is pinned by `tests/preemption.rs`).
- **Process-dictionary interior and heap fragments.** The dictionary is modelled as a flat key/value list (no hash-array interior); this crate exposes no whole-dictionary accessor, and `erlang:process_info(P, dictionary)` is served by `beam_rt`'s native floor. Saved args are a plain `Eterm` root list and `Process::deliver` fits a message into the receiver's own young heap, growing that heap on demand (collect + grow + retry once — the Constraints policy) rather than falling back to a fragment; the fragment-resident cases are a control signal for a receiver whose relocating collection is declined — the crate-owned **unpublished live roots** (**relocation-exempt** or **`Running`**) or the host's `CollectionGate` — the apply-time message build **and** the enqueue-time reason copy (their own suites, `tests/signal_fragment_fallback.rs`, `tests/decline_gate.rs`). `tests/signal_exhaustion.rs` covers the collect-grow-and-retry path and the exit-**policy** refusal a receiver whose collection is declined still meets (an exit signal that would terminate it).
- **Distribution-wide links/monitors**: external pids are decomposed into a `remote::RemotePid` and recorded (`remote_links`/`remote_monitors`), and every relationship change routes through the `remote::DistSignalRouter` trait seam (implemented downstream over `beam_dist`; no crate dependency). **Inbound** decoded control messages (`DOP_LINK`/`DOP_MONITOR_P`/`DOP_EXIT`/`DOP_EXIT2`) reach the table through the route-free receipt primitives above: `beam_rt`'s inbound path decodes the wire and calls them, and the `DistSignal`→`Dop` adapter stays `beam_rt`'s. The table itself never routes — with no router installed the **outbound** side is record-only (`has_dist_router()`). The outbound `DistSignal` keeps the link exit (`Exit` → `DOP_EXIT`) and `erlang:exit/2` (`Exit2` → `DOP_EXIT2`) distinct, and a local process's death routes one `MonitorExit` (`DOP_MONITOR_P_EXIT`, watched-first per `erts_dsig_send_m_exit`, `dist.c:1497-1519`) per recorded incoming `RemoteWatcher`, so a peer's `erlang:monitor(process, RemotePid)` receives its `{'DOWN', …}`; the transport's own `DFLAG_DIST_MONITOR`/`DFLAG_EXIT_PAYLOAD` choice between the 5-tuple and the payload form stays the router's.
- **Port lifecycle driving** — port scheduling, port signals and the port's read path — remains `beam_io`'s; `PortTable` owns only the id plus the ownership/links/monitors, and `ProcessTable::port_closed` delivers the closing port's messages.
- **Port-monitor cleanup on death needs a `PortTable` handle; the `Scheduler` adopts one.** `terminate_into` always drains `Process::port_monitors` (and the exit observer always sees them), but the matching *incoming* `PortMonitor` entries leave the `PortTable` only when a handle is supplied. A `Scheduler` built with `with_ports`/`set_ports` owns one, so its default `run_slice`/`run_ready` service signals through `service_signals_with_ports` and terminate through `terminate_with_ports` — a process dying in a slice cleans its dangling incoming `PortMonitor` (`tests/scheduler_ports.rs`). A scheduler built with `new`/`with_slice` owns none and keeps the port-less behaviour (outgoing watches drained, incoming left in place); the explicit `run_slice_with_ports`/`run_ready_with_ports` override the owned table for one call. The port-less `ProcessTable` entry points (`terminate`, `service_signals`, `apply_exit_signal`/`send_exit` (`erlang:exit/2`), `node_down`) pass no ports, so a process killed through one leaves its incoming `PortMonitor` until the owner runs `service_signals_with_ports` at the peer's next schedule-in. The SMP pool is port-less — a table there would add a **fourth lock family** to the BINDING discipline in `src/smp/CONTEXT.md`, so it is deferred (the pool has no production consumer).
- **Exact exit-reason term from `beam_common::ExitReason`**: signal reasons are carried as live `Eterm` terms (the deliverable form), not the term-independent `beam_common::ExitReason`; the mapping between them belongs to the raising BIF layer (`beam_bifs`).
- **`process_info` source data.** Every item this crate can answer is backed by a public accessor (`tests/process_info_source.rs` pins the mapping): `status` → `Process::status()`, `registered_name` → `ProcessTable::name_of(pid)`, `message_queue_len` → `Process::mailbox().len()`, `links` → `Process::links().iter()`, `monitors` → `Process::monitors().iter()` (+ `port_monitors()` for the `{port, Port}` entries), `monitored_by` → `Process::monitored_by()`, `trap_exit` → `Process::is_trapping_exit()`, `priority` → `Process::priority()`, `reductions` → `Process::reductions()`. Still absent here: `current_function`/`current_location` (this crate tracks no running MFA; `beam_rt`'s runner does and answers both from its own position) and the whole-dictionary view.
- **Monitor semantics not modelled.** `MonitorKind` has no `TimeOffset` variant (`erlang:monitor(time_offset, _)` is the oracle's `badarg`, raised by the BIF layer); `erlang:monitor_node/2,3` is **out of scope** — node-level distribution needing a local node identity plus an inbound `DOP_*` path, neither owned here; and a **named** port monitor (`monitor(port, Name)`) is a typed `unsupported` (the name registry resolves names to processes only, so a process monitor would be a wrong result). `erlang:monitor/2` on a non-live target yields the oracle's `noproc`; only its **timing** deviates (the DOWN is delivered eagerly — see above). `erlang:monitor/3`'s `{tag, T}` form **is** implemented for an **immediate** or a **literal-area** `T` on process **and** port targets (the tag lives in the `tags` side table); the remaining gap is a **heap-resident** tag and a tag on a **remote** external-pid target (both typed `unsupported`). The tag-less `monitor/2` form is complete.
- **`process_flag` coverage gap (owner: `beam_rt`).** `beam_rt`'s `ProcessBridge::process_flag` answers the oracle's **previous value** for `trap_exit`/`sensitive`/`priority`/`save_calls`/`error_handler`/`async_dist`/`message_queue_data`, and `badarg` for `min_heap_size`/`min_bin_vheap_size`/`fullsweep_after`, where the oracle returns the previous value (`beam_gc::AnyCollector` exposes only `policy()`, no `policy_mut`). `max_heap_size` is the exception: this crate now **stores** the setting on the PCB, **accounts** for it (`max_heap_usage`) and **decides** it (`heap_limit_verdict`, recorded by every collection/growth door), so what remains is `beam_rt`'s: install the parsed setting with `Process::set_max_heap_size`, drain `take_max_heap_verdict`, and perform the verdict — a `killed` self-exit for `Kill`, the `=ERROR REPORT====` for `Log` (see Handoffs). No `max_heap_size` enforcement exists in this crate, and by design it never will: this crate exposes the verdict, the host terminates.
- **`spawn_opt` option validation gap (owner: `beam_rt`/`beam_gc`).** `{max_heap_size, N}` with `N != 0` and `N < min_heap_size` is accepted where the oracle is `badarg` (the C `erl_process.c`'s `max_heap_size < min_heap_size ⇒ -1`); and a `{message_queue_data, off_heap}` spawn option is accepted and ignored (the mailbox stays on-heap).
- **`port_info` item gap (owner: `beam_bifs`/`beam_rt`).** `port_info(P, queue_size)` and `port_info(P, locking)` are `badarg` where the oracle answers `{queue_size, 0}` / `{locking, port_level}`; the 7-item `port_info/1` roster and order already match.
- **The reference-id space is closed on this crate's side; the sibling crates still owe the adoption (owner: `beam_rt`/`beam_abi`/`beam_bifs`).** Ids are no longer minted here from a private counter: `RefAllocator` is a zero-sized handle onto the one process-wide source `beam_common::next_ref_id`, shared with `erlang:make_ref/0`, the NIF `make_ref`, the timer references, `seq_trace` and NIF resource terms — so a monitor/alias reference can never carry a bare reference's id, and the old HAZARD-2 `=:=` collision is unrepresentable (`tests/reference_ids.rs` pins the source exactly and the absence of a collision). What remains is sibling code that treated `RefAllocator` as a per-instance **odometer** (`0, 1, 2, …`): `beam_rt/src/context/tests.rs::force_next_reference_id` and `beam_rt/src/runtime/ets_owner.rs::tid_ref_thing` (plus its unit test `the_tid_substitution_lands_on_the_handle_id`, which now mints a tid that does **not** decode back to the table handle) rely on a fresh handle starting at `0`. That is a cross-crate fix — a `MonitorRef` id can no longer be forced by walking an allocator; a public explicit-id mint (or rendering the tid through the canonical writer) is `beam_rt`'s / `beam_bifs`'s to add. Named in `HANDOFFS.md`. The *encodable* limit stays here and is unchanged: `MonitorRef::to_eterm` refuses an id past `MAX_SMALL` with `BeamError::SystemLimit`.
- **The compatibility gate is the sibling `../tools/differential/`'s, not this crate's.** It is `erts_rust/tools/differential/gate.sh`, which drives `differential suite --strict --allowlist <file>` (`gate.sh` itself accepts only `--allowlist`; `--strict` is the differential binary's flag). Read the live pass/fail and per-contract split from its own output — the counts drift as the corpus grows, so none are quoted here. This crate's own gate is `erts_rust/scripts/cargo.sh test --manifest-path erts_rust/Cargo.toml -p beam_process` (green: see `## Status`) plus the sibling suites the delivery is cross-checked against (`-p beam_rt`, `-p beam_engine`, `-p beam_gc`).
- **The receive-scan walk is not reduction-bounded.** The C's in-scan signal handling is bounded (`erts_proc_sig_handle_incoming`'s `limit`/`abs_lim` plus the helper's `left_reds` yield, so it can return mid-queue); `service_receive_signals` applies the whole receive-applicable prefix in one call, so receive pre-emption is the engine's own reduction budget at the caller. No observable term or order differs — only where a yield lands.
- **A distributed-spawn reservation is explicitly consumed or cancelled — there is no `Drop` arm.** `ProcessTable` is not reachable from a dropped handle, so `spawn_reserved` (consume) and `cancel_reservation` (roll back) are the only exits; the guaranteed property is narrower and is the one that matters: a stale/consumed/cancelled/foreign handle can never install a process, and cancel returns the number to the reuse list at most once (only for an existing empty slot), so nothing leaks. A claim on a number beyond the table's end materialises no slot, and a live `insert` at a claimed number kills the claim (a later `spawn_reserved` is `badarg`, never a clobber).
