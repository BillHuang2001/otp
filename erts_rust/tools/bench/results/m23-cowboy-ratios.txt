Caveats that travel with every figure above:
  * latency percentile coverage: the row stores at most 20,000 samples per load run. In --quick
    the sys side issues ~97-99k requests, so its percentiles are over the FIRST 20,000 samples
    (samples recorded: sys 20,000 vs rust 11,674 in r1), while the rust side issues ~11.5-11.7k and every
    request is sampled. Stated, not hidden; the two distributions are single-mode and apart.
  * no `=ERROR REPORT====` block appeared on either server in any pass, and `errors` is 0
    everywhere (the six --quick passes, the --full pair and the probe: 10 rows): every response
    was complete.
  * Cowboy's default `max_keepalive` closes a keep-alive connection after 1,000 requests on it and
    announces `Connection: close`; that is a COMPLETED request, not a transport error, and the
    driver reconnects. The per-run close count scales with the request count (~97 closes for
    ~97.9k sys requests, ~11 for ~11.7k rust requests in --quick) and is in the row notes.
  * `latency_ms[max]` is a single worst sample, so it is an outlier statistic, not a stable
    distributional one: the sys side's worst values (36.5 / 11.7 / 12.0 ms) are single stalls, which
    is why the per-round max ratio swings 0.594 / 1.842 / 1.796 while p50 and p99 do not. Quote p50
    and p99; cite max only with that caveat.
  * `build_ms` is one `make` of the same staged tree (network `git` fetch of cowlib+ranch) and
    `compile_ms` is the same external `erlc`, so both ratios near 1.0 are stage sanity checks, not
    runtime comparisons.
