WHAT THIS PAIR OF RECORDS SUPPORTS — AND WHAT IT DOES NOT
  * It supports, row by row: start-up (both p50 and the p99 direction), the boot-dominated peak-RSS rows,
    the four GC-workstream per-unit rows, and (new) a whole-process `slice` at parity in both wall time
    and footprint. Those are measured against one oracle, on one host, with the side order alternating.
  * It does NOT attribute any row to a specific one of the four changes: there is no binary A/B in this
    session (no second `beam_rt` build was measured), and the engineering rule is that a ratio is never
    chained with an A/B. What the shape does say is that every movement is on the RUST side while the
    oracle is flat, and that the two memory/boot figures match the workstream's own boot claims
    (boot `VmHWM` 91.45 -> 66.68 MiB claimed; 66.03 MiB measured independently here).
  * The one row that moved for a reason no change in this set targets is baseline/compute_loop
    (rust 183.70 -> 150.02 ms, -18.3%, sys +0.9%). That loop builds a 1 000 000-element cons list, so it
    is heap-growth/GC-sensitive — consistent with the `beam_gc` carried-growth change — but it is reported
    as a movement, not as an attribution.
  * A row called "inside" is not evidence of no change; it is evidence that this pair of 6- and 7-round
    records cannot separate change from host drift at that magnitude.
