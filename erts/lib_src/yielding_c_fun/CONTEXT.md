# erts/lib_src/yielding_c_fun/ — Yielding C Fun (YCF)

## Intent
YCF is a **standalone C-to-C source-to-source compiler**: given a C input file and a list of function names, it emits an equivalent file plus generated C where those functions are turned into *yieldable coroutines* (`_ycf_gen_yielding` / `_ycf_gen_continue` / `_ycf_gen_destroy`).
It exists so that long-running Erlang BIFs/NIFs can cooperatively yield without hand-written state machines; it is invoked **at build time** by `erts/emulator` (see `../../emulator/internal_doc/AutomaticYieldingOfCCode.md`) and the generated C is then compiled like any other source.
It is a self-contained tool with no dependency on the OTP build, but it is shipped in the OTP source tree, built as part of `erts/lib_src`, copied into the bootstrap system, and installed into the release.
Author: Kjell Winblad (originally 2019); maintained by Ericsson AB. Apache-2.0.

## API Surface
### The executable
The compiler is one C program (`ycf_*.c`/`.h`); the only artifact is the binary `yielding_c_fun`:
- Standalone build (`TARGET` unset, via `GNUmakefile`): `bin/yielding_c_fun.bin`.
- OTP build (`TARGET` set, via `../Makefile.in`): `bin/$(TARGET)/yielding_c_fun$(EXE_SUFFIX)`.
- Installed by `../Makefile.in`'s `release_spec` into `erts-$(VSN)/bin/` (+ `.pdb` on win32); the top-level `Makefile.in` copies it to `$(BOOTSTRAP_ROOT)/bootstrap/bin/yielding_c_fun` for bootstrap builds.

### CLI (the contract callers depend on)
Documented in `README.md` (authoritative user documentation):
`-h`, `-log_max_mem_usage FILE`, `-f NAME` (auto-yield: decrement a reduction at each loop body and before gotos), `-frec NAME` (`-f` plus before calls to other yieldable functions and before returning), `-fnoauto NAME` (yield only where the macros say), `-fexternal NAME` (a yielding version exists elsewhere — calls to NAME are rewritten to the external one; NAME is *not* transformed here), `-output_file_name F`, `-header_file_name F`, `-debug`, `-only_yielding_funs`, `-static_aux_funs`, and the input `.c` file as the last argument.
Additional modes implemented in `ycf_main.c` but **not** documented in `README.md`: `-yield` (makes the default mode explicit; required by the OTP build), `-repeat` (parse + re-print only, used for round-trip testing), `-print_ast`, `-print_symbols`.
`-h`/`--help` prints usage and exits 0. Output goes to stdout unless `-output_file_name` is given.

### Input-language markers (macro protocol in the transformed file)
`YCF_YIELD()`, `YCF_YIELD_NO_REDS()`, `YCF_CONSUME_REDS(N)`, `YCF_STACK_ALLOC(N)`, `YCF_GET_EXTRA_CONTEXT()`, `YCF_NR_OF_REDS_LEFT()`, `YCF_SET_NR_OF_REDS_LEFT(N)`, `YCF_MAX_NR_OF_REDS`.
Hooks, in two interchangeable styles (`YCF_SPECIAL_CODE_START(EVENT); ... YCF_SPECIAL_CODE_END();` or `/*special_code_start:EVENT*/ if(0){...} /*special_code_end*/`) with events `ON_SAVE_YIELD_STATE`, `ON_RESTORE_YIELD_STATE`, `ON_DESTROY_STATE`, `ON_DESTROY_STATE_OR_RETURN`, `ON_RETURN`.
Generated code also `#define`s `YCF_YIELD_CODE_GENERATED` and `YCF_IS_YIELDED`, which the hand-written driver uses to select the transformed/original call path.

### Generated functions (per transformed function `f`)
- `f_ycf_gen_yielding(long *nr_of_reds, void **yield_state, void *extra_context, ycf_yield_alloc_type, ycf_yield_free_type, void *alloc_free_ctx, size_t stack_alloc_size_or_max, void *stack_alloc_data, <original params>)` — starts the call; `*yield_state` is NULL until it yields.
- `f_ycf_gen_continue(long *nr_of_reds, void **yield_state, void *extra_context)` — resumes a yielded call.
- `f_ycf_gen_destroy(void *yield_state)` — frees the state of a suspended call (used when a process dies while yielded); recurses into active subcalls.

## Constraints
- YCF parses only a **subset of C** (documented in `README.md` "Code Restrictions"): declarations must be `type [*]name[size][= expr];` (no comma-separated declarators, no function-pointer declarators without a `typedef`, no brace-initializers/designated initializers); pointers to stack-allocated data must not outlive a yield (`YCF_STACK_ALLOC` is the workaround); **macros are never expanded**, so anything hidden behind a macro that YCF must see (declarations, `return`, `goto`, calls to yieldable functions) will be missed; and calls to yieldable functions must appear as a whole separate statement, as a whole assignment RHS (optionally negated), or as the whole expression of `if`/`while`/`do-while` — otherwise YCF prints an error to stderr and `exit(1)`.
- `README.md` says "it is recommended to check that the generated code is correct" — the transformation is not a verified compiler; always compile the output with a real C compiler.
- Never hand-edit generated artifacts (`*.o`, the binary, `bin/yielding_c_fun.bin`, `test/tmp_dir/`).
- `Makefile` in this directory is **generated by `GNUmakefile`** (target `Makefile: $(YCF_SOURCES)`) yet is tracked in git; it exists only so non-GNU make can build the tool. Change the build rules in `GNUmakefile`/`main_target.mk`, never in `Makefile`.
- `main_target.mk` is the single source of truth for compile rules and is included by **both** `GNUmakefile` (standalone) and `../Makefile.in` (OTP). Keep it free of standalone-only assumptions.

## Design Decisions
- **Source-to-source instead of a runtime trampoline/coroutine library**: the generated code is ordinary C, so the C compiler still does register allocation, inlining and optimization; there is no platform-specific stack switching or assembly, and the suspended state is an explicit heap object that survives yielding across different scheduler threads/processes and can be explicitly destroyed.
- **The tool intentionally leaks memory.** It is short-lived, so `ycf_malloc` (`ycf_utils.c`) rarely frees; `main_target.mk`'s `YCF_CFLAGS` deliberately strips `-Wstrict-prototypes -Wdeclaration-after-statement -Wmissing-prototypes -fsanitize%` (and `YCF_LDFLAGS` strips `-fsanitize%`) so leak detectors/sanitizers do not fire on the tool itself.
- **Build integration**: `../Makefile.in` defines `YCF_SOURCE_DIR` and includes this directory's `main_target.mk`, so YCF is built as part of `erts/lib_src`'s `all` (its object list depends on `$(YCF_EXECUTABLE)`) before the emulator is built.
- **Two drop-in layouts from one rule set**: with `TARGET` unset objects go next to the sources and the binary is `bin/yielding_c_fun.bin` (standalone); with `TARGET` set they go to `$(YCF_SOURCE_DIR)/$(TARGET)` and `bin/$(TARGET)/yielding_c_fun` (OTP).
- **Compiler-agnostic standalone build**: `GNUmakefile` supports `MODERN_CC`, `CC_32_BIT`, `ADD_SAN`/`MEM_SAN`/`UB_SAN` (`V_CC=clang`) and a generated portable `Makefile` for non-GNU make; none of this affects the OTP build.

## Known Issues / Gotchas
- **`bin/yielding_c_fun` is NOT the compiler** — it is a tracked ~60-line **bash wrapper**. It requires at least one `.c` argument, sanity-compiles each with plain `cc -c` (bailing with "Could not compile file with cc"), then execs `bin/yielding_c_fun.bin` from its own directory. It only works in the standalone layout (there is no `.bin` in the OTP `bin/$(TARGET)/` layout). Do not confuse it with the binary or with the OTP `yielding_c_fun[.exe]`.
- **Unknown options are not rejected explicitly, and usage errors exit 0.** `ycf_main.c` recognises only the options listed above. An unrecognised token *before* any `-f*` option makes the tool print the usage text via `print_help_text_and_exit`; that function ignores its `error_code` argument and calls `exit(0)`, so the run "succeeds" and — if stdout was redirected (as the sha256 demo's rule does) — silently leaves an **empty output file** (this is what the removed `-use_gc` flag triggers). An unrecognised token *after* valid `-f*` options is instead taken as the input file name and fails with exit 1 ("could not open file").
- **Do not rely on the exit status to detect CLI misuse**: `print_help_text_and_exit(prog, error_code)` always `exit(0)`. Genuine failures do `exit(1)`: unreadable input file, function name not found, and an untransformable call to a yieldable function.
- The `-h` text has a typo: `-fextenal` (and it omits `-yield`/`-repeat`/`-print_ast`/`-print_symbols`).
- `README.md` is internally inconsistent in one place: it refers to a `YCF_YIELD_ALLOC(N)` in the "Pointers" restriction, but the actual macro (and the documented one) is `YCF_STACK_ALLOC(N)`.
- **`-fexternal` only marks a name as externally yieldable**; it does not transform anything, so a name given with `-fexternal` must also be produced by another YCF invocation (or the link fails). The emulator relies on exactly this split (`erts_qsort` generated in `utils.c`'s invocation, marked `-fexternal` in `erl_map.c`'s).
- **`lib/simple_c_gc/` no longer exists.** GC support was removed (deleted along with the `-use_gc` flag); `scripts/license-header.es` still lists the stale path `erts/lib_src/yielding_c_fun/lib/simple_c_gc/**` in its no-warning list, and `test/examples/sha256_erlang_nif/c_src/Makefile` still passes `-use_gc` (see that node's CONTEXT.md).
- `-log_max_mem_usage` is only meaningful for the tool's own accounting; combined with the intentional leaking it reports peak, not freed, bytes.
- `TODO` (in-tree) lists known gaps: automatic array-size/struct initialization, and warning on calls from positions YCF cannot handle.
- `ycf_helpers.h` is dead code: no file `#include`s it and no Makefile/script/CI references it (the only in-tree mention is the prose line below). Its `ycf_alloc`/`ycf_free` bodies are duplicated inline in `test/examples/thread_example.c` (lines 23/28) and `doc/thread_tutorial.md` (lines 53/58), which define their own copies instead of including it. Its non-`static` `ycf_free(void*, void*)` would also collide (conflicting types / duplicate symbol) with the differently-signed `ycf_free(void*)` declared in `ycf_utils.h` and defined in `ycf_utils.c` if ever included into a live translation unit.
- The `PRINT_LIST` macro in `ycf_lists.h` is never expanded anywhere (its only occurrence in the repo is its own `#define`); every other `ycf_lists.h` macro is used, either directly or inside `GENERATE_LIST_FUNCTIONS`.

## Notes for Agents
- Before touching the transformation: read `README.md` (authoritative feature/CLI reference, including the "Code Restrictions" section), then run `make test` from this directory. The regression suite compares **program stdout**, not the text of the generated C, so changes to output formatting are not caught — but any behavioural change (yield granularity, reduction accounting, trap/destroy protocol) will break the golden `.c.out` files, which must be regenerated from a real run.
- The emulator consumers to check for breakage are `../../emulator/beam/erl_map.c`, `../../emulator/beam/erl_db.c`, `../../emulator/beam/utils.c` (all contain `YCF_*` markers) driven by `../../emulator/Makefile.in` (`-yield -only_yielding_funs -f ... -fexternal ... -output_file_name $(TARGET)/...`), plus `../../emulator/utils/find_cross_ycf` for cross builds.
- Distinguish the three builders: `GNUmakefile` (standalone, this dir, not used by OTP), `main_target.mk` (shared rules), `../Makefile.in` (real OTP build). If you only need the tool for the emulator, the OTP build already produces `bin/$(TARGET)/yielding_c_fun`.
- Use the `-debug` flag to detect pointers into the C stack across yields; it requires the program to define `ycf_debug_get_stack_start()` (or the OTP helper `ycf_debug_set_stack_start`/`ycf_debug_reset_stack_start`) and works best with a debug build of the consumer.
- `doc/thread_tutorial.md` is the beginners' tutorial; `test/examples/sha256_erlang_nif/` is the end-to-end yielding-NIF demo.

## Dependencies
- A C99 compiler and GNU make (standalone `make`), or the OTP build's configured compiler.
- **clang** specifically, for the test suite (`test/test.sh` hardcodes `CC=clang`).
- Optional for `GNUmakefile`'s extra targets: gcc, tcc, bmake, clang-tidy, clang-format, inotifywait, sanitizer runtimes.
- The sha256 demo additionally needs `rebar3` and an installed Erlang/OTP with `erl_interface`.
- No external libraries — the tool is pure C99 (the previously vendored `simple_c_gc` was removed).

## Test Strategy
- `make test` here (standalone) builds `bin/yielding_c_fun.bin` and runs `test/test.sh`; `make test_all` chains the compiler matrix (`test_gcc_clang_tcc`, `test_bmake`, `test_32_bit`, `test_modern_cc`, the sanitizer variants) plus `clang_tidy`.
- The suite is a bash script with committed golden stdout files; see `test/CONTEXT.md` for the phase list and `test/examples/CONTEXT.md` for the file→feature map.
- **Not run by the OTP build or CI.** Nothing under `.github/`, `scripts/`, `make/` or the ERL_TOP `Makefile.in` invokes YCF's tests; only `../Makefile.in` builds the tool. Regressions are caught only if someone runs the suite by hand.
- Coverage gaps: no assertion on the text of the generated code, no tests for `-fexternal`, `#include`d/multi-file inputs, `-print_ast`/`-print_symbols`, or the error-message paths; the sanitizer targets do not actually sanitize the tool (their `-fsanitize` flags are filtered out by `YCF_CFLAGS`).
