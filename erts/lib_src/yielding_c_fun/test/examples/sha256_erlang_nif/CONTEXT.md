# sha256_erlang_nif — YCF yielding-NIF demo (rebar3 project)

## Intent
The only complete, end-to-end example of using YCF (Yielding C Fun) to implement a *yielding* Erlang NIF.
It is a standalone rebar3 project (not part of the OTP build): a vendored C SHA-256 implementation is transformed by YCF into a yieldable coroutine, wrapped in a NIF that cooperatively yields after a fixed reduction budget, and verified against `crypto:hash/2` from Common Test.
Referenced from the YCF user manual (`../../../README.md`): "This Erlang NIF example shows how one can use YCF to write a yielding Erlang NIF library."
Sibling reference: `../../doc/thread_tutorial.md` is the beginners' YCF tutorial (threads, not NIFs).

## API Surface
- **rebar3 project** `sha256_nif` (app vsn `0.1.0`, no deps). `rebar.config` wires the C build: pre-hook `make -C c_src` on compile, post-hook `make -C c_src clean` on clean (freebsd variant uses `gmake`).
- **Erlang API** — `src/sha256_nif.erl`: `sha256_nif:sha256(Binary) -> Binary` (32-byte digest, byte-identical to `crypto:hash(sha256, Binary)`); `-on_load(init/0)` loads `priv/sha256_erlang_nif.so` via `erlang:load_nif/2`. Before the NIF is loaded the stub raises `{not_loaded, ...}`.
- **NIF library** — `c_src/sha256_nif.c` → `priv/sha256_erlang_nif.so`.
  `ERL_NIF_INIT(sha256_nif, ...)` with `nifload`/`nifupgrade` opening the resource type `"sha256_nif"`; resource payload `sha256continuation` holds the YCF coroutine pointer, a work environment and the output binary.
  Exported NIFs: `sha256/1` (entry point) and the internal trampoline `sha256_nif_cont_after_yield/1` (re-entered with `enif_schedule_nif`, taking the resource as its argument).
- **Top-level `Makefile`** (thin rebar3 wrapper; `REBAR3 ?= which rebar3 || ./rebar3`): `build`/`compile`, `test` (`rebar3 ct`), `clean`, `deps`, `docs` (`rebar3 edoc`), `release`, `all`.
- **Generated by YCF (gitignored, absent in a clean checkout)** — `c_src/gen_yielding_sha_256.c`, `c_src/gen_yielding_sha_256.h`; symbols consumed by the glue: `calc_sha_256_ycf_gen_yielding`, `calc_sha_256_ycf_gen_continue`, `calc_sha_256_ycf_gen_destroy`, `YCF_IS_YIELDED`.
- **Test** — `test/basic_SUITE.erl`: `test1/1` (loops over `1024 bsl V` for V=1..15, checks equality against `crypto:hash/2` through the second `timer:tc` match and prints both timings) and `test2/1` (digest of `<<"hej">>` vs `crypto`).
- **Licensing** — top-level `LICENSE` is Apache-2.0; `c_src/sha-2/` is public domain (upstream `amosnier/sha-2`, commit recorded in `c_src/sha-2/GIT_VERSION`).

## Constraints
- `c_src/sha-2/` is vendored third-party code: `sha-256_orginal.c` is the pristine upstream copy, `sha-256.c` is the *only* file patched for YCF. Keep that split so the delta stays inspectable; do not reformat or re-vendor.
- Only `sha-2/sha-256.c` is fed to YCF. Only files not in `sha-2/` and not `gen_*` are compiled into the library.
- YCF must be built before this demo (`erts/lib_src/yielding_c_fun/bin/yielding_c_fun`, produced by the OTP build or by `make` inside `yielding_c_fun/`); the rule uses the relative path to it.
- The C build derives its include paths from a working `erl` in `PATH` (`code:root_dir()`, `code:lib_dir(erl_interface)`), so a configured/installed Erlang with `erl_interface` is required.

## Design Decisions
- **Yielding strategy**: YCF's `-yield` (auto-yield) mode applied to `calc_sha_256` and `calc_chunk`, driven by an explicit reduction budget `REDUCTIONS_UNTIL_YCF_YIELD()` (`200*300*8`). While yielded, the coroutine state lives in a NIF resource; the trampoline re-enters via `enif_schedule_nif` with a fresh reduction budget, giving cooperative yielding for inputs far larger than one timeslice.
- **State kept across yields**: an `enif_alloc_env()` work environment plus a copied input binary keeps the input alive while yielded; the 32-byte output binary is allocated up front; allocator/freer callbacks are thin `enif_alloc`/`enif_free` wrappers. The resource destructor calls `..._ycf_gen_destroy` and frees env/binary (covers the process-dies-while-yielded case).
- **Why `sha-2/sha-256.c` was patched** (see `sha-256_orginal.c` diff):
  1. YCF forbids pointers to stack objects that live across yields, so the local `uint8_t chunk[64]` became `uint8_t* chunk = YCF_STACK_ALLOC(64)` (`YCF_STACK_ALLOC` = `malloc`).
  2. The include is guarded: the generated file is compiled from `c_src`, so it needs `"sha-2/sha-256.h"` while the original file needs `"sha-256.h"` (`#ifdef YCF_YIELD_CODE_GENERATED`).
  3. The `uint32_t h[] = {...}` array initializer was split into a declaration plus explicit assignments, and `int i, j;` split into two declarations.
  4. The vendored upstream `Makefile`/`test.c`/`.travis.yml` remain solely as provenance, plus the original file for diffing.

## Known Issues
- **The C build rule is stale**: `c_src/Makefile` invokes YCF with `-use_gc`, an option that no longer exists (removed by OTP commit `63367d9f76` "ycf: Remove GC support", which deleted `lib/simple_c_gc/`). `ycf_main.c` rejects an unrecognised leading option by printing the usage text and exiting 1, so the recipe leaves an *empty* `gen_yielding_sha_256.c` and never creates `gen_yielding_sha_256.h`; compiling `sha256_nif.c` then fails. The demo therefore does not build as-is — dropping `-use_gc` from the rule is the fix.
- **Not exercised by any automated test**: the block in `erts/lib_src/yielding_c_fun/test/test.sh` that would run `make clean && make test` here is commented out, so `make test` in `yielding_c_fun/` never touches this directory and nothing in CI does either.
- `c_src/Makefile`'s `SOURCES` filter uses `grep -v "./sha-2/..."` against the output of `find $(C_SRC_DIR)` (absolute paths). It only matches because the regex `.` swallows the `c` of `c_src`; renaming this directory's parent layout or `c_src/` itself would silently start compiling the vendored `sha-256.c`/`test.c` and break the link.
- `rebar.config` repeats `{erl_opts, [debug_info]}.` / `{deps, []}.` twice (harmless leftover).
- `test/basic_SUITE:test1/1` builds each input via `lists:duplicate/2` + `list_to_binary/1` (up to ~32 MB of "h" per iteration) — memory-hungry and slow; it is a benchmark-style test, not a unit test.

## Notes for Agents
- Nothing in this directory is compiled or installed by the OTP build at `ERL_TOP`; it is a reference/demo project. Changes here cannot break the OTP build.
- To use it manually: build YCF (top-level `make`, or `make` inside `erts/lib_src/yielding_c_fun/`), make `rebar3` available on `PATH`, remove `-use_gc` from the `gen_yielding_sha_256.c` rule, then `make` (or `rebar3 ct`) here.
- `c_src/gen_yielding_sha_256.[ch]` and `priv/` are gitignored, so their absence is expected; they are build products to be regenerated, never edited.
- For the contract of the generated functions read the "Generated functions" section of `../../../README.md`; `YCF_IS_YIELDED` is the check the trampoline loops on.
- `bin/yielding_c_fun` (at `../../../bin/`) is a tracked bash wrapper that also verifies the input `.c` compiles with `cc` before running `yielding_c_fun.bin`.

## Dependencies
- `rebar3` (external, *not* vendored — the Makefile falls back to `./rebar3`, which does not exist here), GNU make (or `gmake` on FreeBSD), a C compiler (`cc`/`gcc`; the Makefile branches on Linux/Darwin/FreeBSD), `erl` in `PATH` with ERTS headers and `erl_interface` (the library links `-lei`), and a built YCF wrapper at `../../../bin/yielding_c_fun`.

## Test Strategy
- Intended run: `rebar3 ct` / `make test` → `basic_SUITE` (`test1`, `test2`), which asserts the NIF digest equals `crypto:hash(sha256, _)`. Currently blocked by the stale `-use_gc` rule.
- Manual smoke test without rebar3: build the `.so` into `priv/`, then call `sha256_nif:sha256/1` and compare with `crypto:hash(sha256, _)`.
- Not covered anywhere: the NIF upgrade/reload path (`nifupgrade`), resource destruction for a process killed while yielded, and interaction with dirty schedulers — i.e. exactly the areas the demo would be most useful to validate.

## Routing Table
- `c_src/` → hand-written NIF glue (`sha256_nif.c`), build rules + the YCF invocation (`Makefile`), and the generated `gen_yielding_sha_256.[ch]` (gitignored)
- `c_src/sha-2/` → vendored upstream SHA-256 (public domain): pristine `sha-256_orginal.c`, YCF-patched `sha-256.c`, `sha-256.h`, plus unused upstream `Makefile`/`test.c`/`.travis.yml`/`GIT_VERSION`
- `src/` → Erlang module `sha256_nif.erl` and `sha256_nif.app.src`
- `test/` → Common Test suite `basic_SUITE.erl`
- `../` → sibling YCF example inputs (`*.c` / expected `*.out` pairs) run by `../../test.sh`
- `../../../README.md`, `../../../doc/thread_tutorial.md`, `../../../bin/yielding_c_fun` → YCF manual, tutorial and launcher (read-only, outside this node)
