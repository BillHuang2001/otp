# sha256_erlang_nif — YCF yielding-NIF demo (rebar3 project)

## Intent
The only complete, end-to-end example of using YCF (Yielding C Fun) to implement a *yielding* Erlang NIF.
It is a standalone rebar3 project (OTP app `sha256_nif` 0.1.0, **not** part of the OTP build): a vendored C SHA-256 implementation is transformed by YCF into a yieldable coroutine, wrapped in a NIF that cooperatively yields after a fixed reduction budget so a long hash reschedules the calling process instead of blocking a scheduler thread.
It is primarily *documentation by example* — referenced from `../../../README.md` ("This Erlang NIF example shows how one can use YCF to write a yielding Erlang NIF library") — not part of any OTP build or test run.
Sibling reference: `../../doc/thread_tutorial.md` is the beginners' YCF tutorial (threads, not NIFs).

## API Surface
- **rebar3 project** `sha256_nif` (no deps). `rebar.config` wires the C build: pre-hook `make -C c_src` on compile, post-hook `make -C c_src clean` on clean (freebsd variant uses `gmake`). Note it repeats `{erl_opts, [debug_info]}.` / `{deps, []}.` twice (harmless leftover).
- **Erlang API** — `src/sha256_nif.erl`: `sha256_nif:sha256(Binary) -> Binary` (32-byte digest, byte-identical to `crypto:hash(sha256, Binary)`); `-on_load(init/0)` loads `priv/sha256_erlang_nif` via `erlang:load_nif/2`. Before the NIF is loaded the stub raises `{not_loaded, ...}`.
- **NIF library** — `c_src/sha256_nif.c` → `priv/sha256_erlang_nif.so`.
  `ERL_NIF_INIT(sha256_nif, ...)` with `nifload`/`nifupgrade` opening the resource type `"sha256_nif"`; resource payload `sha256continuation` holds the YCF coroutine pointer, an `enif_alloc_env()` work environment and the output binary.
  Exported NIFs: `sha256/1` (entry point) and the internal trampoline `sha256_nif_cont_after_yield/1`, re-entered via `enif_schedule_nif` with a fresh budget; the resource destructor calls `calc_sha_256_ycf_gen_destroy` (covers a process dying while yielded).
  Reduction budget: `REDUCTIONS_UNTIL_YCF_YIELD()` = `200*300*8`.
- **Top-level `Makefile`** (thin rebar3 wrapper; `REBAR3 ?= which rebar3 || ./rebar3`): `build`/`compile`, `test` (`rebar3 ct`), `clean`, `deps`, `docs` (`rebar3 edoc`), `release`, `all`.
- **Generated by YCF (gitignored, absent in a clean checkout)** — `c_src/gen_yielding_sha_256.c`, `c_src/gen_yielding_sha_256.h`, `priv/`, `_build/`. Symbols consumed by the glue: `calc_sha_256_ycf_gen_yielding`, `calc_sha_256_ycf_gen_continue`, `calc_sha_256_ycf_gen_destroy`, and the `YCF_IS_YIELDED` check the trampoline loops on.
- **Test** — `test/basic_SUITE.erl`: `test1/1` (hashes growing inputs `1024 bsl V`, V=1..15, asserts equality against `crypto:hash/2` and prints both timings) and `test2/1` (digest of `<<"hej">>` vs `crypto`).
- **Licensing** — top-level `LICENSE` is Apache-2.0; `c_src/sha-2/` is public domain (upstream `amosnier/sha-2`, revision recorded in `c_src/sha-2/GIT_VERSION`, Unlicense in `c_src/sha-2/LICENSE`).

## Constraints
- The shared-library basename is derived from the **directory name**: `c_src/Makefile` sets `PROJECT = $(notdir $(abspath $(CURDIR)/..))` → `priv/sha256_erlang_nif.so`, while `src/sha256_nif.erl` hardcodes `?LIBNAME = sha256_erlang_nif`. Renaming this directory breaks NIF loading.
- `c_src/sha-2/` is vendored third-party code: `sha-256_orginal.c` is the pristine upstream copy and `sha-256.c` is the *only* file patched for YCF. Keep that split so the delta stays inspectable; do not reformat or re-vendor.
- `c_src/sha256_nif.c` forward-declares `struct buffer_state;` **before** `#include "gen_yielding_sha_256.h"`: the generated header needs incomplete types used by yielded function parameters to be declared first.
- Only `-f calc_sha_256 -f calc_chunk` are asked to yield (auto-yield mode); `sha-256.h` is not regenerated, so the generated code mirrors the hand-written header.
- Only `sha-2/sha-256.c` is fed to YCF. Only files not under `sha-2/` and not `gen_*` are compiled into the library.
- Never edit generated `gen_yielding_sha_256.*`, `priv/`, or `_build/`.
- The C build derives its include paths from a working `erl` in `PATH` (`code:root_dir()`, `code:lib_dir(erl_interface)`), so a configured/installed Erlang with `erl_interface` is required.

## Design Decisions
- **Yielding strategy**: YCF's auto-yield mode applied to `calc_sha_256` and `calc_chunk`, driven by the explicit reduction budget. While yielded the coroutine state lives in a NIF resource; the trampoline re-enters via `enif_schedule_nif`, giving cooperative yielding for inputs far larger than one timeslice.
- **State kept across yields**: the work environment plus a copied input binary keeps the input alive while yielded; the 32-byte output binary is allocated up front; allocator/freer callbacks are thin `enif_alloc`/`enif_free` wrappers.
- **Why `sha-2/sha-256.c` was patched** (diff against `sha-256_orginal.c`):
  1. YCF forbids pointers to stack objects that live across yields, so the local `uint8_t chunk[64]` became `uint8_t* chunk = YCF_STACK_ALLOC(64)` (in NIF context `YCF_STACK_ALLOC` maps to `malloc`).
  2. The include is guarded (`#ifdef YCF_YIELD_CODE_GENERATED`): the generated file is compiled from `c_src` so it needs `"sha-2/sha-256.h"`, whereas the original needs `"sha-256.h"`.
  3. The `uint32_t h[] = {...}` initializer was split into a declaration plus explicit assignments, and `int i, j;` split into two declarations.
  4. The upstream `Makefile`/`test.c`/`.travis.yml` remain solely as provenance, plus the original file for diffing.

## Known Issues
- **The C build rule is stale and the demo does not build as-is.** `c_src/Makefile` invokes YCF with `-use_gc`, an option that no longer exists (removed by OTP commit `63367d9f76` "ycf: Remove GC support", which deleted `yielding_c_fun/lib/simple_c_gc/`). The current compiler prints the usage text and exits 1 on an unrecognised leading option, so the recipe leaves an *empty* `gen_yielding_sha_256.c`, never creates `gen_yielding_sha_256.h`, and compiling `sha256_nif.c` then fails. Dropping `-use_gc` from the rule is the fix; the rest of the pipeline (flag list, generated function names, and the 9-argument `*_ycf_gen_yielding` call in the NIF) still matches the current generator (no API drift).
- The generation rule calls `../../../../bin/yielding_c_fun`, the tracked bash wrapper, which execs `bin/yielding_c_fun.bin` from its own directory. The in-tree OTP build instead produces `yielding_c_fun/bin/$(TARGET)/yielding_c_fun`, so this path only resolves after a **standalone** YCF build in `erts/lib_src/yielding_c_fun/`.
- **Not exercised by any automated test**: the block in `../../test.sh` that would run `make clean && make test` here is commented out, and nothing in CI or the OTP build touches this directory.
- `c_src/Makefile`'s `SOURCES` filter uses `grep -v "./sha-2/..."` against the output of `find $(C_SRC_DIR)` (absolute paths). It only matches because the regex `.` swallows the `c` of `c_src`; do not "fix" these to literal `./` paths, and beware that renaming the parent layout could silently start compiling the vendored `sha-256.c`/`test.c`.
- In `src/sha256_nif.erl` the `{error, bad_name}` fallback of `code:priv_dir/1` builds an extension-less library path, so it fails unless the app is found in the code path (the normal rebar3 case).
- `test/basic_SUITE:test1/1` builds each input via `lists:duplicate/2` + `list_to_binary/1` (up to ~32 MB per iteration) — memory-hungry and slow; it is benchmark-style, not a unit test.

## Notes for Agents
- Nothing in this directory is compiled or installed by the OTP build at `ERL_TOP`; it is a reference/demo project, so changes here cannot break the OTP build.
- Relative path math: from `c_src/`, `../../../../bin` is `erts/lib_src/yielding_c_fun/bin`.
- To use it manually: build YCF (standalone `make` inside `erts/lib_src/yielding_c_fun/`), put `rebar3` on `PATH`, remove `-use_gc` from the `gen_yielding_sha_256.c` rule, then `make` (or `rebar3 ct`) here.
- `sha-256_orginal.c` is the unmodified upstream source kept for diffing against the YCF-adapted `sha-256.c`; the vendored `sha-2/{Makefile,test.c,.travis.yml,.gitignore}` are upstream leftovers excluded from the build.
- For the contract of the generated functions read the "Generated Functions" section of `../../../README.md`.

## Dependencies
- A built YCF compiler reachable via `../../../bin/yielding_c_fun` — the tracked bash wrapper, which needs `bin/yielding_c_fun.bin` produced by a standalone `make` in `erts/lib_src/yielding_c_fun/`.
- A working Erlang/OTP installation with `erl` on `PATH`: `c_src/Makefile` shells out to `erl -noshell` to discover `erts-*/include` and the `erl_interface` include/lib dirs, and links against `libei` (`-lei`).
- `rebar3` on `PATH` (the wrapper Makefile falls back to `./rebar3`, which does not exist here), GNU make (or `gmake` on FreeBSD), and a C compiler (`cc`/`gcc`; the Makefile branches on Linux/Darwin/FreeBSD).
- The `crypto` OTP application at test time (used by both test cases but *not* declared in `src/sha256_nif.app.src`).

## Test Strategy
- Intended run: `rebar3 ct` / `make test` → `basic_SUITE` (`test1`, `test2`), which asserts the NIF digest equals `crypto:hash(sha256, _)`; `rebar3 clean` triggers the `make -C c_src clean` post-hook. Currently blocked by the stale `-use_gc` rule.
- Manual smoke test without rebar3: build the `.so` into `priv/`, then call `sha256_nif:sha256/1` and compare with `crypto:hash(sha256, _)`.
- Not covered anywhere: the NIF upgrade/reload path (`nifupgrade`), resource destruction for a process killed while yielded, and interaction with dirty schedulers — exactly the areas the demo would be most useful to validate.
