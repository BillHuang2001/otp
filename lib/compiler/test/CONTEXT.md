# Compiler — Common Test Suites

## Intent
Common Test suite directory for the `compiler` OTP application (`lib/compiler/src/`).
Validates the whole compilation pipeline — Core Erlang passes, the SSA (BEAM SSA) optimization passes, and the final BEAM assembler/validator — plus the public `compile` API, warnings/errors and documentation emission.
The central strategy: the *same* suite source is compiled and run repeatedly under different compiler-optimization option sets, so that any optimization that fails to preserve semantics shows up as a behavioural difference (see "Cloned suites").

## How Suites Are Run
- Each suite is a standard `*_SUITE.erl` exporting the usual Common Test callbacks (`all/0`, `suite/0`, `groups/0`, `init_per_suite/1`, …).
- Pragmatically every suite calls `test_lib:recompile(?MODULE)` from `init_per_suite/1`; this recompiles the suite module with its own optimization options (recovered from `module_info(compile)` and filtered by `test_lib:opt_opts/1`) when the cover server is running, then smoke-tests `beam_disasm` on the result.
- Long-running per-test work is fanned out via `test_lib:p_run/2` (parallel, bounded to ≤8 processes / scheduler count) or run sequentially on 32-bit systems (`test_lib:s_run/1`); `{comment, "N warnings"}` results are aggregated into the suite result.
- `test_lib:parallel/0` returns `[parallel]` (or `[]` on single-scheduler systems) and is used as the group property in most `groups/0`.
- Run from this directory with `make test` (builds the `Emakefile` then `erl -make`, then Common Test).
- The parent `lib/compiler/Makefile` overrides the `test` target to pass `ERL_ARGS="-enable-feature maybe_expr"`, so the `maybe_expr` language feature is enabled at runtime during tests (required by `maybe_SUITE` and others); do not run these suites without it.
- `compiler.spec` is the release test spec (`{suites,"../compiler_test",all}`); `compiler.cover` is the Cover config (instruments module `compiler`, excludes `core_scan`/`core_parse`).

## Cloned (Suffixed) Suites
`MODULES` lists the base suites. The Makefile derives *cloned* suite modules from a base suite `<S>` by `sed`-renaming its `-module(...)` (`%_X_SUITE.erl: %_SUITE.erl`), compiling each clone with a distinct option set, and running them as separate suites.
The clone lists are subsets of `MODULES` (`NO_OPT`, `INLINE`, `COVER`, `DIALYZER`, `R29`, `NO_BOOL_OPT`): cloning a feature suite under multiple option sets is what turns it into an optimization-correctness test.
Clone suffix → compile flags (via the generated `Emakefile`):
- `_no_opt_SUITE` → `+no_copt +no_bool_opt +no_share_opt +no_bsm_opt +no_fun_opt +no_ssa_opt +no_recv_opt +no_postopt` — all optimizer stages off (reference "unoptimized" semantics).
- `_post_opt_SUITE` → same as `_no_opt_SUITE` minus `+no_postopt` — higher-level opts off but the low-level post-optimization passes still run.
- `_no_copt_SUITE` → `+no_copt` only (skip Core→SSA optimizations).
- `_no_copt_ssa_SUITE` → `+no_copt +no_ssa_opt`.
- `_no_ssa_opt_SUITE` → `+no_bool_opt +no_share_opt +no_bsm_opt +no_fun_opt +no_ssa_opt +no_recv_opt`.
- `_no_bool_opt_SUITE` → `+no_bool_opt` (only `guard`, `andor`).
- `_no_module_opt_SUITE` → `+no_module_opt`; `_no_type_opt_SUITE` → `+no_type_opt`.
- `_inline_SUITE` → `+inline`; `_cover_SUITE` → `+line_coverage`; `_dialyzer_SUITE` → `+dialyzer` (only `bs_match`); `_r29_SUITE` → `+r29` (only `native_record`).
`test_lib:is_cloned/1` recognises the suffixes; `test_lib:get_data_dir/1` maps a clone's (non-existent) data dir back to the base suite's `*_SUITE_data` directory.
Generated clone `.erl` files and `Emakefile` are build artifacts — git-ignored (root `.gitignore`), never edited by hand; edit the base suite.

- `stage2_suite_driver.erl` + `run_stage2_suites.sh` — the host runner for the six Stage-2 pass suites (see "Host Runner For The Stage-2 Suites"). `stage2_suite_driver` is listed in `MODULES` like the other support modules; the `.sh` wrapper is a dev helper, not installed.

See the routing table for its generator, option matrices and measured counts.
- `test_lib:get_unique_files/1,2` enumerates non-cloned, non-LFE `*_SUITE` files (used for the "loaded/smoke" style suites).

## Compile-Throughput Measurement (Stage-2 passes)
`measure_stage2_compile.sh` (+ `stage2_bench.erl`) is a manual, committed measurement harness — not a suite and not in CI. It answers "what do the opt-in Stage-2 passes cost, and did they fire at all?":
- `lib/compiler/test/measure_stage2_compile.sh` (env: `CORPUS=stdlib|all` default `stdlib`, `REPS=N` default 5, `RIG_EBIN=DIR` to reuse a rig, `KEEP_SCRATCH=1`). Step 1 resolves `RIG_EBIN` via `../scripts/host_env.sh build` (read-only; writes only to `/tmp`), step 2 compiles `stage2_bench.erl` with the *host* `erlc` into a scratch `ebin`, step 3 runs `erl -noshell -pa <scratch> -pa $RIG_EBIN -s stage2_bench main -extra $REPS $ERL_TOP $CORPUS` (never an escript: escripts reject `-pa` and preload the host `compile`).
- `stage2_bench` takes the corpus from that third `-extra` argument: `stdlib` (the default when the argument is omitted) = `lib/stdlib/src/*.erl` (96 modules), `all` = `lib/*/src/*.erl` (772 modules — the source of the full-`lib/*/src` reach numbers). Every corpus gets `-I lib/stdlib/include lib/kernel/include lib/compiler/src`; `all` additionally gets every `lib/*/include` directory. It compiles the corpus in ONE session, once per option set — `off`, `loop_opt+loop_arith_licm`, `fusion_opt`, `fbip_opt`, `all` — after one discarded `off` warmup, rotating the option order every repetition (so drift does not favour one set). It prints min/median/max wall-clock, the ratio against `off`, and the number of modules whose `Code` chunk differs from the `off` reference; the raw per-repetition numbers are printed too. Modules that fail to compile are counted and listed and the run continues. It exits non-zero only on harness errors (wrong compiler, empty corpus, nothing compiled), never because a pass did or did not fire.
- It refuses to run unless `code:which(compile)` is inside `RIG_EBIN` (exported by the wrapper): a forgotten `-pa` would otherwise silently benchmark the host OTP compiler, whose default pipeline knows nothing about these flags.
- The `Code` chunk is extracted by hand from the FOR1 container (4-byte chunk id, 32-bit size, 4-byte-aligned payload, after the unsized `BEAM` form type) because the host's `beam_lib:chunks/2` cannot read it (`{error,beam_lib,{unknown_chunk,...}}`).
- Only COMPILE time is measured here, and the only output about the passes is the `Code`-chunk change count: `stage2_bench` never loads or executes a compiled module (no `code:load_binary`, no per-kernel timing). Execution time is measured by `measure_loop_opt_speed.sh` for the loop passes (see "Runtime Speed Measurement") and, non-assertingly, by `beam_ssa_opt_equiv_SUITE:benchmark/1` for all four flags.
- Interpretation: this host is shared/loaded, so only *ratios* mean anything (observed per-set spread is 10–40% within a run, and the last repetitions of a run drift upward together), always read the "changed" column first. Last measured (host OTP 29.1.1, rig compiler 10.0.6). 96-module stdlib corpus, 5 repetitions: 24 modules change under `loop_opt+loop_arith_licm`, 2 under `fusion_opt`, 3 under `fbip_opt`, 27 under `all` — the same numbers in every repetition; cost `off` 14.8 s median, `loop_opt+loop_arith_licm` +15.0% (min-ratio +8.4%), `fusion_opt` ±0% (0.998), `fbip_opt` +9.2% (min-ratio +4.1%) and `all` +16.2% (min-ratio +12.7%) on the median — `loop_opt+loop_arith_licm` and `all` are consistently the slowest sets, `fusion_opt` is indistinguishable from `off` at this noise level. 772-module `lib/*/src` corpus, 1 repetition: 17 of the 772 files fail to compile for unrelated include/host reasons (`beam_asm`, `beam_disasm`, 4 `dialyzer` modules, `eldap`, `inet_dns` and 9 `public_key` modules), leaving 755 compilable; 83 change under `loop_opt+loop_arith_licm`, 12 under `fusion_opt`, 8 under `fbip_opt`, 98 under `all`, with raw wall-clock 95.8 s / 129.9 s / 100.9 s / 93.6 s / 89.7 s — a single repetition on a loaded host, where the LAST-measured set came out fastest, so quote only the `changed` column from `CORPUS=all` and take the cost ratios from the stdlib 5-repetition run.

## Runtime Speed Measurement (Stage-2 loop passes)
`measure_loop_opt_speed.sh` (+ `loop_opt_bench.erl`) is the execution-time counterpart of `measure_stage2_compile.sh`: a manual, committed harness — not a suite, not in CI — that answers "does `loop_opt`+`loop_arith_licm` make a real loop RUN faster?".
- `lib/compiler/test/measure_loop_opt_speed.sh` (env: `REPS=N` default 15, forced odd and >= 11; `ROUNDS=N` default 5, `0` skips the whole-program cross-check; `RIG_EBIN=DIR` to reuse a rig; `KEEP_SCRATCH=1`). It resolves the rig through `../scripts/host_env.sh build` (read-only; writes only to `/tmp`), compiles the driver with the *host* `erlc`, then runs `erl -noshell -pa <scratch>/ebin -pa $RIG_EBIN -s loop_opt_bench main -extra $REPS $ROUNDS` (never an escript).
- Every kernel is a standalone module exporting `run/0`, compiled TWICE from the same source — `off` = `[binary,return]`, `on` = `[binary,return,loop_opt,loop_arith_licm]` — under two different module names, and both builds are loaded into ONE VM. Interleaved paired samples in the same process then pay VM warm-up, JIT state and host load identically for both variants; one round is discarded, the measured rounds rotate the variant order, and the median of an odd count is reported.
- Hard assertions: a kernel declared to reach must produce a different `Code` chunk OFF vs ON, a control kernel marked `expect_reach => false` must not change, and every variant of a kernel must return the same value from `run/0`.
- Six realistic tail-recursive loops (the shape all of Erlang/Elixir/LFE lower to), each dominated by one rewrite family, so a win or its absence is attributable: `lcg_shift` (power-of-two LCG — `* 1024`, `rem 65536`, `div 256`, `rem 256`), `adler_pow2` (Adler-style rolling checksum, two `rem 65536`), `fixed_point` (`rem 1048576`, `div 1024`, `rem 1024`), `mul2_sum` (an unbounded `* 2`, i.e. the `X+X` rewrite), `base64_digits` (`div 64`/`rem 64`/`div 4096` digit extraction) and `bitpack` (shifts only — the deliberately unchanged CONTROL).
- Kernels with a hand-written form also get a THIRD variant, `manual`: the same loop with `band`/`bsr`/`+` spelled out in the source, compiled with the flags OFF. Its ratio against `off` is the CEILING of what the rewrite can buy on this machine — if hand-written shifts are not faster than `div`/`rem`, no compiler-side rewrite of them can be either.
- Reported per kernel: OFF/ON medians, `ratio = OFF/ON` (>1 = ON faster), the run's own spread (per-variant IQR over its median, summed), the `manual` median and `man/off`, whether the `Code` chunk changed, the `div/rem/*` -> `bsl/bsr/band` instruction-count delta from `beam_disasm`, and the per-variant allocation evidence of one isolated run (GC count, words reclaimed and `final_heap_words` from `erlang:statistics(garbage_collection)` in a fresh process).
- The harness prints `/proc/loadavg` and states the caveat in its own output: the host is shared and loaded, absolute times are NOT reproducible, and only the ON/OFF ratio of one session is a signal — together with its spread and the reach column.
- Measured (host OTP 29.1.1, rig compiler 10.0.6, load average ~28 on 14 cores; all six kernels reach as declared, the control is unchanged): the rewrites fire — `div/rem/*` 4/2/3/1/6 -> 0 with `bsl/bsr/band` 4/3/3/0/6 introduced — and NONE of them is faster. Two runs (21 and 15 interleaved samples) gave OFF/ON ratios `lcg_shift` 0.928 / 0.891, `adler_pow2` 0.995 / 1.019, `fixed_point` 1.025 / 1.010, `mul2_sum` 1.014 / 0.972, `base64_digits` 1.008 / 1.066, against 1.047 / 1.121 on the UNCHANGED control `bitpack` — the run-to-run noise floor is 5–12%, so only `lcg_shift` is distinguishable from it, and it is consistently ~7–11% SLOWER with the flags. There is no win to report on any kernel.
- Allocation: `erlang:statistics(garbage_collection)` reports 0 GCs and 0 reclaimed words for every kernel and every variant, which is the expected result — the strength reductions change CPU work, not allocation, and a tail-recursive loop allocates nothing. The `final_heap_words` column does vary ±30% between variants because a process heap grows on demand and is never shrunk by these loops, so that column is not attributable to the flags.
- The `manual` column explains the null result: `man/off` = 0.937 / 1.006 / 1.014 / 1.048 / 1.032 in the 21-sample run and 0.921 / 1.016 / 0.997 / 0.994 / 1.014 in the 15-sample one, i.e. writing `band`/`bsr` by hand buys nothing here. The reason is in the JIT, not in the pass: `erts/emulator/beam/jit/x86/instr_arith.cpp` already turns `rem`/`div` by a power-of-two immediate into a mask / right shift (gated on the dividend's clamped range being >= 0, the very condition the pass requires) and `X * 2^n` into a left shift, and `erts/emulator/beam/jit/arm/instr_arith.cpp` does the same.
- The whole-program cross-check (a fresh `erl -noshell` per variant, `ROUNDS` alternating rounds, the loop timed in-VM) runs only for kernels flagged `whole_program` (`lcg_shift`). It measures cold code in a new VM and is dominated by start-up, so it corroborates the in-VM direction (0.880 vs 0.928) instead of replacing it.
- `beam_ssa_loop_opt_SUITE:real_loop_speedup/1` is the suite-side version of the same measurement: it hard-asserts reach and identical results and only REPORTS the ratio (see Known Issues for why no direction is asserted there).

## Compile Flags for the Suites Themselves
`ERL_COMPILE_FLAGS += +clint +clint0 +ssalint +nowarn_missing_spec_documented` — the suites are themselves compiled with the compiler's SSA/core linters enabled (so test code exercises the linters); `+deterministic` is filtered out.

## Core-Erlang (LFE) Suites
`CORE_MODULES = lfe_andor_SUITE lfe_guard_SUITE` are compiled from `.core` (Core Erlang) sources with `+from_core`.
Their `.core` files are generated from the LFE compiler (see `lfe.readme` for the regeneration procedure; `lfe-source.patch` and `lfe-core.patch` are applied to the LFE checkout).
Dummy `.erl` stubs are generated (`ERL_DUMMY_FILES`) so the release test dir has a matching `.erl` for each `.core`.

## Property Tests (`property_test/`)
- `compile_prop.erl` — PropEr/EQC property randomly generating Erlang abstract code and compiling it (used by `random_code_SUITE`).
- `beam_types_prop.erl` — properties over the internal type lattice (`beam_types.hrl`), e.g. absorption; high repetition count.
- Both `-include_lib` `ct_property_test.hrl` and (via `-ifdef(PROPER)`) are gated on the `proper_erlang_abstract_code` add-on being present; suites using them (`random_code_SUITE`, `beam_types_SUITE`) call `ct_property_test:init_per_suite/1` and `{skip,_}` when it is unavailable.
- `random_code_SUITE` compiles random code under all compiler option combinations; the run count defaults to `?NUMTESTS = 1000` and can be overridden with the `ERL_RANDOM_CODE_NUMTESTS` environment variable.

## Constraints
- Do not edit generated clones or `Emakefile` (build artifacts); edit the base suite or the Makefile variables.
- Adding a new feature suite that must be re-run under multiple option sets means adding it to the relevant subset variable(s) in the Makefile (and to `MODULES`).
- Suite data lives in `<base>_SUITE_data/`; a clone must obtain it via `test_lib:get_data_dir/1`, not a hard-coded path.
- Keep suites feature-agnostic where possible — they are compiled with many different feature/optimization combinations.

## Notes for Agents
- `TEST_NEEDS_RELEASE` is NOT set for this app: tests run in-tree against the freshly built compiler, not an installed release.
- Tests assume a working build of `compiler` (and `stdlib`/`kernel`) is on the code path; running them from a bare checkout without `make` first will fail.
- The six opt-in Stage-2 suites (`beam_ssa_loop_opt_SUITE`, `beam_ssa_fus_SUITE`, `beam_ssa_fbip_SUITE`, `ssa_opt_budget_SUITE`, `beam_ssa_opt_diff_SUITE`, `beam_ssa_opt_equiv_SUITE`) exercise compile options that are OFF by default (`loop_opt`, `loop_arith_licm`, `fusion_opt`, `fbip_opt`, `ssa_opt_budget`/`ssa_opt_watchdog`/`ssa_opt_fn_budget`/`ssa_opt_gates`). Each is self-contained (compiles its own probe modules in-test, no `*_SUITE_data` dir — `beam_ssa_opt_diff_SUITE:real_corpus/1` additionally compiles the real `lib/stdlib/src/*.erl` corpus, resolved through the repository root) and needs a `compiler` that already contains the matching pass module. `beam_ssa_loop_opt_SUITE` additionally `-include`s `../src/beam_ssa.hrl`/`beam_types.hrl` and builds SSA terms in-process, so it needs the native-record owner modules available.
- None of the six suites is in a clone subset (`NO_OPT`/`INLINE`/`COVER`/`DIALYZER`/`R29`/`NO_BOOL_OPT`), so `make test` compiles each exactly once with `ERL_COMPILE_FLAGS` (`+clint +clint0 +ssalint +nowarn_missing_spec_documented`) and runs it once; `compiler.spec` is `{suites,"../compiler_test",all}`.
- Assertion style / option sets per suite (verified against the code): `beam_ssa_loop_opt_SUITE` — flat `all/0`, 23 cases (incl. `real_loop_speedup/1`, which compiles a real tail-recursive kernel OFF vs ON in `priv_dir`, hard-asserts the `Code` chunk changed and that both builds return the same value, and only REPORTS the timing ratio), hand-built `#b_set{}` SSA fed to `beam_ssa_loop_opt:opt/1` and `opt_arith/1` (shape assertions) plus executed ON-vs-OFF probes (`{ok,V}` vs `{Class,R}`); `beam_ssa_fus_SUITE` — group `p` `[parallel]`, 20 cases over 6 option sets (`opt_sets/0`), `beam_disasm` shape/instr-count assertions, executed equality, `Code`-chunk identity in `fusion6_kill_switches`; `beam_ssa_fbip_SUITE` — group `p` `[parallel]`, 12 cases, default 2 option sets (some cases pass custom 3/5-set lists), asserts the `update_record` hint and whole-function/whole-module identity; `ssa_opt_budget_SUITE` — group `p` (sequential), 20 cases, probes compiled with `no_spawn_compiler_process` and inspected through `beam_ssa_opt_budget:get_stats/0` (counters of the MOST RECENT compilation only); `beam_ssa_opt_equiv_SUITE` — group `p` (sequential), 9 cases, executed OFF-vs-ON batteries plus `changed_funs/2` (label-canonicalised) as the non-vacuity control; `beam_ssa_opt_diff_SUITE` — group `diff` (sequential), 4 cases, 20-set matrix (1 baseline + 6 transform + 12 identity + 1 `no_ssa_opt` control), default corpus 6 modules × 12 arity-1 funs × a fixed 30-argument battery ⇒ 41,040 compared calls.
- `ts_install_cth` (Common Test hook referenced in `suite/0`) comes from `common_test`.
- When `ts_install_cth`/`ct_run` is unavailable in the installed OTP, run a suite by invoking its callbacks directly (`init_per_suite/1` then each testcase from `all/0`/`groups/0`) from a small driver module. Select the freshly built compiler with `erl -pa <built-ebin>` *at startup*: an `escript` preloads the system `compile` before `code:add_patha/1` takes effect, so an escript driver silently tests the wrong compiler (opt-in passes then appear not to fire). Run the driver with `erl -noshell -pa <built-ebin> -pa <driver-dir> -s driver main`, and preload the built `.beam`s (native-record owner modules must be loaded first).
- `beam_debug_info_SUITE` compiles itself with `-compile([beam_debug_info])` on purpose (to disassemble a module carrying debug info).
- `beam_validator_SUITE_data/*.S` are hand-written BEAM assembly listings fed to `beam_validator` (invalid ones must be rejected); `beam_ssa_check_SUITE_data/*.erl` carry `%%` directives consumed by `beam_ssa_check` to assert SSA annotations.
- `beam_ssa_fus_SUITE` (1604 lines), `beam_ssa_opt_diff_SUITE` (1360) and `beam_ssa_opt_equiv_SUITE` (1145) carry large probe-generator fixtures — they are legitimately long; do not split them for size alone.

## Running A Single Suite Without ct_run (verified recipe)
`ts_install_cth.beam` is NOT built into `common_test/ebin` in a plain in-tree build, so `suite/0`'s `{ct_hooks,[ts_install_cth]}` cannot be resolved and neither `ct_run` nor `ct:run_test/1` will start these suites. Drive the callbacks directly instead:
1. Build the tree (`./otp_build configure && make`) and compile the suites you need into a scratch ebin with the same lint flags the Makefile uses:
   An in-tree OTP-30 build has not been validated in this container (the host OTP here is OTP-29/erts-17.1 — see `## Known Issues`); where no built tree is available, the committed host rig is the supported route.
   `./bin/erlc -I lib/stdlib/include -I lib/compiler/test -o "$SCRATCH/ebin" +clint +clint0 +ssalint +nowarn_missing_spec_documented lib/compiler/test/<SUITE>.erl lib/compiler/test/test_lib.erl`
2. Run a driver that adds that ebin to the code path **at startup** and calls the callbacks itself (never from an escript: an escript preloads the system `compile` before `code:add_patha/1` takes effect; an `erl -noshell -pa <ebin> -eval ...` is safe). For each suite: `init_per_suite([{priv_dir,Dir}])`, then for every entry of `all/0` either call the testcase with that Config, or (for `{group,G}`) call `init_per_group(G,Config)`, run the testcases listed for `G` in `groups/0`, then `end_per_group/2`; finish with `end_per_suite/1`. `groups/0` entries may be 2- or 3-tuples (`{Name,TCs}` / `{Name,Props,TCs}`) and may contain non-testcase properties such as `parallel`.
   Trap: `code:ensure_loaded/1` returns `{module,M}` when the suite is already loaded, not `{ok,M}` — a driver that matches only `{ok,_}` dies before the first testcase, and since `halt/1` does not flush the io queue the failure can look like "no output at all". Have the driver append its report with `file:write_file/2` and exit with `erlang:halt(Status,[{flush,true}])`.
3. Wrap each testcase call in `try ... catch Class:Reason -> {Class,Reason} end`. A failing testcase shows up as `exit:{test_case_failed,Reason}` (`ct:fail/1` is just `exit({test_case_failed,Reason})`) or as an `error:{assertEqual,...}`/`erlang:error` from `assert.hrl`; both are caught, so no Common Test process is needed.
4. The scratch ebin must be a directory of its own: `erl -pa` on a directory with tens of thousands of entries (e.g. the shared `$TMPDIR`) makes the node fail to start.
This recipe drives the pass suites (`ssa_opt_budget_SUITE`, `beam_ssa_loop_opt_SUITE`, `beam_ssa_fus_SUITE`, `beam_ssa_fbip_SUITE`, `beam_ssa_SUITE`) against the in-tree compiler.

## Host Runner For The Stage-2 Suites (`run_stage2_suites.sh`)
`run_stage2_suites.sh [SUITE ...]` (+ `stage2_suite_driver.erl`) is the committed way to run the six Stage-2 pass suites (`beam_ssa_loop_opt_SUITE`, `beam_ssa_fus_SUITE`, `beam_ssa_fbip_SUITE`, `ssa_opt_budget_SUITE`, `beam_ssa_opt_diff_SUITE`, `beam_ssa_opt_equiv_SUITE`) on a machine whose `erl`/`erlc` is an *older* OTP than this tree (here OTP 29.1.1 vs OTP-30 beams). It exists because `ts_install_cth` is not installed there, so `ct_run`/`ct:run_test` cannot start these suites; it therefore drives the CT callbacks itself (`init_per_suite` → `all/0` → `groups/0` → `end_per_suite`) and prints `PASS`/`FAIL`/`SKIP`/`WARN` per testcase to stdout and `$STAGE2_SCRATCH/report.txt`; exit 1 on any failure, 2 on a usage/environment error; the scratch dir is kept.
- Compilation is host-only: the suites are *compiled* by the host `erlc` from a scratch copy that `../scripts/host_env_xform.py` flattened (`xform_in/` = `../src/*.{erl,hrl}` + `test_lib{.erl,.hrl}` + `stage2_suite_driver` + the requested suites → `xform_out/`, then `erlc -I xform_out -I ../stdlib/include`; never `-I ../src`). This is what makes the hand-built SSA terms (`#b_set{}`/`#b_literal{}`/`#t_integer{}`/`#opt_st{}`) classic **tuple** records matching the rig's identically flattened pass modules. Compiling the suite with the rig compiler instead emits opcode 193 (the host refuses to load it), and a `+no_native_record_opt` recompile leaves the terms disagreeing (`badrecord` in the 9 SSA-level loop testcases).
- Execution is against the **rig** compiler: `erl -noshell -pa $RIG_EBIN -pa $SCRATCH/ebin -run stage2_suite_driver main ...`; the runner exports `STAGE2_RIG_EBIN` and the driver prints and checks `code:which(compile)`, so a forgotten `-pa` cannot silently test the host compiler.
- It builds the rig via `../scripts/host_env.sh build` unless `RIG_EBIN` is preset.
- The report carries a `host adaptation:` header line and a per-suite `NOTE` wherever the flattening applied, so a host result is never mistaken for a real OTP-30 run (it exercises the pass *logic*, not native records).
- The transform is strict and only the compiled files are handed to it: requesting `compile_SUITE` (arity-1 `is_record/1`) or `native_record_SUITE` (`#_{...}`, arity-1 `is_record/1`) aborts with the offending construct named — those constructs cannot exist on a host without native records.
- Invocation is a plain `erl -noshell -pa $RIG_EBIN -pa $SCRATCH/ebin -run stage2_suite_driver main <report> SUITE…` started from the repository root (`run_stage2_suites.sh:228-235`) — no `ct_run`, no in-tree OTP build: only a released host OTP plus the rig ebin (built by `../scripts/host_env.sh build`, or preset via `RIG_EBIN`) and `python3` for the flattening. The host `erlc` compiles the suites with `+clint +clint0 +ssalint +nowarn_missing_spec_documented` and retries without the lint flags if the host rejects them (`:203-223`). No host OTP version is hardcoded; the driver only WARNS when `code:which(compile)` is not under `$STAGE2_RIG_EBIN` (`stage2_suite_driver.erl:170-193`), so check that header line in the report.
- Last full run (host OTP 29.1.1, rig compiler 10.0.6): **88 pass, 0 fail, 0 skip, 0 warn**, exit 0 (`loop_opt` 23, `fus` 20, `fbip` 12, `budget` 20, `diff` 4, `equiv` 9); the run takes ~5.5 minutes on this host.

## Known Issues
- **The host runner compiles the suites with an older OTP**, so nothing it runs can validate OTP-30-only language/term features (native records in particular), and `beam_lib:chunks/2` cannot read the `code` chunk on this host — `beam_ssa_opt_equiv_SUITE` therefore extracts the `Code` chunk by hand from the FOR1 container.
- **`beam_ssa_opt_equiv_SUITE`'s `benchmark` verdict is computed, never asserted**: `benchmark/1` classifies the run as `"ON faster"` / `"ON slower"` / `"inconclusive (the difference is inside the measured spread)"` (spread = the per-kernel interquartile range over the median, propagated to the sum of medians), so "inconclusive" is the everyday outcome on a shared host, not a hardcoded result; the reported per-kernel `ratio` column is `median(Off)/median(On)` while the aggregate ratio is `OnTot/OffTot` (opposite orientations). The case's only PERFORMANCE assertion is the loose per-kernel `median(On) =< median(Off) * 2` guard in `kernel_row/2`; it additionally hard-asserts that both builds return identical `{ok,V}`/`{Class,Reason}` for the small battery (`check_battery` on `bench_cases/0`). Do not quote the printed ratio as a speedup.
- **The budget eligibility gates are consulted whenever the machinery is enabled by any option**, not only under `ssa_opt_gates` (which merely enables them *without* a bound): `beam_ssa_opt:wrap_fun/3` always supplies `gate(Name)` and `beam_ssa_opt_budget:run/5` always evaluates it, so in a budgeted, gates-off build a gate-skipped pass is counted under `gated`, not `over_budget`. `ssa_opt_budget_SUITE` asserts the observable consequence rather than the prose.
- **The host `erl`/`erlc` here is OTP 29.1.1 / erts-17.1 and refuses this tree's OTP-30 beams** (*"Use of opcode 193; this emulator supports only up to 191"*), so the committed host rig (`scripts/host_env.sh` + `host_env_xform.py` + `run_stage2_suites.sh`) is the supported route to build and run the compiler in this container; a full in-tree OTP-30 build (`./otp_build configure && make`, the `Running A Single Suite Without ct_run` recipe) has **not** been validated here.
- **The default-OFF byte-identity claim holds at the `Code`-chunk level only**: whole `.beam` files differ between option sets because the `CInf` and `Dbgi` chunks embed the option list, so identity must be asserted on the `Code` chunk (as the suites and both harnesses do), never on the whole file.
- **`beam_ssa_fbip_SUITE`'s moduledoc spells the disassembled instruction as a 7-tuple** (`{update_record,{atom,Hint},Size,Src,SrcFun,Dst,{list,Updates}}`); the real shape is the 6-tuple `{update_record,Hint,Size,Src,Dst,{list,Updates}}` (`beam_disasm:resolve_inst/4`), which is what `hint/4` and `is_update_record/1` match. Trust the code, not that comment.
- **No test asserts the SHAPE of `beam_ssa_loop_opt`'s `?SAFE_BIFS` (tag test) / `?SAFE_OPS` (`put_list`/`put_tuple`) hoist** (`?MAX_HOIST` = 64): `beam_ssa_loop_opt_SUITE` pins the arithmetic-LICM and strength-reduction shapes and only exercises the constructor hoist implicitly, through the `lp_ctor` equivalence probe of `loop_opt_preserves_result/1` (values only, no disassembly).
- **The loop passes' strength reductions buy NO runtime speedup on this runtime, and that is measured rather than assumed.** `measure_loop_opt_speed.sh` shows the rewrites firing on every kernel (`div`/`rem`/`*` bifs 4/2/3/1/6 -> 0, replaced by `bsl`/`bsr`/`band`) while the ON/OFF ratio stays at the noise floor (0.93-1.03 against a 1.047 ratio on an UNCHANGED control kernel), and the `manual` variants — the rewrites written by hand, flags OFF — are equally not faster (`man/off` 0.92–1.05). The mechanism is the JIT: `erts/emulator/beam/jit/x86/instr_arith.cpp` already lowers `rem`/`div` by a power-of-two immediate to a mask / right shift under the same clamped-range condition the pass requires, and `X * 2^n` to a left shift; the arm64 backend does the same. So on a JIT build these rewrites can only be neutral, and `X*2^n -> bsl n` on the loop kernel came out marginally NEGATIVE (0.928 in-VM, 0.880 in a fresh VM). What is still unmeasured and could pay off: an interpreter-only backend (no JIT strength reduction) and the LICM halves of the pass, which can only act on the pipeline's only CFG cycles (receive loops) and save at most one allocation per iteration — no benchmark in this directory exercises either.
- **`real_loop_speedup/1` asserts reach and value equality, never a timing direction.** It compiles a real tail-recursive kernel OFF vs ON, hard-asserts the `Code` chunk changed and that both builds return the same value, and prints the medians/ratio/spread plus a caveat through `ct:pal/2`; the only timing assertion is the loose non-flakiness guard `OnMedian =< OffMedian * 2` (mirroring `beam_ssa_opt_equiv_SUITE:kernel_row/2`), because the honest measured direction here is "no gain, possibly a small loss" and asserting either way would flake on this shared host.
- **`beam_ssa_opt_diff_SUITE:sensitivity/1` asserts transform REACH, not mutation detection**: it requires every `transform` set to change ≥1 probe module's `Code` chunk. No testcase mutates a pass; "injecting a deliberate unsoundness is caught" is a manual experiment, not committed code.
