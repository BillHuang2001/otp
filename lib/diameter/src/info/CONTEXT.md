# diameter/src/info — Debug & Introspection Modules

## Intent
Holds the two `diameter` modules that provide interactive debugging and runtime introspection facilities, used from a shell rather than by the stack itself.
They are excluded from the application's `modules` list (see `CONSTRAINTS`) but are still compiled, installed and dialyzed.
`diameter_dbg` is the user-facing entry point (tables, processes, versions, trace helpers); `diameter_info` is a formatting/collection helper library used only by `diameter_dbg`.

## API Surface
Flat directory, two modules, no headers, no tests of their own.

`diameter_dbg` — debug/introspection entry points (all exported, called manually from the shell):
- Table inspection: `table/1`, `tables/0`, `sizes/0`, plus one accessor per diameter ets table (`diameter_config/0`, `diameter_peer/0`, `diameter_reg/0`, `diameter_request/0`, `diameter_sequence/0`, `diameter_service/0`, `diameter_stats/0`).
- Build/version introspection: `modules/0` (modules listed in the installed `diameter.app`), `versions/0`, `version_info/0` (system/OS/module version dump), `fields/1` (field names per table), `procs/0` (diameter processes), `nl/0` (load all diameter modules on all nodes).
- Structure/topology: `children/0` (supervision tree), `subscriptions/0` (service → pid subscribers), `pp/1` (pretty-print a Diameter message binary, header + AVP loop).
- Trace control: `tracer/0,1`, `p/0,1`, `tpl/1`, `tp/1`, `stop/0` — thin wrappers over the `dbg` module (runtime_tools) for tracing in a shell, streaming to a process, an IP port or a file.

`diameter_info` — generic table-listing/formatting toolkit (also usable standalone for "rolling your own"):
- `format/1..4`, `table/2`, `tables/1,2`, `list/1`, `split/2,3`, `tab2list/1` — pretty-print records in ets tables, locally and (via `rpc:multicall(nodes(known), ...)`) on all known nodes.
- `modules/1`, `versions/1`, `version_info/1`, `attrs/2`, `procs/1`, `collect/2` — collect the corresponding information for a module prefix/list or a process predicate.
- `usage/1`, `sep/0,1`, `widest/1`, `p/1`, `p/3` — output/layout helpers for building further listings.
- `format/3` (`format(Tables, SplitFun, CollectFun)`) is the remote-node entry point: its `collect/2` counterpart is what gets `rpc:multicall`-ed to remote nodes.

## Constraints
- The modules MUST NOT be added to the `{modules, [...]}` tuple of `src/diameter.app.src` (`%INFO%` is intentionally on a commented line); the app file is generated by `src/Makefile` from `modules.mk`.
- `INFO_MODULES` in `src/modules.mk` is the single source of truth for this directory's contents; adding/removing a module here propagates to `TARGET_MODULES` (build + install), `src/Makefile` `dialyze` and the app-file generation.
- Membership in `TARGET_MODULES` means the beams go to `../ebin/` and the `.erl` sources are installed under `$(RELEASE_PATH)/lib/diameter-<vsn>/src/info/` (`release_src_info`), in addition to the app-module sources.
- No `.hrl` of its own: `INTERNAL_HRLS` in `modules.mk` lists no `info/` entry; `diameter_dbg` includes the public `diameter/include/diameter.hrl` via `-include_lib`.
- These modules must not be depended on by runtime modules: `diameter_app_SUITE:xref/1` asserts that the only modules not in the app file that may be used from runtime modules are exactly `?INFO_MODULES ++ ?COMPILER_MODULES`.
- Any code here may only call applications that are declared or optional-by-documentation; `dbg` (runtime_tools) and `c:nl/1` (tools) are deliberately NOT app dependencies.

## Design Decisions
- They live outside the app's `modules` tuple so that `runtime_tools` (and, for the compiler modules, `syntax_tools`) does not become a mandatory dependency: the `diameter.app.src` comment states these are "only required if the dictionary compiler and debug modules (respectively) are needed/wanted at runtime, which they typically aren't".
- Because they are excluded from `modules`, they are also excluded from being loaded/started with the application; they are auto-loaded on demand from `diameter/ebin` only when someone actually calls them in a shell.
- `diameter_info` is kept as a separate module from `diameter_dbg` so the generic formatting machinery ("Support for rolling your own") is reusable and `diameter_dbg` stays a thin, diameter-specific layer; `diameter_dbg` reaches it via the `?I` macro.
- Both are `-moduledoc false` and carry no `-doc`/`-spec` attributes: they are intentionally undocumented and outside the published API (no `diameter_info(3)`/`diameter_dbg(3)` manual page — docs are generated by ExDoc from `-doc` attributes, and `doc/src/` holds no XML).
- Both are excluded from coverage measurement (`test/diameter.cover` `excl_mods`), but ARE included in the `dialyze` target in `src/Makefile`.

## Notes for Agents
- Nothing outside this directory calls these modules: the only repo references are `src/modules.mk` (`INFO_MODULES`), `test/diameter_app_SUITE.erl` (`?INFO_MODULES`, used by `modules/1` and `xref/1`), `test/diameter.cover` (coverage exclusion) and this CONTEXT.md — no test suite exercises their functions.
- `diameter_dbg:modules/0` reads the *installed* `diameter.app` via `file:consult(filename:join(code:lib_dir(diameter), "ebin")` — hence `versions/0`, `version_info/0` and `nl/0` cover only the runtime modules listed in the app file, never the info/compiler modules; it also requires the application to be on the code path.
- That `file:consult/1` call is flagged as a possibly unsafe function for security-sensitive projects, silenced by `-compile([{nowarn_possibly_unsafe_function, {file, consult, 1}}])` — keep the attribute if the call is kept.
- `diameter_info:version_info/1`/`versions/1` rely on the `app_vsn` attribute inserted at build time by `ERL_COMPILE_FLAGS` (`+'{attribute,insert,app_vsn,"$(APP_VSN)"}'`); modules built outside that makefile report `"?"`.
- `diameter_dbg:sizes/0`, `table/1` etc. silently skip non-existent tables (`ets:info/1` → `undefined`), so a service that is not running yields empty output rather than an error.
- `diameter_dbg:collect(diameter_peer)` rebuilds peer listings from `diameter:services/0` + `diameter:service_info/2` and asks watchdog/transport pids for their `{state, Pid}` message with a monitor; it can block briefly on those pids.
- `tables/0` does an `rpc:multicall(nodes(known), ...)` with a 30 s timeout (`?LONG_TIMEOUT`) and reports "no reply from <node>" for failing nodes — expect latency in multi-node setups.
- The `pp/1` AVP parser is a hand-rolled binary decoder (network byte order) independent of the generated dictionary decoders; it validates lengths/padding and reports `truncated_binary`, `bad_message_length`, `non-zero padding` etc.
